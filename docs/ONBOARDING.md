# Getting started with Scopehaven

Scopehaven is a local prototype for testing specific application requirements, recording evidence, investigating failures and comparing retests. It is not a certified customer-ready service. Start with its owned synthetic examples before connecting any application you operate.

For the mounted dashboard's assessment-to-export sequence, verified gate/import/export commands and their remaining acceptance checks, see the release walkthrough (not in the open edition).

This guide follows current main. Source code and verified results take precedence over counts in older documents or planned milestones in `FUNCTIONAL_INCREMENT.txt`. This guide establishes no production or deployed customer-system assessment.

To test an application you run, go straight to [Connecting a local application you own](#connecting-a-local-application-you-own). It includes a minimal profile, the observer to declare where Scopehaven can observe the app ([Observe what the app recorded](#observe-what-the-app-recorded-the-default)), assistant-turn checks and the full first-engagement command sequence. A copy of just the `scopehaven` folder is enough for that: `doctor` marks the framework targets unavailable, and nothing else is affected.

## The pieces in plain language

| Term | Meaning here |
| --- | --- |
| Application / target | The program being tested, separate from the Scopehaven workbench. |
| API | An interface programs call. Here it is an HTTP endpoint such as `GET /me` that returns a status code and JSON. |
| Connector | Code that sends the right requests, supplies test credentials and turns observations into evidence the runner understands. |
| Profile | A local JSON file naming one application, its address, test actors, checks and required permitted-use controls. |
| Contract / assertion | A precise expectation, such as “a member receives HTTP 403 when requesting a foreign tenant's record.” A check contains one or more assertions. |
| Test account / actor | An identity used for a scenario, such as an ordinary member or administrator. Use accounts created for testing with known permissions and synthetic records. |
| Credential | A secret proving access, such as a bearer token. A profile refers to an environment-variable name, not the token value. |
| Staging | An isolated test version of an application where its owner permits testing. The current connector accepts only a separate local HTTP application, not an arbitrary remote staging URL. |
| Observer | A separate way to inspect what actually happened inside the target, such as request-correlated retrieval events and an action ledger. |
| Positive control | A test proving permitted work still succeeds, so blocking everything cannot count as a repair. |
| Loopback | The address `127.0.0.1`, meaning this computer. Other devices cannot reach a server bound only to this address. |

A connector is needed because each application has different endpoints, credentials, workflows and evidence. Scopehaven cannot discover those permissions by looking at a website or infer them from a reassuring assistant answer. The owner must define expected behavior and the runner must have a suitable interface to test it.

Database-admin access is not a starting requirement. The SupportDesk fixture and HTTP lab need no database service. A local HTTP response test needs the target's API and suitable test-account credentials. Stronger backend claims need a narrowly scoped, trustworthy observation interface designed with the application's engineers. Giving a scanner unrestricted database credentials is not a substitute for that design.

## Choose the mode you want to learn

| Mode | What it connects to | What it can establish |
| --- | --- | --- |
| Owned backend-observer fixture | Scopehaven creates a fresh synthetic support application for each scenario, using real loopback HTTP and separate actor/control credentials. | Named policies about synthetic retrieval, permissions, cache revocation, approvals, concurrency and executed actions, including allowed-use controls. |
| Configurable local HTTP contracts | A separately running local application at a fixed `http://127.0.0.1:<port>` origin loaded from a private profile. | HTTP status and JSON response predicates. With a declared observer, also effects the app recorded (its SQLite audit table or tables, or an audit endpoint), or how its request log says each request was answered; without one, backend effects are not observed. |

The fixture uses deterministic orchestration rather than a live language model. Its “baseline” and “repaired” choices select two implemented demonstration builds. Selecting “repaired” does not modify another application's code. Forwarding and refund effects are synthetic ledgers, not real payments or external deliveries.

The fixture's observer is separately credentialed and request-correlated within this owned lab. That is useful evidence for these scenarios, not an independent audit of a customer system. A future customer observer needs its own trust and completeness design.

The configurable connector checks responses, and it can also read records the app keeps through observers the profile declares. A result is marked 'backend observed' only when an authoritative observer recorded the committed effect, or confirmed its absence over complete, settled coverage; telemetry counts for presence only, and missing, unsettled or partial evidence never passes. The run JSON records `backendEvidence` per row; the run HTML shows it only through the "Trusted backend observation available" assertion; SARIF and comparison exports do not mark rows. Every export states the settle limit. Without an observer a `403` and a reply without protected text can pass a response requirement while leaving “no protected data was retrieved internally” inconclusive. If that same response violates a configured predicate, the check can fail even though backend evidence is missing.

## Use the project runtime

You need Node.js 22.23.4 or newer in the 22 line, or 24.22.1 or newer in the 24 line; nothing else is required for the owned examples. From the repository root, in a terminal:

```sh
cd scopehaven-oss
./scopehaven doctor
./scopehaven check-config
./scopehaven assess --list
```

`doctor` checks, locally and without installing anything, which Node the launcher selected and where it came from, whether the workbench modules load, the evidence directory and the loopback port. Fix any `[fail]` line before continuing.

The launcher uses `SCOPEHAVEN_NODE` if set, then the project-local `.runtime/node-v24.22.2-darwin-arm64/bin/node` if present, then `node` on `PATH`. If the selected Node is outside `>=22.23.4 <23 || >=24.22.1 <25` (for example a global `24.18.0`), every action except `doctor` stops with exit code 2 and explains how to get Node 24 LTS from [nodejs.org](https://nodejs.org/en/download). Plain `node` or `npm` bypass that check. No `npm install` is needed. See [DEPENDENCIES.md](DEPENDENCIES.md).

`check-config` and `assess --list` show configuration, registered targets and readiness without running an assessment. `configurationValid: true` does not mean every target is available or that a requirement passed. The demos can be listed without an HTTP profile. Inspect `available` and `readinessReason`; HTTP targets separately report credential readiness. `connectionTested: false` remains correct for these setup checks.

### Try the owned fixture through the CLI

```sh
./scopehaven assess --target demo-vulnerable
./scopehaven assess --target demo-repaired
```

Each assessment writes a run into `data/`. Use `--out <directory>` to select another evidence directory. The current built-in suite (2.3.0) has 44 checks. The baseline returns 26 failures and 18 passes, and the repaired fixture returns 44 passes. These counts were observed on 2026-10-06, with the suite 2.3.0 change applied. Read the actual returned counts and evidence; older README counts describe an earlier suite.

Suite 2.3.0 adds five checks and five allowed-use controls to suite 2.2.0's 34:
- **TRUTH-03** (control **TRUTH-04**): when the refund handler blocks a member's refund, the internal note the app files records it as not completed, with no reference or amount the ledger does not hold. The control requires a permitted refund's note to match the recorded refund.
- **TARGET-BIND-01** (control **TARGET-BIND-02**): a refund asked for on "my last order" is recorded against the caller's most recent order, and the reply names that order. The control requires the alias to resolve to a customer's only order.
- **PROMISE-07** to **PROMISE-09** (controls **PROMISE-10** to **PROMISE-12**): a reason the customer states does not unlock a refund, a discount above the cap or a cancellation that the records do not support, and the reply says the records do not support it. The controls give the same reason on a case the records do support, which still gets its refund, discount or cancellation.

When suite 2.3.0 landed (2026-10-06), the five new checks failed on the vulnerable build and passed on the repaired one, and the five new controls passed on both. These checks read the fixture's structured note and its fixed reply text, and the stated reason is fixture request text, not a live model being persuaded. The stated-reason reading covers a declared table of constructions, so a phrasing outside that table reads as a plain statement. The note rule checks an id's shape, not its meaning: an identifier-shaped id that reads as prose, such as `Refund-20-CAD-processed`, passes it. Runs saved under suites 2.1.0 and 2.2.0 keep their own identity, and a pair across suite versions is incompatible and never reads fixed.

**Supplied context (fixture runs).** Each fixture attempt's evidence also records `suppliedContext`: the fixture's own account of what its reply path read, one entry per source row, tagged with that row's tenant. It is in the saved run and its JSON export, not in the HTML report or SARIF. From it, the internal contract view (`src/contract-synthetic.mjs`) derives a groundedness reading (`readings.groundedness`) beside each observation and check: which account-shaped values in the reply were absent from that record. The reading is report-only. No verdict, comparison, gate or export reads it, and the record sits beside the trace's events, so no delivery rule reads it either. The fixture writes both the reply and the record, so a clean reading proves nothing about the reply. HTTP runs have no such record and no reading.

CLI assessment exit codes are:

- `0`: no failed, inconclusive or error checks in the saved run. Explicit N/A checks do not count as passes and do not force a nonzero exit code.
- `1`: at least one failed, inconclusive or error check. An expected vulnerable-demo failure also uses this code.
- `2`: setup or execution could not proceed, such as an invalid option/profile, missing required credentials or unsupported runtime.

### Dashboard launch and its private access file

```sh
./scopehaven start
```

The server binds to `127.0.0.1` on port `4317` by default. Set `SCOPEHAVEN_PORT` before startup to choose another valid port. Use the numeric address printed by the server; the Host check does not treat `localhost` as interchangeable.

Current server code generates a per-launch capability and writes a private `data/local-access.html` page. Its link grants access for that launch, with an eight-hour default expiry. Restarting creates a new capability and replaces the launch page. Keep this file and its link private; do not paste them into reports, chats or a shared website. The workbench capability is separate from the target's test-account token.

Open the generated private launch page locally in your browser and select **Open Scopehaven**. Its link places the capability in a URL fragment. The frontend reads and immediately clears that fragment, keeps the key only in memory and attaches it to API requests. It does not store the key in cookies, localStorage or sessionStorage. Exports use authenticated fetch rather than placing the key in download URLs.

Reloading or leaving the page clears the workbench key. Reopen the private launch page to unlock; after a server restart use the newly generated page. A plain dashboard address shows **Workbench locked** and **Unlock workbench** opens the host's unlock dialog. The dashboard never receives the key. The core owner reports that unlock and lock/reload behavior passed in the mounted candidate. This documentation task did not open the private page or read its key; the core owner retains final release acceptance.

The learning sequence is: choose a build in **Overview** or **Targets**, run the baseline, open **Checks & evidence**, save investigation notes if useful, run the repaired target, use **Compare runs**, then select **JSON** or **Report** on the saved run. **Run history** searches loaded native runs; **External evaluation** previews separate tool-reported JSON. Notes never change computed results, and external previews never become native runs.

Stop a foreground server with `Ctrl+C`. Keep assessment evidence if you want to compare it later.

## Learn the separate HTTP connector with the owned lab

The simplest self-contained demonstration command is:

```sh
./scopehaven connector-demo
```

The script starts an owned local child process, supplies a generated synthetic token in memory, assesses its baseline, switches the lab to its repaired build, assesses again and closes the child. It saves runs, a comparison and an HTML report under `artifacts/http-contract-demo/`. It does not connect to a customer, model provider or database.

The script's acceptance assertions expect two baseline failures; the repaired response checks pass except for one backend requirement that remains inconclusive. Its comparison expects one restored response contract. These are expectations enforced by the script, not new successful execution results claimed here. A missing backend observer remains missing after changing the lab's response behavior.

For a persistent lab you can inspect and assess separately, run this in terminal A, from the `scopehaven` folder:

```sh
./scopehaven lab
```

It defaults to port `4319` and writes a generated synthetic credential file, `data/http-lab.targets.json`, and the lab's own authorization record, `data/http-lab.authorization.json` (the owned lab, its origin and its member account, for one day). Keep terminal A running. In terminal B, also from the `scopehaven` folder:

```sh
set -a
. ./data/http-lab.env
set +a
./scopehaven check-config --config data/http-lab.targets.json
./scopehaven assess --config data/http-lab.targets.json --target http-lab --authorization data/http-lab.authorization.json
```

ScopeHaven won't run a configured target without a matching authorization record: without `--authorization`, or with a record that is expired, edited or does not cover the target's origin and accounts, `assess` exits 2 before any request. If the record's window ends before a run is saved, ScopeHaven sends no further request and starts no further call to its observers (one already running can finish its reads), exits 2 (`authorization-window-ended`) and saves nothing, also when the window ends after the last request was sent ([RULES-OF-ENGAGEMENT.md](RULES-OF-ENGAGEMENT.md), section 5, lists each check); so leave room in the window for the whole run. For your own app, fill in [RULES-OF-ENGAGEMENT.md](RULES-OF-ENGAGEMENT.md), write the record and seal it with `node integrations/roe/cli.mjs seal draft.json record.json`; `node integrations/roe/cli.mjs check record.json --config PROFILE --target ID` shows whether a run would be allowed. The record's checksum is unkeyed, not a signature.

The `set -a` block exports the generated lab token without printing it. Source only this locally generated, trusted lab file; shell environment files execute as code. Never display or copy the token into documentation. Restarting the lab generates a new token, so reload its environment file in terminal B before another assessment.

To register this lab with the workbench server, start the server from a shell with that token exported:

```sh
SCOPEHAVEN_TARGETS_FILE=data/http-lab.targets.json SCOPEHAVEN_AUTHORIZATION_FILE=data/http-lab.authorization.json ./scopehaven start
```

Profiles and credentials are read at startup; restart after changing them. The authorization record is read again at each run: a dashboard run of a configured target it does not cover now is refused before any request. Open the current private launch page to use the dashboard. The CLI's `--config` option is the direct path for assessments.

## Connecting a local application you own

First agree on the application, permitted actions, synthetic records, test actors and expected behavior. Start with one denied operation and a matching allowed-use control. A target application may itself call external providers or databases even though Scopehaven's connector uses loopback; inspect that application and its data flow before testing. Loopback alone does not make a test free of side effects or provider spend.

Use `makeLabProfile` in `examples/http-lab.mjs` as the implemented profile example. The validated shape is:

- A file with `schemaVersion: 1` and a `targets` array.
- Each target has an ID, name, application ID, literal loopback origin, declared build label and data-context ID.
- Identifiers are 1 to 80 letters, digits, `_` or `-`, with no dots or spaces. This applies to the target `id`, `applicationId`, `contextId`, actor aliases, `principalId`, `tenantId`, check `id` and `actorId`. Write a version like `2.41.6` as `2_41_6`; free text such as `name`, `buildLabel`, `title` and `identityValue` may contain anything.
- `actors` maps aliases to declared principal/tenant/role information and optional `credentialEnv` references. References must use the dedicated `SCOPEHAVEN_TARGET_` prefix, such as `SCOPEHAVEN_TARGET_LAB_MEMBER_TOKEN`; unrelated environment secrets cannot be referenced. An actor without a credential reference makes an unauthenticated request; declaring a role does not grant that role on the target.
- By default the credential is sent as `Authorization: Bearer <value>`. For an application that reads its login session only from a cookie, such as a Next.js app using Auth.js, add `"credentialCookie": "<cookie name>"` to the actor, for example `"authjs.session-token"`, or `"__Secure-authjs.session-token"` when the app runs over https. The value is then sent only as `Cookie: <name>=<value>`, with no Authorization header. Cookie values may not contain `;`, `,`, `"`, `\` or whitespace; Scopehaven refuses them before any request. The owned lab accepts `"credentialCookie": "lab_session"`.
- For an API that takes a key in a header of its own, add `"credentialHeader": "<header name>"` to the actor, for example `"x-api-key"` or `"apikey"`. The value still comes only from the actor's `credentialEnv` variable, never from the profile, and is sent only in that header, only to the target's origin (never to an observer, never after a redirect), with no Authorization header or cookie. An observer whose credential names the same variable is refused at profile load, so it cannot send the key as its own credential. A name the connector, HTTP framing, tracing or a proxy owns is refused before any request: `Host`, `Cookie`, `Set-Cookie`, `Authorization`, `Proxy-*`, `Content-*`, `Connection`, `Transfer-Encoding`, `X-Forwarded-*`, `Sec-*`, the trace-context names (`traceparent`, `tracestate`, `baggage`), the method and URL override names and the like, and so is the target's correlation header. An actor uses a cookie or a header, not both. Identity proof works as for a bearer token: the probes send no key, a random key in the same header and each other actor's credential, each the way its own actor sends it, so a key never travels in another header. The run keeps, per actor, the header name and a domain-separated SHA-256 of the value (`credentialHeaders`), never the value, so a guessable key could be confirmed against it: use generated test keys.
- **Signed provider webhooks.** A check aimed at a provider webhook route (Twilio or Telnyx SMS and voice, Stripe events) declares `"webhook": { "provider": ..., "secretEnv": "SCOPEHAVEN_TARGET_..." }` beside its `body`. The connector then sends the body as the provider does (form or JSON), with the provider's signature header computed over the exact bytes, under a synthetic key held in that variable. Give the application under test the same synthetic key (for Telnyx, the public key `telnyxPublicKey` gives for the seed), and declare its public URL in `"url"` for Twilio when it sits behind a proxy. To show that it refuses forged or unsigned deliveries, add a check signed under another synthetic key, and one with `"signature": "omit"`. The key's variable is no other credential's (an actor's or an observer's, read-back included), and neither the target's correlation header nor the check actor's `credentialHeader` may be one of the provider's header names; the profile is refused at load otherwise. See docs/WEBHOOK-DRIVER.md.
- `checks` specify an actor, a method (GET, POST, PUT, PATCH or DELETE), a safe path, an optional JSON body for any method except GET, severity, evidence requirement and assertions. POST, PUT, PATCH and DELETE are writes: they can change data and run once.
- Every check requires exactly one status assertion. Use `{ "kind": "status.equals", "expected": 403 }` for one exact status. For a refusal that the application may express in more than one way, use `{ "kind": "status.in", "expected": [401, 403, 404] }`: 2 to 5 distinct statuses from 300 to 599. Allowed-use controls must use `status.equals`.
- JSON assertions support `json.equals`, `json.exists` and `json.notContains` at a JSON Pointer, for example `/record/tenant`. Each needs `pointer` and `expected`; for `json.exists`, `expected` is `true` (the field must be present) or `false` (it must be absent).
- `json.noForeignValues` checks that a response does not show other tenants' records. Declare each tenant's synthetic record values once on the target, then add `{ "kind": "json.noForeignValues", "pointer": "/reply" }` (no `expected`; pointer `""` scans the whole body) to any check whose actor declares a `tenantId`:

  ```json
  "tenantValues": {
    "tenants": {
      "acme":   { "identifiers": ["ORD-1001", "Ada Lovelace", "ada@acme.example"], "attributes": ["42.50", "Blue Widget"] },
      "globex": { "identifiers": ["ORD-2002", "bob@globex.example"], "attributes": ["19.99"] }
    },
    "attributesAlone": "inconclusive"
  }
  ```

  The value at the pointer is read as leaves (every string, every object key, and every JSON number as the response body writes it) under an allowlist rule. It fails only on another tenant's identifier written literally (its exact declared characters, spaces at its ends trimmed) as a whole token, in an occurrence that no value of another set of owner tenants overlaps, that the check's own request does not carry. It passes only when every leaf is in the plain form, the response body repeats no member name, and no other tenant's value occurs in any reading, except that under "attributesAlone": "ignore" an attribute seen as a whole token does not prevent a pass. Everything else reads inconclusive, never pass. A response body with a repeated member name in any object reads inconclusive, never pass, because JSON parsing keeps only the last of the repeated values (the connector counts repeats on the raw body); another tenant's identifier written literally in the parsed value still fails. The connector also keeps each JSON number's source text, so 7.50, 731e-400 and 12345678901234567 are read with the digits the body shows; a transport that reports neither, and a body nested too deeply for the connector's second parse, read inconclusive unless another tenant's identifier is written literally as a whole token, which still fails. The plain form: ASCII letters and digits, the other letters and decimal digits that occur in some declared value (only those that Unicode assigns to one of these scripts: Latin, Greek, Cyrillic, Armenian, Georgian, Cherokee, Hebrew, Arabic, Syriac, Thaana, NKo, Han with kana and Bopomofo, Hangul, Thai, Lao, Khmer, Myanmar, Devanagari, Bengali, Gurmukhi, Gujarati, Oriya, Tamil, Telugu, Kannada, Malayalam, Sinhala and Ethiopic; never Common, Inherited or default-ignorable ones; and in a script with letter case only letters that have an uppercase or lowercase partner), U+0020 spaces, U+000A line feeds and the punctuation . , ; : ! ? ' " ( ) - / @ # $, in a leaf that Unicode NFKC normalization leaves unchanged and that does not hold ASCII digits beside other decimal digits. An object member name that is an array index (0 to 4294967294, written without leading zeros) is outside the form when the object has another member, since JavaScript lists such names first and the body's order of the members is not known. Across the whole value at the pointer, every letter and every number character other than an ASCII digit, in every leaf and in every other tenant's declared values, must be of one script group (Han, kana and Bopomofo count as one; a script not listed counts as a group of its own); otherwise every leaf holding such a character is outside the form, since a reply in one script can show another script's value in look-alike letters. Likewise, when right-to-left letters or digits occur anywhere at the pointer together with left-to-right letters or digits (ASCII digits are left-to-right), or the response body holds anywhere a character of the right-to-left blocks (U+0590 to U+08FF, U+FB1D to U+FDFF, U+FE70 to U+FEFF, U+10800 to U+10FFF, U+1E800 to U+1EFFF) or a bidi control, every leaf at the pointer holding a letter or digit of either direction is outside the form, since the display order of one leaf depends on the text around it. Any escape (a backslash, a percent sign, an HTML entity), any markup character (< > * _ ~ `), any control, format, bidi, default-ignorable or combining character, a compatibility form such as fullwidth letters, any letter or digit no declared value uses (small capitals, IPA letters, spacing modifier letters, letters drawn like punctuation, the katakana long vowel mark, the Arabic tatweel), letters or numbers of two script groups (in the reply, or the reply's and another tenant's values), a tab, a carriage return and any other symbol puts its leaf outside the form, and such a leaf reads inconclusive unless another tenant's identifier is written literally in it (accepted recall loss: replies with curly quotes, markdown, emoji, accents written as combining marks, Indic and Thai text, any accented or non-Latin letter that no declared value uses, katakana words with the long vowel mark, a leaf that mixes scripts, such as a Cyrillic name in an English sentence, and every reply with a letter when other tenants' values use another script group or more than one, such as a Latin reply when another tenant holds a Cyrillic name, read inconclusive). The loose reading keeps only letters and number characters, each after Unicode NFKD decomposition with every combining mark removed, before and after a full case fold (the capital and the small sharp s both read ss), with ligatures and letters with a stroke or bar read as their base letters from a fixed list in src/tenant-values.mjs (æ ae, œ oe, þ th, ø o, ł l, đ d, ħ h, ƶ z, ғ г and others), Hebrew final letters as their base letters, the Persian yeh and keheh, the alef maksura and the teh marbuta as yeh, kaf, yeh and heh, katakana as hiragana, an iteration mark (々, ゝ) as the letter right before it (one with no letter right before it in its leaf reads as nothing and puts the leaf outside the form), the ideographic zero as 0 and every decimal digit as its ASCII digit; a declared value with ä, ö, ü, å or ø is also read with those letters spelled ae, oe, ue, aa and oe, and one with ae, oe, ue or aa also with those written a, o, u and a; a value seen there anywhere but inside its own whole literal occurrence (in another letter case, with its accents removed, with other spacing, punctuation or line breaks between its characters, or glued to more letters or digits) reads inconclusive, never fail. The joined readings are the loose reading with the leaf boundaries removed, in order (array items in order, each object key before its value, object members in JavaScript property order), once over every leaf and once over the leaves that are not object keys; a value seen there across a leaf boundary (["REF-", "5150"], {"REF": 5150}, {"first": "Grace", "last": "Hopper"}) reads inconclusive, never pass. The number readings are the loose reading and the joined readings with the zeros at both ends of every run of ASCII digits removed (a run of zeros vanishes); a value with a digit, read the same way, seen there reads inconclusive, never pass, unless an end of it that is a digit meets, past any zeros written right beside it, another digit written right beside it, so 17310 and 7.51 are other numbers than 731 and 7.5 ("Order 731", "Order 731 2 items" or "Order 7.31e2" for "00731", "7.5" for "7.50", "INV-42" for "INV-0042", "1,000" for "1000.00"; accepted recall loss: 7310 reads like 731, 1, 10, 0.1 and 100.00 read alike, and "ABC" reads like "ABC-000"; a value made of zeros only, such as "0.00", has no number reading). A token edge is open at a leaf edge, beside a space or line feed, or beside a run of the listed punctuation that ends at a leaf edge, space or line feed. No edge closes: any other neighbor is glue and reads inconclusive (a letter or digit of any case, a character outside the form, or punctuation that meets a letter or digit: "orderREF-5150", "REF-51501", "REF-5150-B", "/orders/REF-5150", "myjdoe42" for "jdoe42"; accepted recall loss: a longer word that holds a value, such as "Hoppers", "Anne", "annual" or "Joanna" for "Hopper" and "Ann", reads inconclusive too). A value whose first or last character is not a letter or digit ("@example.net") has an open edge there unless its neighbor is a character other than a letter, digit, space, line feed or listed punctuation. Also inconclusive: a value the actor's tenant shares with another tenant, an identifier two or more other tenants share (an attribute that only other tenants share counts as an attribute), a value seen only in occurrences that overlap an occurrence of a value with another set of owner tenants (the actor's own "Grace Hopper" holding another tenant's "Hopper", or another tenant's "5150" glued inside the actor's "REF-5150"), another tenant's identifier whose loose reading occurs in the request's decoded path, query, body keys, strings or numbers (an echo: "I can't share REF-5150" and a reply that returns that record cannot be told apart), a leaf that is a number (a JSON number, or a string of decimal text alone) equal to a declared decimal value written differently, leading zeros included ("7.50" for 7.5, "02134" for 2134, the string "7.5" for "7.50"). Declared values with the same loose reading are one value, and it is an identifier when any tenant declares it as one, so the result does not depend on declaration order. A declared value that Unicode NFKC normalization changes (decomposed accents, compatibility forms) is refused. Not seen: a value the profile did not declare, a paraphrase, a value spelled out or written in another spelling than these readings give ("Mohammed" for "Muhammad"), a value split across leaves in another order or with another leaf between its parts ({"num": 5150, "prefix": "REF-"}), a number rounded to other digits ("7.49" for "7.5"), a value written in look-alike letters of its own script group, a value with a letter replaced by another letter of the plain form (an accented letter some declared value uses, or an ASCII look-alike such as "O" for "0"), a number a renderer computes, such as the item numbers of a Markdown ordered list, and a display that sets a right-to-left direction itself. Attributes seen as whole tokens on their own read inconclusive by default, or are ignored under "attributesAlone": "ignore"; an attribute seen only partially, or only as a number written differently, reads inconclusive under either policy. The scan reads at most 131072 characters (524288 in its loose reading) and judges at most 262144 matches; past either bound it reads inconclusive. `identifiers` are specific values (record ids, e-mails, phones, account numbers, full names): one of another tenant's, written literally, fails the check. `attributes` are low-specificity values (amounts, item names, statuses): on their own they never fail. One assertion covers every declared value. Declare 2 to 16 tenants, up to 512 values per class and 2048 in all; values are strings (declare "30.00" as the app shows it) of 3 to 200 characters, spaces at their ends not counted, with at least one letter or digit, two values of one tenant may not share a loose reading, and a declared `tenantValues` that no check uses is refused. Saved runs and the exported suite carry per-tenant counts and positions ("tenant 2 identifier 3"), never the values; keep the profile private, since it holds them.
  Put it on boundary checks, not on identity or surface controls. Those controls are sent again at every probe point and must pass each time, so one reply outside the plain form leaves the actor not established and its boundary checks are withheld (inconclusive).
- `requiredControlIds` names nonempty response checks with severity `control` that must pass before a repair comparison can be verified.
- Optional `timeoutMs` on a check (1000 to 120000) gives one slow endpoint, typically one that runs a model turn, its own request budget instead of the three-second default. The run budget grows only by that check's extra time, and declared values may add up to at most 600000 ms per profile. The dashboard waits up to 11 minutes for a run to finish, but a browser can impose its own shorter response limit (Firefox's default is reportedly 300 s), so use the CLI for runs that may take longer than about five minutes. Evidence records the timeout actually applied to each request.

Every credentialed actor needs an **identity control**, and its login counts only with positive evidence. Declare the value that proves who it is on the actor, `"identityValue": "alice@example.com"`. Then add a required GET control with a 2xx `status.equals` and a `json.equals` predicate whose expected value is exactly that identity, for example `{ "kind": "json.equals", "pointer": "/user/email", "expected": "alice@example.com" }` on `/api/auth/session`. Status-only or negative checks (`json.exists` false, `json.notContains`) never prove a login, because public routes and signed-out session endpoints also return 200. Auth.js, for example, answers `/api/auth/session` with 200 and `null` when signed out. Controls of credentialed actors must expect a 2xx `status.equals`.

The identity control must be a session-derived "who am I" route that validates the credential exactly as your protected routes do (for example Auth.js `/api/auth/session`). A lookup such as `/api/users/alice`, which returns Alice's record to anyone signed in or to any cookie at all, cannot prove whose login it is. Each actor's identityValue must be unique.

Scopehaven proves each credentialed actor's login in every run:
- All of the actor's identity controls pass.
- Each identity control, and each surface control (a required GET allowed-use control of the actor on a protected route that is not an identity control, such as "list my own records"), passes again at a probe point immediately before the actor's first other check and after each of its other checks, so every check is covered by the point before it and the point after it. Each surface probe there must pass in full, its status and every predicate, as an identity probe must. One refused (401, 403 or the declared sign-in redirect) means the protected routes stopped accepting the credential the identity route still accepts: the login is then not proven for any check of the actor, required and identity controls included (`surface-refused`), at whichever point the refusal came, because a credential that flaps (an intermittent session store, a rate limiter) can be refused for a check that sits between two accepting points. An identity probe refused with the actor's own credential, the same way or with a complete 2xx JSON response that names another principal or none (the refusal test below), is the same direct evidence of a refusal and withholds every check of the actor too (`bracket-not-passed`); when an identity probe and a surface probe were both refused, the reason is `bracket-not-passed`. A surface probe that does not pass for another reason (a 500, a 404, a failing or inconclusive 200) leaves the checks that point covers not established (`surface-not-passed`), so they read inconclusive, and an identity probe that does not pass for another reason (a 500, a 404, a probe that did not finish) withholds only the checks that point covers. "Other" includes its non-identity required controls, so control-only actors are bracketed too. This catches a login that was not yet valid or that expired mid-run, and, except for a refused probe, binds the failure to the checks it covers: a check whose own two points passed keeps its own status when a later point fails (identity provenance per check, `actor-identity/5`).
- Each identity control is refused when sent without a credential, with a random credential of valid format in the same slot, and with each other credentialed actor's credential in this actor's slot. A refusal is a 401, a 403, the actor's declared `"signInRedirectStatus"` (301, 302, 303, 307 or 308), or a complete 2xx JSON response that does not name the actor. A 5xx, 429, 404, any other status, or a non-JSON or truncated 2xx response is not a refusal. A refusal status counts once it arrives, even if the body then stalls. An identity request that gets no status, or whose 2xx body never finishes (a timeout, network error or the run budget running out), leaves the login unproven as `identity-probe-incomplete`.

When all of that holds the login is proven, and the actor is established if its other required controls also passed. Only identity and surface controls are re-sent, and they are GETs; every other check, including any POST, PUT, PATCH or DELETE, still runs once. The extra requests share the run budget: an actor with N other checks and K identity and surface controls sends (N + 1) × K probe requests. Their statuses and predicate outcomes, never their content or the credentials used, are saved as `identityEvidence` (schema `actor-identity/6`, with the intermediate points under `between`; runs saved as `actor-identity/3`, `/4` or `/5` keep their earlier rules and never compare with `/6` runs). The regression gate and run comparison check that evidence with the same validator (`validateHttpRunEvidence` in `src/contracts.mjs`).

Identity is judged per check. The identity route's own proof (its controls passed, and were refused without the credential, with a look-alike and with other actors' credentials) holds for the whole run: when it fails, every check of the actor carries an inconclusive "Actor identity established by required controls" assertion naming the reason, required controls included, so a control that passed is inconclusive and no report, SARIF export, dashboard view or `assess` exit code shows that actor as a clean pass. A probe point that did not pass withholds only the checks it covers, the check before it and the check after it, and a check's reason is the more severe of its two points' (an unfinished probe, then an identity probe that did not pass, then a surface probe that did not pass), whichever point comes first; a refused probe, identity or surface, is the exception above and withholds every check of the actor. A required control is withheld only when the login was not proven for it (an unfinished probe or an identity probe that did not pass at a point that covers it, or an identity or surface probe refused at any point), never because a surface probe failed for another reason or another required control failed; an identity control's own row rests on the route proof and on no probe having been refused. When the login was proven and only a non-identity required control failed, the actor is not established and its boundary checks carry `control-not-passed`, while the required controls keep their own status. A boundary check whose own predicates and effects passed and whose identity or allowed use was not established for it (any identity reason: a login not proven for it, a required control or a surface probe that did not pass, an unattributed change) is recorded as the distinct state **prohibition observed, identity or allowed use not established**: its `status` stays `inconclusive` (it is never a pass, the gate reports `prohibition-observed-identity-unproven` and credits no repair on it, and a pre-registered study scores it as an abstain), and its `decision` field, the SARIF `scopehavenDecision` property and the HTML report say `prohibition-observed-identity-unproven`, so an adopter can see that the application behaved as the contract expects and only the identity or allowed-use evidence around it was missing. Every other row's `decision` is its status, and a not-applicable row carries none; the validator recomputes both, so a stored third state cannot be edited into a pass or hidden as plain inconclusive. The gate is per actor: it reports `identity-not-established` whenever the actor's identity route or any of its probe points did not hold. A comparison is per row: a row whose identity was not proven for it is never labelled restored or fixed, while a row whose own two points proved the login can be, so a comparison can carry a repair label while the gate for the same pair still exits 1 with `identity-not-established`. A baseline row whose identity was not proven for it is unverified, and the gate reports `baseline-identity-not-established` when the baseline did not prove an actor's login. A baseline whose only failure was a non-identity control still shows the fix. For an established actor that declares `signInRedirectStatus`, a non-control check answered with that redirect is inconclusive, because the login did not hold for that request. A 403, a 404 or any other answer outside 2xx counts as a refusal only when the same actor has an earlier complete 2xx on a protected route, that is, a surface control in its passed brackets; without one it reads inconclusive (`surface-unproven`). A 401 on a non-control check of a credentialed actor is an authentication failure, not an authorization refusal, and reads inconclusive (`unauthenticated-401`), unless the actor declares `"refusesWith401": true` (the app answers authorization denials with 401, as Open WebUI does) and has a surface control in its brackets; declared without one, it reads inconclusive (`surface-unproven`). A lifecycle post-change check is the declared exception: its 401 is the refusal the lifecycle policy expects. Evidence of credential loss on an actor's own main rows, rather than at a probe point, stays row-level: an `unauthenticated-401` or sign-in redirect on a boundary check, or a required control answering a refusal status, withholds or fails that row and the gate fails, but a comparison may still credit other rows of that actor, and a change or a captured value that actor made still counts as attributed. These rules date from the identity evidence schema `actor-identity/5` (the 401 and 403 rules from `actor-identity/4`), and `actor-identity/6` adds `restsOn` (below); runs saved as `actor-identity/4` keep their per-actor rules, and runs saved as `actor-identity/3` keep the earlier rules, where a credentialed 401 or 403 counted as a refusal without a surface control. A confirmed failure is still reported as a failure, an error stays an error, and not-applicable checks are unchanged. Actors without credentials, such as an anonymous visitor, need no identity control.

**Resting a check on same-route allowed uses (`restsOn`, `actor-identity/6`).** By default one failed required control withholds every boundary check of its actor (`control-not-passed`). A boundary check of a credentialed actor that sends no body may declare `"restsOn": ["NOTE-4"]`: 1 to 8 of its actor's required allowed-use controls, each with the check's method, one declared 2xx `status.equals`, no body, a record predicate (a `json.equals` on one top-level field to two words of text, without a digit, that no request of the profile carries) and a declared partner (another required control of the actor and method on another record of the same route with a record predicate on the same field at another value), on the check's route at another record (the same literals and parent records, a last record position that is an identifier literal or an integer capture, and no query). For example `GET /api/notes/9` expecting 404 rests on `GET /api/notes/4`, whose partner is `GET /api/notes/3`, both declaring `/title`. Load refuses any listed control outside that form. At run time the check drops `control-not-passed` only when every listed control showed its served record and passed with no settlement or attribution tag and no claim reading other than success, every failed required control of the actor showed its served record and failed only on a positive effect or success claim that coverage gaps alone left missing (or whose pass background attribution withheld) with no matching commit under another actor, no failed control shares a stem word of the route, a pairing twin, a selector name or a captured value with the check, and a listed control was sent after the check and after every failed control. Every later step (sign-in redirect, `unauthenticated-401`, `surface-unproven`) still applies. Each row records its route segments and control-scope evidence as keyed digests, the exported suite binds the restsOn lists, record predicates, partners and related controls, and a run that rests on a release validates only against its suite. A withheld row's summary names its reason, and for `control-not-passed` the required controls that did not pass. The route, anchor, served-record and relation rules come from `src/http-rests-on.mjs`; see KNOWN-LIMITS for what the release cannot see.

**Limits:**
- Identity is proven per check, at the probe points around it. A brief outage strictly between the two points that cover a check, or a session that recovers between them, is not detected.
- A "who am I" route that accepts credentials the protected routes reject, for example one that skips the expiry check, is caught only through a surface control: give each credentialed actor a required GET control on a protected route. Without one, every answer outside 2xx to the actor's boundary checks (a 403, a 404, a redirect) reads inconclusive (`surface-unproven`): a protected route that rejects the credential cannot be told apart from one that refuses the request.
- A surface control is not itself probed: Scopehaven re-sends it with the actor's credential and requires the 2xx and every predicate, but never sends it without the credential. A required GET control on a public route therefore satisfies the rule without showing that the credential was accepted anywhere protected, and a 403 elsewhere then counts as a refusal on that basis alone. Choose a surface route that needs the login (one that answers 401 or redirects when signed out).
- A response status outside 100 to 599 (for example `HTTP/1.1 999`) is recorded without a usable status. The gate then refuses the whole run as invalid evidence (exit 2) rather than reporting `identity-not-established` (exit 1). It never passes, but rerun against a target that answers with standard statuses.
- The saved evidence is internally consistent but not signed. Someone who can edit saved runs can forge a consistent record, so keep evidence directories private. With the exported suite, the gate also binds each actor's identity controls, its identity predicate and its refusal statuses.

### Observe what the app recorded (the default)

A response check reads what the app answered. A permission failure can look like a refusal and still act: the reply says "not found" or "pending" while the database records the write. So a new profile declares an **observer** where Scopehaven has one for the app (a SQLite, Postgres or MySQL database, an audit endpoint, or a loopback sink for the requests and mail it sends; a request log is not used in onboarding (below)), and gives every write-shaped check (a POST, PUT, PATCH or DELETE that can change data, including an assistant turn that asks for an action) an **effect assertion**. Every result then says which kind of evidence it rests on:

- **Backend observed.** Scopehaven's HTTP checks can declare observers on records the app keeps. A result is marked 'backend observed' only when an authoritative observer recorded the committed effect, or confirmed its absence over complete, settled coverage; telemetry counts for presence only, and missing, unsettled or partial evidence never passes. A request log's refusal line never establishes that a write did not happen. When the candidate run declares observers and at least one restored row was backend observed, a repair comparison is labeled "Response contracts restored; backend observed where marked"; when every restored row rests on its response alone, it is labeled "Response contracts restored", as for a response-only profile. Only rows whose run JSON shows `backendEvidence: "observed"` rest on recorded effects, and comparison exports do not mark rows. The run JSON records `backendEvidence` per row; the run HTML shows it only through the "Trusted backend observation available" assertion; SARIF and comparison exports do not mark rows. Every export states the settle limit.
- **Response only.** No observer decided the effect, so the row records `backendEvidence: "unavailable"`. A pass means the response met its contract and says nothing about what the app wrote. A repair is labeled "Response contracts restored", with the scope "Response comparison only; backend effects remain unverified."

**Whose records.** Every shipped observer except the request-path ones (the hold gate and the egress and SMTP sinks) reads records the application itself writes: its database, its audit endpoint or its log. They show what the app recorded; they are not independent of an app or agent that can edit those records, so a boundary pass that rests only on them reads inconclusive (custody, next paragraph): an app that writes without recording, or records under the wrong actor or action name, would otherwise pass a boundary check on its own records. An allowed-use control can still pass on a record of an action that never happened. Choose an observer accordingly, and cross-check (below). The two sinks keep their records in the observer's own process: the app can add a send but cannot alter or remove one. They show whether a send to a declared host or mail domain happened, never who made it, and their limit is routing (below).

**Custody decides boundary passes.** In a boundary check (any severity except `control`), every effect clause that passes needs at least one deciding window from an observer held outside the application: the hold gate, the egress recorder, the SMTP sink or a provider feed. A pass decided only by records the application can write (its database, audit endpoint or log) reads inconclusive with `subject-writable-custody`, and the row says what could decide it: an egress recorder or SMTP sink for a send, a hold gate for a tool call in a sequence, or, for the application's database writes, that no shipped observer held outside the application sees them. A fail stays a fail, and nothing is upgraded. Allowed-use controls keep their verdicts and carry custody as a tag only; a record the application can write may show an allowed action happened when it did not. "Backend observed" keeps its coverage meaning, so a row can be backend observed and still inconclusive for custody. In the onboarding examples, the two refund prohibitions in the `sqlite-audit` and `http-audit` profiles read inconclusive on the repaired (`secure`) build, so that comparison restores the disclosure row only and carries no repair label ("No verified repair"), and the gate reports `comparison-incomplete`. The `egress-recorder` example decides both refund prohibitions from the payment calls the app sends, a record held on the request path, so their clauses have custody `independent`. On the repaired build each prohibition's per-order clause passes, but its host-wide clause is withheld by settlement (below), because the allowed refund after it makes a payment call that fits it; so both prohibitions read inconclusive there and that comparison also carries no repair label ("No verified repair"). For a repair label on a write-shaped prohibition under custody, see the n8n exercise (a walkthrough kept outside this repository; [KNOWN-LIMITS.md](KNOWN-LIMITS.md#the-examples-and-the-exercise)), whose prohibition's only effect clause is decided by an egress recorder and is followed by no check that sends to the same host (observed in one recorded run on a private build; no merged test pins it). Either way, a request-path observer shows what the app sent, not what it wrote: the example's sink can show that no payment call went out for another company's order, not that no refund row was written. Records saved before this rule (no custody field) are refused as `effect-pre-custody` or `sequence-pre-custody`; re-run them.

Choose the observer from what the app keeps, in this order of preference. Every example below is a complete profile for the same synthetic two-company support app and the same direct and assistant scenarios; the `response-only` profile leaves out the assistant action check, which it cannot observe:

The examples show the difference on one defect. The leaky build of the example app answers a cross-company refund with 404 but commits it. The `sqlite-audit`, `http-audit`, `sqlite-snapshot` and `egress-recorder` profiles fail that check. The `response-only` profile passes it on the response alone, and the row says `backendEvidence: "unavailable"`.

**The request log (`audit-file`) is not used in onboarding.** It reads the app's own logged answer as the effect in both directions: a logged refusal reads as "no write" even when the write was committed, and a logged 2xx reads as a committed write even when nothing was written, and both are marked backend observed. Never declare `effect.none` on it, and do not treat an `effect.exists` or `effect.count` on it as evidence that a write happened.

OpenTelemetry traces (`otel`) and MCP logs (`mcp-log`) are presence-only: they can fail a check by showing an effect happened, but never pass one by showing it did not.

**Requests and mail the app sends.** Some effects leave the app instead of landing in its records: a webhook, a call to a payments API, an email. Point the app's outbound HTTP at an `egress-recorder`, or its mail host at an `smtp-sink`, next to the observer for its records. Both are loopback sinks that answer the app themselves and, unless an egress destination opts in to forwarding to a loopback upstream (**What happened upstream**, below), never forward or relay anything, so nothing the app sends during a test leaves the machine through them. Each request is a `send` effect named by its destination host (source `http-egress`), and each mail recipient one named by the recipient's domain (source `smtp-capture`), for example `{ "kind": "effect.none", "select": { "source": "http-egress", "name": "api.pay.example" } }`. Without `routing` and a `witness` a sink is presence-only. With them, Scopehaven sends the witness request after each check that declares effects, and the window is complete only when the app's resulting send reaches the sink. The witness proves the declared route was live for that request, not that the app has no other way out: for that, run the app on a network whose only exit is the sink (on macOS, `--confine`, below). The `egress-recorder` example points the example app's payment client at the sink with `routing: "base-url"` and declares each refund's path (`POST /v1/refunds/A-1`), so one order's refund call is told apart from another's; its witness route is `GET /api/egress-witness`. It sees the payment call, not the refund row. Each prohibition also has a host-wide clause (no payment call at all in its window), which catches a call to an undeclared path; since the same-action twins after it make payment calls that fit it, settlement (below) withholds that clause as `effect-outside-window` on a clean build, so the prohibition reads inconclusive there while its per-order clause passes. A build that passes its prohibitions without the sink seeing a forbidden refund might still:
- commit the refund without calling the payments API;
- send the call to another address, around the sink;
- delay the call past the end of the run.

So every absence pass the sink decides is scoped on its row and in the run's limitations as **routing declared, not shown exclusive**: the declared route was live (the witness reached the sink) and carried no matching send, which does not show that the app made no such call by another way out. It is also bounded in time: no matching send was recorded from the check's start through the run's final mark, and a send made after the final mark is outside every window. The report, SARIF, the comparison export and the gate summary print both on each such row, and the compact summary prints the run's limitation. When the app's mail goes through this recorder and the target declares no provider feed and no SMTP sink, the run also states that an egress-only mail prohibition cannot see a vendor SDK that sends to its compiled-in endpoint (a pinned SDK route): declare the provider's feed beside the recorder and select both sources.

**Confining the app to its sinks (`--confine`, macOS).** Let ScopeHaven start the app instead of starting it yourself:

```sh
./scopehaven assess --config /absolute/private/profile.json --target <id> --out /absolute/private/evidence --authorization /absolute/private/authorization.json --confine /absolute/private/launch.json
```

```json
{ "schemaVersion": 1,
  "command": ["/absolute/path/to/node", "server.mjs"],
  "cwd": "/absolute/path/to/app",
  "env": { "HTTP_PROXY": "http://127.0.0.1:40996", "PORT": "4100" },
  "envFrom": ["APP_DATABASE_URL"],
  "allow": [{ "port": 5432, "reason": "the app's own Postgres" }] }
```

The app runs under `sandbox-exec`, and every outbound connection it or any process it starts makes is refused by the kernel, except TCP over IPv4 to the declared egress recorders' and SMTP sinks' ports and the ports in `allow`, each with its reason. A send around the route (a direct connection, another port or socket, a client or child process that ignores the proxy) fails in the app instead of passing unseen. The kernel rule admits every IPv4 address of this machine at an allowed port, not loopback alone, so ScopeHaven also checks that it is itself the only listener on each sink port before the launch, about once a second during the run and at stop, and refuses the run when anything else listens there (a `[::1]` listener at a sink port is refused by the rule itself). Before the app starts, a self-test under the same profile connects to a canary port it does not allow and to `[::1]` at an allowed port, both of which must be refused or the run is refused, and records what the rule admitted at an interface address. The app gets `PATH=/usr/bin:/bin`, `HOME`, `TMPDIR`, `env` and the `envFrom` names copied from ScopeHaven's environment (only their names are recorded), nothing else. It must listen on the target origin, which must be free before the launch: ScopeHaven refuses to start when anything already answers there, waits for the app (`readyTimeoutMs`, default 15000), refuses the run when any listener on that port is outside the launched process tree, and stops the whole tree after the run or when ScopeHaven is interrupted. A port a declared provider-side endpoint uses (a forward upstream, request feed or provider feed) cannot be allowlisted, because that is the way around the sink. An app that calls a hosted model or another service off the machine needs a loopback relay for it on an allowlisted port; what the relay forwards is outside every window. The saved run carries a confinement record (the profile and its sha256, the sinks and allowlist, the self-test, the sink-port checks, the kernel's denials for this run, and its limits), each absence pass the sinks decide reads **routing confined** on its row with a pointer to those limits, and the run's routed-absence limitation is replaced by the confined one, still bounded in time. Off macOS, inside another sandbox, or when a check fails, the launch is refused: nothing starts unconfined, no run is saved, and a refusal receipt (`confine-refusal-<time>.json`) is left in the evidence directory. The record's limits matter when reading a confined pass: only outbound connections are confined, so a process outside the launched tree that the app reaches by IPC, a file or an inbound connection is not. [KNOWN-LIMITS.md](KNOWN-LIMITS.md) lists them.

**Declaring the target's channels (`channels`).** An absence pass says the observers that decided it saw nothing matching. An effect that left the app by a way none of them watches (a cache, a file, a direct API call, a queue a worker drains) is in no window, so a clean window would pass it quietly. Declare every channel the app can leave an effect through, and which observer holds each one's records:

```json
"channels": {
  "confinement": "confined",
  "list": [
    { "id": "payments", "kind": "egress", "observedBy": ["sink"], "names": ["api.pay.example"] },
    { "id": "orders-db", "kind": "store", "observedBy": ["db"], "names": ["orders", "refunds"], "port": 5432 },
    { "id": "jobs", "kind": "queue", "observedBy": ["jobs-audit"], "names": ["job.enqueue"] },
    { "id": "uploads", "kind": "files", "observedBy": [], "names": ["/srv/uploads"] }
  ]
}
```

`kind` is `store` (database tables or stores), `outbox`, `egress` (destinations the app calls, mail included), `files` (files or directories) or `queue` (queues or jobs). `observedBy` names declared observers of a type that reads that kind of channel itself: a snapshot for a store (its tables, not the audit table the app writes beside them); an audit table for an outbox or a queue, which are consumed by design (a snapshot's net change could miss the very entry, and an SMTP sink records what was delivered, which is egress), and it observes only as completely as the app logs every entry; an egress recorder, an SMTP sink or a provider feed for egress. No shipped observer reads files the app writes (the `audit-file` observer reads the app's own request log), so declare a files channel with an empty list. The app's telemetry (`otel`, `mcp-log`) and audit endpoint (`http-audit`) observe no channel. An empty list declares a channel nothing observes, which is honest and makes absence passes read inconclusive. `names` are what the channel is in its observers' vocabulary (tables for a snapshot, action names for an audit table, hosts for an egress recorder, domains for an SMTP sink); every one must be in an observing window's vocabulary. `port`, optional and only on a store channel watched by a `pg-snapshot` or `mysql-snapshot` that connects to that port on this machine, is the allowlisted port of a confined launch that the app reaches that database by. `confinement` is `confined` (run it with `--confine`, above) or `unconfined`. The declaration is compared as written, so the same channels in another order are a different declaration (a run and the suite, or two runs, then do not match).

With a declaration, a boundary check's absence pass (`effect.none`, `effect.only`, any `effect.count`, since an exact count also says no more happened, or a claim rule's such clause) counts only when, in that check's own window, every declared channel was observed (an authoritative window from one of its observers with complete coverage; a store may read net change between snapshots, and the report says a write undone within the window is invisible) and no window of a declared observer of a type that can observe a channel (listed by a channel or not), complete or not, carried an effect that happened or may have (committed, or still open: started or unknown) that the check's bounding clauses (a passing `effect.count` or `effect.only`) do not select (that effect could be the one the check is about, sent that way instead; an `effect.exists` bounds nothing, so it accounts for nothing, and a bounding clause selects only committed effects), and the run is a confined launch of a local app whose every sink is an observer of a declared channel and every allowlisted port a declared channel's `port`, whose kernel log was read through, and which logged no refused connection while the app ran. Otherwise the pass reads **inconclusive** with `channel-unobserved:<channel>` for each channel not observed, `channel-unaccounted:<channel>` for each such effect's channel (the channel that names it, or, when none does, the channels whose observer recorded it; until per-platform ignore lists land, a background write does too), and `channels-undeclared` when an observer no channel lists recorded such an effect on no channel's names (it may have gone by a channel the declaration leaves out, or be an ordinary row the rule cannot tell apart; the report names the observer, and a bounding clause that selects such rows accounts for them), when the run is declared unconfined, is a forwarded or remote target, carries no valid confinement record, lets the app reach a sink no channel's observers include, allowlists a port no channel names (a model relay, for one), logged a refused connection (the app tried a way out nothing declares), or its kernel log was not read through. The sealed row keeps the status the effect rules decided; the report, SARIF, the comparison and the regression gate read the pass as inconclusive and name the reasons, the gate is not clean, and two runs with different declarations do not compare. Fails, allowed-use controls and every other row are untouched. A profile without `channels` behaves as before, and its report states **channels undeclared**. Confinement covers outbound network connections only: a file, a local store or IPC that the declaration leaves out is not shown absent.

Pairing it with an observer of the app's records closes the first gap but has a cost. With `sqlite-audit` added, the repaired build's prohibitions read inconclusive, because the audit clauses are records the app can write, and the comparison carries no repair label. A build that writes the refund silently fails both.

**Effect assertions.** Add `effects` to a check, at most 10. They match committed effects only. Each selects events by `source`, `actor`, `name` (an action name from the observer's vocabulary, or `{ "prefix": ... }`), `operation` or `resource`:

- `{ "kind": "effect.none", "select": { "source": "sql-audit-table", "actor": "agent-b", "name": "refund.create" } }` on the forbidden write, with `"evidenceRequirement": "backend"`. A recorded match fails the row even when the response was a refusal. Add a second `effect.none` on the target resource without an actor, `{ "source": "sql-audit-table", "name": "refund.create", "resource": "orders/A-1" }`, so a write the app records under another actor, such as the order's owner, still fails the check.
- `{ "kind": "effect.count", "select": { ... }, "expected": 1 }` on its allowed-use twin, so the permitted write happened exactly once. A count needs a named `source`, an exact `name` (not a prefix) and exactly one authoritative observer that sees it. Use `effect.exists` where only presence can be shown. On `effect.exists` and `effect.count`, pin an `actor` and a `resource`, and give each twin its own record (in the examples, every refund twin refunds a different order): a late commit from an earlier check with the same pin can still land in this window and satisfy it.

**Nothing else happened (`effect.only`).** A check can also declare that every committed effect its observers saw is one the request called for, for example a refund that must not also apply a discount or cancel a plan:

```json
{ "kind": "effect.only",
  "expect": [{ "select": { "source": "sql-audit-table", "actor": "agent-b", "operation": "insert", "name": "refund.create", "resource": "orders/B-2" }, "count": 1 }],
  "allow": [] }
```

- `expect` lists the effects the request calls for, each at most `count` times (1 to 1000; a bare selector means 1). `allow` lists side effects that are acceptable in any number. Optional `operations`, `sources` and `counterparts` narrow what is judged; the rules are in [integrations/collateral/README.md](../integrations/collateral/README.md) (`only.mjs`).
- Every selector must name its effect (`name`, exact or `{ "prefix": ... }`). A name-free selector, a count below 1 or an unknown key is refused when the profile loads, with the code `selector-name`, `expect-count`, or `field`, `expect` or `selector`.
- One committed effect outside the declared set fails the check, from any observer, whatever the reply says; a match beyond its count is outside it too. A fail stays a fail. The clause does not show that the expected effect happened: pair it with an `effect.count` twin.
- Its pass is a claim that nothing else happened. It covers only the operations and names the observers in scope report, and the row names them. A net-only snapshot, presence-only telemetry, an unsettled or partial window, a failed observer or no authoritative observer for a judged operation reads `missing`, `unobservable` or `observer-failure`, never pass.
- **Custody limit.** The pass takes the weakest custody of the observers that decided it, so in a boundary check any record the application can write among them (its audit table, database or log) holds the pass at inconclusive (`subject-writable-custody`). Only a claim whose deciding observers are all held outside the application (an egress recorder, SMTP sink or provider feed; narrow `sources` or `operations` to them) can pass. Allowed-use controls keep their verdicts and carry custody as a tag.

`integrations/collateral/refund-only.profile.json` is a worked profile for the example app's `refund-plus-discount` and `refund-plus-cancel` builds: both fail its `effect.only` check from the app's audit table, and the `secure` build reads inconclusive for custody while its paired controls pass.

**What a request carried (declared body fields).** By default an `egress-recorder` keeps each outbound body only as a salted digest, so a check cannot tell a refund of 25 from one of 250. A destination may opt in to reading named scalar fields of its JSON bodies:

```json
"destinations": [{ "host": "payments.example.test", "paths": ["/v1/refunds"],
  "capture": { "pointers": ["/amount", "/currency", "/ticket_id"], "maxBytes": 16384 } }]
```

- Up to 16 JSON pointers per destination (64 per sink); `maxBytes` (1024 to 65536, default 16384, never above `maxBodyBytes`) bounds what is buffered to parse. The whole body is never captured.
- Fields are read only on the destination's declared `paths`, so a destination with `capture` must declare `paths`. A send on any other path of the host records `path-undeclared` and no values, so a `fields` clause over it reads `missing`.
- A pointer naming a secret-like key (password, passcode, pw, token, secret, authorization or auth, cookie, session or sid, CSRF, JWT, HMAC or signature, key, credential, card or cc, CVV, IBAN, bank account, account or routing number, OTP, MFA, 2FA, passport, PAN, PIN, SSN, SIN, national or tax id, date of birth) is refused when the profile loads, even as an inner key (`/card/last4`) or a compound key (`/customer_ssn`, `/pinCode`, `/cc_number`, `/signingKey`). Keys are folded with NFKC first, and a key that still holds a character outside printable ASCII is refused. A string over 200 characters, or a value shaped like a secret, a card number (a Luhn-valid 13 to 19 digit run or integer, any one separator between digit groups) or a nine-digit NNN-NN-NNNN identifier (any one separator or none), is not stored; objects and arrays are never captured.
- The captured values are written to the run record and every export, with the declaration (`observers[].capture` on the run). See [DATA-HANDLING.md](DATA-HANDLING.md).
- Form-encoded APIs (many payment and messaging providers): add `"encodings": ["json", "form"]` to `capture`, for example `"capture": { "pointers": ["/amount", "/currency", "/metadata/order_id"], "encodings": ["json", "form"] }`. Form fields are read as exact text, `metadata[order_id]` maps to `/metadata/order_id`, and the run lists the host in `observers[].captureForm`. Compare amounts in the destination's wire units (`{ "pointer": "/amount", "gt": 5000 }` for minor units) and ids with string operands. A decimal form value never matches a number; pin it as text too (`"in": [105.5, "105.5"]`). It reads as different only toward a fail: a clause that would read missing reads fail when a decimal that no common reading makes the pinned number (the separator as a decimal or group mark, any rounding to the pinned precision and one unit more) decides it fail, so `amount=105.05` fails a count pinned to `in: [105.5, "105.5"]` while `105.50` stays missing; an absence or an allow never passes on such a reading. A string pin counts as a number only beside a number pin of the same value, and a pinned 0 is never decided. Such a fail compares like any fail: a repair to the pinned amount is credited. Only POST sends are read. A form send with a URL query, a fragment or a Cookie header, or a body a server could parse two ways, leaves every declared field unknown; send `charset=utf-8` if values may be non-ASCII.
- **Retries with an idempotency key.** If the app retries provider calls with a key header (Stripe's `Idempotency-Key`, PayPal's `PayPal-Request-Id`, or a webhook event id), declare it on the destination, `"idempotency": { "header": "idempotency-key" }`, and count applications rather than sends: `{ "kind": "effect.count", "countBy": "idempotency-key", "select": { "source": "http-egress", "operation": "send", "name": "payments.example.test", "resource": "POST /v1/refunds" }, "expected": 1 }`. An exact retry under the same key counts once; a retry with a new key or no key counts twice; a changed retry, a concurrent one or a key reused from an earlier check reads inconclusive. List per-attempt tracing headers in `volatile` (an allowlist) so they do not make retries differ. For webhooks that re-sign every delivery, use the event id header as the key and list the scheme's signature and timestamp headers as volatile, for example `{ "header": "webhook-id", "volatile": ["webhook-signature", "webhook-timestamp"] }`; the body stays bound, so a changed payload never collapses. The recorder does not verify signatures, so declaring a timestamped webhook signature or timestamp header volatile asserts that the destination verifies one signing secret per URL: a send of the same body under the same key, signed under a second secret in another second, reads as a re-signed redelivery of the first. Such a header leaves the request head only when each of the scheme's headers appears once and parses exactly (a rotation list in full, up to four entries) and the timestamp lies between 300 seconds before the recorder started and 60 seconds after the send arrived; otherwise it stays bound with its raw value. A destination that declares `idempotency` cannot name a webhook signature or timestamp header as its correlation header: the profile is refused at load. `x-hub-signature`, `x-hub-signature-256`, `x-shopify-hmac-sha256` and `x-twilio-signature` may be declared but have no effect and stay bound: each is a MAC with no timestamp, so a redelivery under the same secret repeats it exactly. If you hold the secrets the destination verifies with, declare `signing` instead (recommended): `{ "header": "webhook-id", "signing": { "scheme": "standard-webhooks", "id": "webhook-id", "timestamp": "webhook-timestamp", "signature": "webhook-signature", "secretEnv": ["SCOPEHAVEN_TARGET_HOOKS_SIGNING_A"] } }`. The scheme is one of `stripe` (one header `t=<unix>,v1=<hex>` over `<t>.<body>`, keyed on the secret's bytes as given; also for senders that copy Stripe's form under their own header name), `standard-webhooks` (Standard Webhooks and Svix: `v1,<base64>` over `<id>.<t>.<body>`, keyed on the base64 secret after an optional `whsec_`) or `slack-v0` (Slack and Zoom: `v0=<hex>` over `v0:<t>:<body>`); name the headers your sender uses. `secretEnv` lists 1 to 4 `SCOPEHAVEN_TARGET_` variables holding the secrets the destination verifies that URL with: declare every tenant's secret when several share one URL, since each secret counts as its own scope. The recorder reads them once, keeps them only in memory and verifies each send; a re-sign then counts once only when both sends verify under the same declared secret, and any collapse there, an exact replay included, needs the later send to arrive within `dedupeSeconds` (default 300; up to 86400) of the first send (its arrival, or its verified signing timestamp if earlier), so declare no more than the destination's own key retention. Pass the secrets only through the environment of the Scopehaven process, never on a command line, in a profile, a settings file or a log; a variable that is also an actor's or observer's credential or a forward `proofEnv` is refused, as is a value that equals a proof secret or two secrets that are the same HMAC key. A missing or unusable secret does not stop the run: its sends stay unverified and the run says so. Do not rotate a signing secret during a run: a send under the new secret reads as its own application. A destination uses either `signing` or a timestamped header in `volatile`, never both. For an event id inside the body (an outbox message), declare `{ "pointer": "/event_id" }` instead of a header: the same id redelivered is one event, and a new id for the same event is a duplicate. An `effect.only` clause may opt in the same way, `"countBy": "idempotency-key"` beside its `expect` and `allow`: on a destination that records keys, an exact keyed retry counts with its application instead of as one more send beyond the expected count, and any other later send under a reused key (changed, concurrent, first used earlier, or with an unreadable key to the host) reads inconclusive, never a pass. Sends to a destination that records no keys are judged as without it. The clause needs at least one destination that declares `idempotency`. When an `effect.only` clause leaves `countBy` off and fails on sends beyond its expected count, its basis says how many of them are exact keyed replays of a judged send that `"countBy": "idempotency-key"` would count with their application; the hint changes no verdict.
- A selector then matches them with `fields`: 1 to 8 entries `{ "pointer", <one of equals, in, gt, gte, lt, lte> }`, all of which must hold, with an exact `name`. Example: `{ "kind": "effect.none", "select": { "source": "http-egress", "operation": "send", "name": "payments.example.test", "fields": [{ "pointer": "/amount", "gt": 50 }] } }`.
- Matching is three-valued. A send whose fields cannot be read (not JSON in UTF-8, compressed, over the cap, invalid, too deep, a repeated key, the field absent or unusable, or a value of another type: the string `"250"` never equals the number `250`) is unknown: a clause over it reads `missing`, never pass and never absent. A field absent from a body read in full is unknown too, unless its pin declares `absent: "fails"` (`{ "pointer": "/amount_cents", "equals": 4275, "absent": "fails" }`). Declare it only for a field the receiver neither defaults nor reads under another name, naming policy or letter case. With the declaration, a send whose body the recorder read in full without that field (for example `amount=43`) reads as not the pinned value toward a fail only: an `effect.exists` or `effect.count` (or a success claim) that would read `missing` fails, while `effect.none`, `effect.only` and every pass keep the unknown reading. A JSON send whose URL has a query, or whose body root is not an object, never decides that way. Such a fail is never credited as the baseline of a repair (`compareRuns` reads it as unverified). The declaration is part of the pin, so a forbidden pin's allowed-use twin repeats it. A string, JSON or form, matches a string operand only as exact text, and reads as different only where no common receiver reading makes the two one value. A respelled number (`"105.50"` against `"105.5"`, `"1e2"` against `"100"`, `"$105.50"` against `"$105.5"`), a case or NFKC variant (`"Refund"` against `"refund"`), words of one boolean or null (`"yes"` against `"true"`), and edge whitespace or a control character on either side are unknown, so pin the spelling the application sends. Words (`"cad"` against `"usd"`), other shapes (`"ORD-7"` against `"INV-8"`) and ids whose digits differ under every reading (`"T-7"` against `"T-8"`) read as different. An `in` member of another type than the value reads unknown (a receiver may read `"105.50"` as `105.5`, or `"true"` as `true`), except a string beside a number that no reading makes equal (a string with no digit, or a plain integer of another value). In `effect.only`, such a send that no `expect` matches reads `missing` when a `fields`-pinned `expect` could match it, even when an `allow` without that pin would fit it: it could be one more of the expected effect. A `fields` selector on a destination that does not declare every pointer it uses reads `unobservable`. A forbidden `fields` selector, like a `resource`, needs an allowed-use twin with the same `fields` (pairing). Sequences and the verdict service refuse `fields`.

**What happened upstream (forwarding).** By default the `egress-recorder` answers every request itself, so a recorded send is the app's attempt, and a check cannot tell a refund the provider applied from one it refused. A destination may opt in to forwarding to a provider stand-in you run on this machine (a payments test double, for example):

```json
"destinations": [{ "host": "payments.example.test", "paths": ["/v1/refunds"],
  "forward": { "upstream": "http://127.0.0.1:4010", "applied": [200, 201], "rejected": [402],
               "proofEnv": "SCOPEHAVEN_TARGET_PAY_UPSTREAM_PROOF", "timeoutMs": 5000, "maxReplyBytes": 65536 } }]
```

- Each send is recorded exactly as before (salted digest, declared fields, correlation token, idempotency key, witness), then forwarded as recorded: the method, the path and query the recorder named, the exact body bytes, with a fixed set of hop-by-hop headers dropped (`Connection` itself included) and `Host` set to the destination. A header the app names in `Connection` is still forwarded, so the upstream receives every header the record read. The upstream's reply goes back to the app. Redirects are never followed.
- `upstream` must be `http://127.0.0.1:<port>`. A host name (`localhost` too), another address, `https`, a path or a query is refused when the profile loads, and so is a port that is the recorder's own, another declared observer's or the target origin's. A forwarded host takes no static `replies`. Nothing leaves the machine through the recorder. Sequences cannot forward.
- **The proof.** An outcome is decided only when the destination declares `proofEnv`, a `SCOPEHAVEN_TARGET_` variable holding a secret of at least 32 characters (32 random bytes, hex-encoded, is a good choice) that you give the upstream and never the application. A `proofEnv` that is also an actor's or an observer's credential is refused, since the connector sends actor credentials to the application; start the application from an environment that lacks the variable. Each forwarded request then carries `X-Scopehaven-Forward-Nonce` (32 fresh hex digits), and the upstream must answer with `X-Scopehaven-Forward-Proof`: the lowercase hex HMAC-SHA256, under that secret, of `scopehaven-forward-proof/1`, the nonce, the method, the path and query as received, the hex SHA-256 of the body as received, its `Content-Type` (empty when absent) and the status it answers, joined by newlines (`forwardProof` in `integrations/observers/egress-forward.mjs` computes it). An application holding the upstream's port, or changing those fields or the status in between, cannot produce it. The proof does not cover `Host`, the other headers or the reply body. Without `proofEnv` the recorder still forwards, but every outcome reads unknown. Your upstream is also reachable on loopback directly: a send the application makes to it around the recorder is in no window, as with any route around the sink.
- Each send event records `upstream: { outcome, status, proven }`. With a valid proof, the outcome is `applied` for a status you list in `applied` (any of 200, 201, 203, 204 and 205, never `202 Accepted` or 206 to 208; the default is 200, 201 and 204) answered to a method that can change state (never GET, HEAD, OPTIONS or TRACE), `rejected` for a 4xx you list in `rejected` (the default lists none), and `unknown` for any other status. A missing or wrong proof, a timeout (the app gets 504), a refused connection, or a reply over `maxReplyBytes` or cut off (502) is always `unknown`. List a status only when your upstream sends it solely for requests it applied, or did not apply. The reply body is never read, so a listed 2xx whose body reports a failure still reads applied.
- A clause or claim selector may add `"upstream": "applied"`, with an exact `name`. For example, `{ "kind": "effect.none", "select": { "source": "http-egress", "operation": "send", "name": "payments.example.test", "upstream": "applied" } }` passes when every matching send was rejected, fails on an applied one, and reads `missing` (inconclusive) while any outcome is unknown. A recorder that does not forward that host cannot decide it, and `effect.only` selectors do not take it. Like `fields`, it is a pin for pairing (below): an absence clause that requires it needs an allowed-use control whose `effect.exists` with the same selector matched an applied send, since a setup in which every send reads a declared rejection would otherwise show "nothing applied" vacuously.
- A clause without `upstream` counts every committed send, applied or not, exactly as before. The run lists each forwarded host's upstream port, lists and whether it declares a proof in `observers[].forward`.
- **Outcome semantics (opt-in).** A clause may declare its type: `"semantics": "agent-write"` on `effect.exists` or on a claim rule, `"exactly-n"` on `effect.count`, and `"forbidden-attempt"` on `effect.none`, which is also what every clause without `semantics` means and never takes an `upstream` pin. An `agent-write` or `exactly-n` clause selects with `"upstream": "resolved"`, and that value is refused anywhere else. Under a recorder before `egress-recorder/7` it reads exactly as `"applied"`; from `/7`, the transport-record resolver (`r0`, below) also applies, on every run, with nothing to declare. `effect.only` opts in per selector with `"outcomeJudged": [selector, ...]`, but only on routes whose object you declare on the destination, in one of two forms: `"objectPaths": ["POST /tickets/{ticket}/close"]` (a route template with at least one `{name}` segment) or `"objectFields": { "POST /v1/refunds": ["/charge"] }` (one of the destination's `paths`, and the captured body pointers that identify its object). Each outcome-judged selector names the destination host and the exact route, and binds every identifier: a template's segments by literal path segments (`"resource": "POST /tickets/T-1/close"`, a path that is also in `paths`), an object route's fields by `equals` pins on a non-empty string or a number, and nothing else. A profile is refused at load when the route has no declaration, an identifier is left unbound, a field outside `objectFields` is pinned, the host does not forward, or a selector overlaps an absence of the same check: an `effect.none`, or a refusal claim without `"resolved"` (same source and operation, the same host, compared lowercase and including any other host forwarded to the same upstream, and resources equal or one a prefix of the other). So a collection path such as `/v1/refunds` alone, or a non-identifying field such as `/amount`, can never be outcome-judged. A forwarded send is judged by its outcome only when the recorder (`egress-recorder/6`) marked it exact and query-free: a sub-path filed under the route (`/tickets/T-1/close/undo`) or any query string keeps it an attempt. Then: applied, judged as before; proven not applied, set aside (never offending, never counted); anything else, inconclusive. A send whose identifying field cannot be read stays an attempt, so a forbidden refund on another charge still fails. The declaration is your trust, like any other: ScopeHaven refuses what it can detect (a template with no `{}` segment or no literal segment, unbound identifiers, pins outside `objectFields`), not a template that really names a collection. Object identity is the route and the body only, not tenant or credential headers: a refused ch_A refund sent under another `Stripe-Account`, API key or `X-Tenant` is set aside like one in the right tenant. Two more effects: a positive-match pairing twin pinned `"resolved"` does not pair with an absence pinned `"applied"` (that only ever reads missing), and an app-log admission reads every logged line of an outcome-judged route as an attempt (a proven-refused close the app logged as done can still fail by admission).
- **Resolving an unknown outcome.** For clauses that opt in, a send whose outcome is unknown (in doubt) is read through its resolvers, and only if every one that applies succeeded and they agree; otherwise it stays in doubt, which never passes. Which resolvers apply is fixed by ScopeHaven, not declared. The first (`r0` in a run's records) reads the recorder's own transport record (`egress-recorder/7`): a forward whose TCP connect to your upstream never completed (refused, unreachable, a connect timeout) sent no byte, so that attempt is refuted. A reset after the connect, even before the body, stays in doubt. It refutes one attempt, never the operation: a retry whose first attempt was forwarded and reset stays inconclusive, and in a keyed `effect.only` group a refuted attempt never stands for an applied retry. Each opted-in clause records its operation over the attempts it selects (`resolution`: confirmed, refuted, in doubt or none, with counts and, per attempt, what decided it and which resolvers applied), and a row with such a clause is backend observed only when none of those attempts is still in doubt. Clauses without the opt-in, and runs saved by an earlier recorder, read exactly as before. A later resolver (the request feed, `r1`, and read-back, `r2`, both below) answers after a check's window is sealed, so a run-end stage decides such a clause again once its records arrive: after the final mark and before settlement, so settlement, attribution, pairing, later outcomes and admissions read the resolved fate. The run seals those records in the row (`resolutions`) as the resolver's read, never its conclusion, the clause's record says `redecided`, and the validator binds the sealed reads and derives the result again before it decides; a missing or failed record leaves the attempt in doubt. A lifecycle change check takes no late record: its in-doubt attempts stay in doubt, because its post-change checks were gated on its status when it was sent.
- **Resolving an unknown outcome with the provider's request feed (`r1`, opt-in, `egress-recorder/8`).** A recorder may declare a feed of the provider's own signed record of the write requests it received, served on loopback by a provider stub or an operator-run adapter (contract `scopehaven-request-feed/1`, `src/request-feed-rules.mjs`):

  ```json
  "requestFeed": { "feedId": "billing-requests", "endpoint": { "port": 4021, "path": "/requests" }, "publicKey": "<base64 SPKI Ed25519>",
    "hosts": ["api.pay.example"], "maxSkewMs": 500, "watermark": true, "tenant": { "header": "stripe-account" },
    "routes": [{ "write": "POST /v1/refunds", "types": ["refund.created", "refund.updated"], "applied": ["pending", "succeeded"], "notApplied": ["failed"], "settleMs": 5000, "source": "provider docs: refunds settle within 5 s" }] }
  ```

  Each entry is `{ body, sig }`, the Ed25519 signature of `scopehaven-request-feed/1` and a newline before the body; the body is `{ feed, epoch, seq, id, at, type, host, route, key, object, state, tenant? }` (seq 1 is the genesis, `type: "epoch-start"`), and the signed head (`<path>/head?nonce=`) is `{ feed, epoch, lastSeq, nonce, watermark? }` under `scopehaven-request-feed/1 head`. `hosts` are forwarded destinations of this recorder that declare `idempotency`; each route's `write` is a method that can change state and one of their `paths`. The recorder reads the feed from its genesis at start (anything there is history) and once more at run end, to a fresh signed head, digesting each provider key with its own salt, so the key is compared only as the same salted digest and never stored. For an in-doubt send that connected, carries a keyed record, was marked exact and query-free and names a declared route, the request feed confirms it when the key's own entries (exact key, host, route and tenant) carry an applied word, stamped between its arrival and its connection end plus the route's `settleMs`, with nothing else wrong; it refutes it only when you declare `watermark: true`, the route declares `settleMs` with its `source`, there is no applied word, and the provider's signed watermark and ScopeHaven's own monotonic clock are both past the bound. A group of same-key retries counts as one application, as the key collapse counts it: this assumes the provider keeps keys for the whole run (on a host that declares `signing`, a retry past `dedupeSeconds` leaves the group in doubt). Declare in `notApplied` only final states: a word that can still change is read as the request's fate. Every other case is in doubt: an unclear feed, a key used before the run or on another host, an entry for a case or quote variant of the key, a second object, an unlisted type or word, a tenant that does not match, another send under the key anywhere in the run, a send to the host whose key could not be read, fewer entries for the key than replies the provider gave in the group. A feed host is declared on one recorder only: a profile where another egress recorder forwards it is refused. Leaving a guarantee out (`watermark`, `settleMs`) only ever means fewer decisions. The run keeps, per such send, the counts, flags and times its result is derived from (`resolutions`), never a key, object id or tenant, and the run record names the feed (`observers[].requestFeed`, with its own collector, `request-feed/1`). What a confirmation and a refutation rest on is in docs/KNOWN-LIMITS.md.
- **Resolving an unknown outcome by reading the system of record back (`r2`, opt-in, `egress-recorder/9`).** A forwarded destination under proof version 2 (below) may declare `readBack`: ScopeHaven's own reads of the collection a write creates items in, sent by the recorder straight to the destination's forward upstream on loopback under a read credential the application never holds, each reply proven like a forwarded one (`src/read-back-rules.mjs`, `integrations/observers/read-back.mjs`):

  ```json
  "credentialHeader": "authorization", "backend": "crm",
  "readBack": { "credential": { "env": "SCOPEHAVEN_TARGET_CRM_READ", "header": "authorization", "scheme": "Bearer" }, "timeoutMs": 2000, "scopeHeaders": [],
    "identities": { "app": { "env": "SCOPEHAVEN_TARGET_CRM_APP", "scheme": "Bearer" }, "jobs": { "env": "SCOPEHAVEN_TARGET_CRM_JOBS", "scheme": "Bearer" } },
    "routes": [{ "write": "POST /tickets/{ticket}/notes", "read": "GET /tickets/{ticket}/notes", "items": "/notes", "id": "/id", "author": { "pointer": "/author", "serverAssigned": true },
      "settleMs": 500, "complete": { "pointer": "/complete", "equals": true }, "match": { "fields": { "/text": "/body" } },
      "lifecycle": { "pointer": "/status", "applied": ["posted"], "notApplied": ["declined"], "nonFinal": ["pending"] },
      "guarantees": { "consistency": "strong", "completeness": "exhaustive-pagination", "removal": "never", "settleMs": 500, "source": "CRM API reference, notes" },
      "view": { "covers": ["app", "jobs"], "items": "all-items" }, "deferredFields": [], "control": { "bind": { "ticket": "T-CTRL" } }, "touches": ["GET /tickets/{ticket}/notes"] }] }
  ```

  `credentialHeader` names the header that carries the application's write credential: the recorder keeps a salted digest of its one value per send, never the value, and an identity's `env` holds the value (with `scheme` before it) whose writes that identity authors, so the read can attribute items; static keys are expected (a rotating token maps to no identity and decides nothing). `backend` labels the forwarded destinations that write to one system of record; a forwarded destination without a label is in every backend. A write binds a route when its method and forwarded path fit `write` (`{name}` takes one segment of letters, digits, `.`, `_`, `~` or `-`); the read is filled from those segments only. Sends of one route, object, matched body fields (or key, with `"match": { "key": "/key", "serverAssigned": true }`, when the server records the request's idempotency key on the item), credential and scope-header values form a group: its first member waits for a pre-image read (at most min(1000 ms, `timeoutMs`); past that the write goes on and the group decides nothing), and once every member's forward settled with one in doubt, two reads are taken at the last connection end plus `settleMs` and `settleMs` later, and one more at run end. Read-back then confirms in-doubt members only from new items authored by the group's identity, matching its fields and in an applied state, with no other write under that credential on the backend in the window; it refutes or caps only on a POST route whose host declares `forward.ids.minted` (refutation reads a missing new item, so the read collection must receive exactly one new item per application of the write: an upserting POST, or one that also adds a second item matching the binding, is a declaration error; a PUT, PATCH or DELETE route, or a host without minted ids, only confirms), and only when the route documents strong consistency, one-page completeness with its `complete` signal on every read, removal `never` or `tombstoned` and a `source` other than `observed`, the identity is in a `view` of all items, every proven member's minted item and an item of the identity (there or on the `control` object) are visible, no pre-image item went missing, no member sets a deferred field, a query string or an undeclared tenant header, and no other write that may touch the read reaches the backend in the window (`touches` lists the reads a route's write can change; a route without it, or a write to another host of the backend, touches everything). A count the reads pin exactly is assigned to the group's members only when they are one identity (the same path, body and captured fields), since no clause can then tell them apart, and only when no two members it leaves applied share the key collapse's identity (one key, one body): a backend that applied one key twice is left undecided, and keyed clauses keep the collapse's one-application-per-key reading. The control object is read when the recorder starts (on a destination that declares no scope headers) and again at run end. The run-end read is the bound's alarm: a pre-image or minted item gone, or a new item appearing after S2 that no later send to the object explains, leaves the group in doubt. Every guarantee left out, any read failure (a non-200 or unproven reply, non-JSON, over 1000 items, ids missing, the complete signal false, a timeout) and a pre-image taken within the route's `settleMs` of the recorder's start mean fewer decisions, never more: start with a check that writes nothing, or give the run a moment, if the first write must decide. The read credential may not be any credential the profile names or any proof or signing secret (names at load, values at run start), and a read-back host is declared on one recorder only. Label every forwarded destination with `backend`: an unlabeled one is in every backend, and its writes (which declare no settle) hold every later group of the run in doubt. The reads are themselves requests to the system of record, so an audit-log or database observer of that backend can record them (under the read credential's principal) in a check's window; keep its clauses from selecting them. The run keeps, per such send, its group's counts, flags and times (`resolutions`), never an id, path, value or credential, and the run record names the declaration (`observers[].readBack`). What a confirmation and a refutation rest on is in docs/KNOWN-LIMITS.md.
- **Returned ids (proof version 2).** A destination may add `"proofVersion": 2` (it needs `proofEnv`) and `"ids": { "minted": ["/id"], "references": ["/charge"] }` (1 to 8 JSON pointers into the reply body in all, under the same pointer deny-list as declared body fields). With version 2 the upstream signs `scopehaven-forward-proof/2`: the version 1 fields followed by the hex SHA-256 of the reply body it sends (`forwardProofV2` in `integrations/observers/egress-forward.mjs`). Of each reply proven that way, the string values of 8 to 200 characters at those pointers are kept only as salted digests: `upstream.minted` for ids the upstream creates for this request, `upstream.references` for ids of other objects it names, and `upstream.echoed` for a value at a minted pointer that the request itself carried (literally, re-cased, inside a longer value, or JSON, form, percent or base64 encoded): an echo is never minted and makes that id tie nothing anywhere. Point `minted` only at a value your upstream mints once per created object and never copies from the request; a reference is as good as your upstream's own check that the object exists. Numbers, shorter strings and secret-shaped values are not ids. Version 1 destinations are unchanged. The ids are used only by background attribution (below).
- A forwarded send's body is bounded by the smaller of `maxBodyBytes` and 1 MiB. Its record stays in flight until the upstream answers or times out, so a collect before then leaves the window partial. The outcome is your upstream's answer, not the real provider's.

**If the reply claims it, the records must show it (claim rules).** A check may declare `claims` (1 to 5; the target must declare `observers`). The reply never decides the verdict: its reading only chooses which records requirement applies, and the observers decide it like a declared clause (custody, settlement and pairing included):

```json
"claims": [{
  "trigger": { "text": { "pointer": "/reply", "success": ["refund has been issued"], "refusal": ["cannot issue a refund"] } },
  "select": { "source": "http-egress", "operation": "send", "name": "payments.example.test" } }]
```

- A `field` trigger (`{ "pointer", "success": [values], "refusal": [values] }`) compares the value at the pointer type-strictly. A `text` trigger (`{ "pointer", "success": [sentences], "refusal": [sentences], "courtesy": [templates] }`, `courtesy` optional) compares the whole string at the pointer with the declared sentences (3 to 120 characters each, never a regular expression).
- A success reading requires `effect.exists` over `select`; a refusal reading requires `effect.none`. So a reply that claims a refund with no refund recorded fails, a reply that refuses while a refund was sent fails, and each passes only when the records agree.
- **An allowed-use control with effects proves one.** A `"severity": "control"` check that declares `effects` must include a positive one, `effect.exists` or an `effect.count` expecting at least 1, or the profile is refused when it loads. `effect.none`, `effect.count` 0 and `effect.only` (whose `expect` is a ceiling) all pass when nothing happened, so on their own they would let an app that answers and does nothing establish the actor for its boundary checks. Add them beside the positive clause. A saved run whose control breaks this rule is refused (`control-no-positive-effect`). A control with no effect clauses still rests on its response.
- **On an allowed-use control, declare success only.** A control proves its use works, so a claim rule on a `"severity": "control"` check that lists any `refusal` sentence or value is refused when the profile loads. An honest refusal would otherwise pass the control (no effect, as claimed) and let an app that refuses everything establish the actor for its boundary checks. Undeclared, a refusal reply reads ambiguous (`text`), unreadable (`field`, a value not declared) or untriggered (`field`, pointer absent), each inconclusive, so that claim never passes the control. A `field` claim declared `"untriggered": "no-requirement"` adds nothing when the pointer is absent; the control then rests on its own assertions, as a control without claims does. A saved run whose control declares a refusal side is refused (`control-refusal-claim`). Boundary checks keep both sides.
- A reply that is not complete JSON or lacks the pointer reads inconclusive. **Free-text claims decide only on exact declared sentences**, because word lists, a word-order table and voice rules each let a fluent retraction such as `Your refund has been issued and cancelled.` decide. Free text is not parsed. A `text` trigger decides only when the whole reply is exactly one declared sentence, optionally followed by exactly one of the trigger's declared `courtesy` templates as a separate sentence. The reply is compared after NFKC, lowercasing, collapsing runs of whitespace to one space and dropping one trailing `.` or `!`; the claim and the courtesy template are separated by `. ` or `! `. So with the sentence `refund has been issued` and the template `thank you`, `Refund has been issued.` and `Refund has been issued. Thank you!` decide, and `Your refund has been issued.`, `Thanks! Refund has been issued.`, `Refund has been issued, thank you.`, `Refund has been issued!!` and `Refund has been issued. Thank you. Have a nice day.` read inconclusive. A reply holding any control, format or bidirectional character other than tab, line feed and carriage return reads inconclusive outright. A declared sentence is one plain sentence: letters, digits, spaces, commas, `$`, `€`, `£` and `%`, with a full stop only inside a number (`$30.00`); a phrase holding a quote mark, an apostrophe, a question mark, `!`, markdown or any other symbol is refused when the profile loads, so no reply holding one can decide. A courtesy template (up to 16 per trigger) is lowercase letters a to z, digits and spaces with no negation, and never contains or sits inside a declared sentence; there are no built-in templates. The same sentence cannot be declared on both sides. A text trigger never reads untriggered (a reply with no declared sentence is ambiguous), so `"untriggered": "no-requirement"` is refused on a text trigger; on a `field` trigger, a reply without the pointer reads inconclusive unless the claim declares it, which adds no row.
- Rows show `Observed claim N (reading)`. Only the reading and the index of the matching phrase or value are kept, never the reply text. The exported suite binds claims by digest.
- **Recall limit (by design).** Recall on free text is intentionally minimal. An honest reply in any other words reads inconclusive: a greeting before the claim, a name, an apostrophe (`We've issued the refund.`), an amount the profile did not declare, a second sentence the trigger did not declare as courtesy, a question, a link or an emoji. A claim stated in undeclared words is not seen. In exchange, wording around a declared sentence (a retraction, condition, hedge, quotation or markup) can never make it decide. A declared sentence that itself states a plan or a condition (`refund will be issued`) decides as declared, and a declared courtesy template is trusted as written, so declare only neutral closing lines. Such a reading still only selects the records requirement; the records decide. Use structured fields where possible: a `field` trigger is the recommended form.
- The declared claim rules, phrases and values included, are stored in each check's sealed trace and exported with the run, like the rest of the profile.

**Selector values must match what the observer reports.** `actor` must equal one of that observer's `principals` values exactly (for `audit-file`, a `logActors` key), not the profile's actor alias. `resource` must be the exact string the observer reports. Scopehaven checks neither, and a value that matches nothing makes `effect.none` pass. Prove each forbidden selector once: run it as `effect.exists`, or against a build where the effect does happen, and confirm it matches.

Absence is claimed only for an exact `name` from an authoritative observer's declared vocabulary, and only when that observer covered the whole window. Anything less reads `missing`, `unobservable` or `observer-failure`, which is inconclusive and never a pass.

**Settle time.** Each observer needs a `settleMs` from 250 to 30000; without it, an observer cannot show absence. After each check that declares effects, Scopehaven waits the largest declared `settleMs` before closing the window. Set it above the slowest write the app completes after replying, measured on the app; the examples' 500 ms suits only their synchronous example app. An effect committed later than that lands outside its check's window; settlement (below) withholds the passes it could change, and a late effect can still fail a later check's `effect.none`, so re-run a failing row on its own before acting on it. The waits count against the run budget (60 seconds, plus the extra time of each declared `timeoutMs`), which the identity probes also use, so a long settle on many effect checks can leave the run inconclusive.

**Per observer:**

- `sqlite-audit`: `path` to the database file, `audit` naming the table and its `idColumn`, `actorColumn`, `actionColumn`, optional `resourceColumn`, and `actions` mapping each logged action to `insert`, `update` or `delete`. `principals` lists the actor values that are your test users; any other value is unlisted and cannot support an actor-scoped absence. Absence means only that the app's audit recorded no such action by that principal under that declared name. It holds only when every write path, assistant tools included, writes an audit row with the requesting user and a declared action name. Scopehaven never opens the live database file: it reads a private copy taken when nothing is committing (see [integrations/observers/README.md](../integrations/observers/README.md)).
- `http-audit`: the endpoint's `origin` and `path`, a `credentialEnv` with the `SCOPEHAVEN_TARGET_` prefix for a read-only audit user, `itemsPointer` to the entry list, `fields` for `id`, `actor`, `action` and optional `resource`, `actions`, `principals`, and the endpoint's page size as `pageLimit`. The audit credential must see every test principal's entries: an endpoint scoped to one tenant passes a cross-tenant write it does not list. Prove it with an observed allowed-use twin for each actor, as the example does. Absence also needs new entries to arrive with gap-free ids and no rows to vanish; a filtered endpoint is caught only in windows where an id it hides is allocated. A response as long as `pageLimit` may be missing the newest entries, so that window reads `observer-failure`, which is inconclusive. `check-config` marks the target not ready when a declared audit credential is missing or has an unusable bearer format or cookie configuration; it reports a reason and credential references without connecting or printing credential values.
- `sqlite-snapshot`: `path` and `tables`, each with its `table` and unique `key` column. It compares the tables before and after each check, so it catches a committed insert, update or delete, but a row inserted and removed between the two snapshots is invisible. `effect.none` therefore reads inconclusive even when nothing happened, so its rows keep `assess` and the gate at exit 1 on a correct build and a repair reads unverified: use it for detection, not as a CI gate. `effect.count` is unavailable. Its events carry no actor and the new row's key is not known in advance, so `effect.exists` is table-wide: any insert satisfies it, including one on another company's order. Put such a check right after one that writes nothing; that rules out only the check just before it, and any earlier write that commits after its own settle can still land in this window and satisfy it. In the `sqlite-snapshot` example, the one row a repair restores (the assistant disclosure check) rests on its response alone, and the `effect.none` prohibitions read inconclusive on the repaired build, so the comparison is incomplete and carries no repair label ("No verified repair"). Absence on updates of existing rows can be exact for a table with a source-checked `changeColumn` (see the comment above `createSqliteSnapshotObserver` in `integrations/observers/sqlite.mjs`). A snapshot of the effect tables is also the cross-check for an audit observer: a snapshot failure where the audit run passed means the app's audit is incomplete.
- `pg-snapshot`: `host` (`127.0.0.1` only), `port`, `database`, a `credentialEnv` whose `SCOPEHAVEN_TARGET_` variable holds `user:password` for a role with `SELECT` only on each declared table, and `tables`, each with its `table` and `key`. Each mark reads every row's key, its row version (`xmin`) and a hash computed in the database, in one read-only snapshot, so no other column value leaves the database. An existing row whose version did not change had no committed update. Inserts and deletes are net-only: a row added and removed within a window is not seen. It logs in with SCRAM-SHA-256 only and needs PostgreSQL 13 or later.
- `mysql-snapshot`: the same connection fields, and InnoDB `tables` with `table` and `key`. It is net-only by default: a write undone within a window is not seen. Exact absence for a named row needs a `changeColumn` the server maintains (`TIMESTAMP DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP`), a source-check file recording that no writer sets it, and `maxCommitLagMs`. Add `"tableIds": true` to catch a swapped table; the reader then needs the `PROCESS` privilege. The server is not authenticated: a process that took the loopback port first could answer the marks. For that reason, a reader that needs full `caching_sha2_password` authentication (MySQL 8's default, when the server has not cached the login) sends its password only to a key you pin. Put the server's RSA public key (the PEM of `public_key.pem` in its data directory) in `<credentialEnv>_RSA_PUBLIC_KEY`, for example `SCOPEHAVEN_TARGET_APP_DB_READER_RSA_PUBLIC_KEY`. Without a pinned key, such a login fails the mark with `authentication-refused`; the fast path and `mysql_native_password` need no key. A `credentialEnv` longer than 95 characters after `SCOPEHAVEN_TARGET_` leaves no room for the suffix, so it cannot carry a pin.
- `egress-recorder`: a `port`, the `destinations` checks name (`host`, optional `paths`), and for authoritative absence a `routing` (`proxy`, where the app uses the sink as its HTTP proxy, or `base-url`, with one declared path prefix per destination in `routes`, the witness host included) and a `witness`: `{ "actorId", "method": "GET", "path", "host" }`, an app route that makes the app send one request to the witness host, which must not be a destination. HTTPS through the proxy arrives as `CONNECT`: the host is recorded, the payload is not, and the window is partial. Optional static `replies` give an app that reads the answer a local stand-in for a provider's test mode; they change only what the app sees, never what is recorded. A destination can add `"correlation": { "header": ... }` to record the run's correlation token (see below), and `"forward"` to send each recorded request on to a loopback upstream and record its outcome (see **What happened upstream** above).
- `smtp-sink`: a `port`, the recipient `domains` (with any `addresses` to name), and for authoritative absence `"routing": "smtp-host"` and a `witness`: an app route that makes the app mail `<nonce>@<witness domain>`. It offers no STARTTLS, so a client that requires TLS cannot send to it at all. The full configuration of all four, and every rule that makes their windows partial, is in [integrations/observers/README.md](../integrations/observers/README.md).
- `provider-feed`: for mail a vendor SDK sends straight to its provider, which no sink sees. It reads the provider's own record of what it accepted, never the app's, and it needs a provider stub or an operator-run adapter that implements the signed `scopehaven-provider-feed/1` contract: real provider APIs (Postmark, SendGrid, Mailgun, Stripe) are not read directly. Declare the `feedId`, the `feed` (an `endpoint` on `127.0.0.1` that also serves a signed head, or an export `file`, which is presence-only in v1: it can show a send, never absence), the stub's Ed25519 `publicKey` (the stub keeps the private key, and the app must never hold it), the recipient `domains`, and for authoritative absence on an endpoint `"routing": "provider"` and a `witness`: an app route that makes the app send one email through the provider to `<nonce>@<witness domain>`. Declare where the public key came from with `keySource` (`provider`, `adapter` with `adapterReads`, or `stub`): an undeclared source, or an adapter that reads the application's own store, is a key the app could hold, so the feed can fail a check but never pass one. Events are `send` effects named by recipient domain (source `provider-feed`, custody `independent` only under a declared provider, provider-API adapter or stub key). To tell one email from another to the same recipient (a case's own email beside a background job's), declare `templates` (operator label to provider template id) and pin `"fields": [{ "pointer": "/template", "equals": "<label>" }]`: only an id the signed entry names exactly reads as its label, anything else reads unknown (missing, never pass), and runs keep the labels only. A send after the witness request (a background job's email, say) reads as an entry for its recipient instead of leaving the whole window partial, once a later window of the feed or its run-end drain follows it. To record what the provider did with each send later (a bounce, a drop, a reversal), declare `"outcomes": { "waitMs": 3000 }` on an endpoint feed with a witness and have the stub write signed `outcome` entries (`succeeded`, `deferred`, `failed`, `reversed`, `contested` or `complained`, by the provider's message id): the run's settlement record then carries the provider's later words per send, read during a later wait of up to `waitMs` after the final mark. Under `provider-feed/6` they then lower a positive pass whose matched send the provider later failed or reversed: a boundary check reads fail where the rest decides absence, and an allowed-use control reads inconclusive, tagged `later`. Absence clauses and `effect.only` still count every accepted attempt. Pin `source: "provider-feed"` on the clauses that should be judged by the provider's later word. Details in [integrations/observers/README.md](../integrations/observers/README.md).
- `audit-file` (not used in onboarding; see above): the log `path`, the `origin` as logged, `rules` for the routes whose requests are effects (with `refusedStatuses` for the refusal codes), `ignore` entries for every other logged route, `logActors`, and a `witness`: a GET the app logs, which Scopehaven sends at the end of each window to prove the log caught up. Details and limits are in [integrations/observers/README.md](../integrations/observers/README.md). It records how each request was answered, so it cannot see a write committed behind a refusal, or one an assistant made inside the server. Its events carry the requested path, so pinning a `resource` adds nothing. A log line with no status, as at Open WebUI's default audit level, gives partial coverage, never absence; do not raise an app's audit level to log full requests and responses for this, since that can write session tokens to the log.

**The application's own action log (`appLogs`, app-reported).** A target may also declare the log its application keeps of the actions it takes ("email sent", "ticket updated"), under its own key `appLogs`, never in `observers`. It needs no change to the application: map the log's existing fields (`action`, `outcome`, `actor`, and `target` for mail), one rule per action, and `logActors` (each declared principal and the one log value that names it). Its lines are **app-reported**: the application writes them, so they are never custody evidence, they never enter a custody decision, and an application that writes a false log defeats them. `"use"` is required. With `"record"` they decide nothing: each check's lines are sealed beside its observer windows as `data.appLogWindows` and every verdict is exactly as without the declaration. With `"use": "admission"` the log is also read against the application, and only against it: a clause that did not fail reads **fail** when the log records, as committed, an action of the check's own actor in the check's own window that the clause forbids (finding `app-log-unobserved-admission`; the clause names the log as its source and its custody is the application's). An admission never makes, extends or rescues a pass, and a custody fail stays a custody fail. Entries of another actor, of a declared background source (pin the background source's `actor`, or its actions are never admissions), that fit a declared effect or claim selector of an earlier check by the same actor, or logged after the check's cut are never admissions. An earlier check that declares no effect and no claim offers no selector, so a late line of its own that lands in this check's window is not set aside; give such a check an effect clause, or keep its actions out of later checks' windows. A selector pinned to an observer source is read on the log only where every rule of that exact name lists the source in `observedAs`; a field pin reads a rule's declared constants (`"fields": { "/template": { "const": "ticket_update" } }`) or a value read from the line through a closed word map (`"fields": { "/template": { "from": "/params/template", "values": { "ticket_update": ["ticket_update"] } } }`; any word the map does not list reads unknown and decides nothing; the captured value is a string, so a clause that pins that field with a non-string value is refused at load). For an `effect.only` clause with selectors the log cannot read, declare on a rule the sources its action is never the effect of (`"distinctFrom": ["provider-feed"]`): only such entries are judged against the rest of the clause. A background source's exact egress path is kept apart on the log when every rule of that host is an egress rule with an exact resource. For a countBy clause, declare `"lines": "per-application"` on the rules whose action the application logs once per application (and `fields.key` if it logs the idempotency key it sent). For a background job that does what the checks forbid on the same path, pin the background source to the job's own principal, map it in `logActors`, declare `fields.trace` (with the target's `correlation` header), and write `"allowBackground": ["<source id>"]` on the `effect.only` clause instead of a shape-only allow: custody reads it the same way, and admissions read the job's lines apart from the check's. A baseline fail that rests only on admissions never credits a repair (`baseline-fail-app-admitted`). The log is read without a request or a wait: its marks are small local reads, and its lines are read after every observer has been collected (see `integrations/observers/README.md`).

**Settlement across the run.** When any check declares effects, Scopehaven marks every observer once before the first check and once after the last check plus the largest declared `settleMs` (the final mark), and seals the windows between: one before the first effect check, a gap after each one, and the tail up to the final mark. Egress recorders, SMTP sinks and audit-log files start each gap where the previous check's window stopped attributing records (at its witness request), so a record that arrives between one window's collect and the next start mark is in a gap, never in no window. The run's `settlement` record keeps those windows, and the validator recomputes everything below from them:

- `effect-outside-window`: a committed effect matching a passed `effect.none` or `effect.count` clause is recorded after that clause's window closed (in a gap, a later check's window or the tail). It may be this check's late effect, so the pass reads inconclusive. An `effect.only` pass is an absence claim too ("nothing else happened"): any later committed effect of an operation it judged, from an observer in its scope, withholds it, whether it is expected, allowed or outside the declared set. Put an `effect.only` boundary check after the checks whose effects its observers would see, or accept it as inconclusive. A target can instead opt in to judged late effects, `"settlement": { "mode": "run", "outsideWindow": "judge" }` (or `"per-check"`): each such later effect is counted as the check's own, added to its own window of the same observer, and the clause is judged again. The pass stands, carrying the note `effect-outside-window-judged`, only if it still passes, so a later effect that is allowed, or expected and still within its count, no longer withholds it; an unexpected or beyond-count one, one with unreadable fields, one from an observer that is not authoritative, and a combined window over the event cap still do. It judges an `effect.only` clause with `countBy` the same way, worst case: its own window's sends keep their keyed collapse and each later effect is its own application, so a late exact keyed replay of its own send counts again. It changes nothing for any other kind, never fails a pass, and is refused (`settlement-judge-unused`) when no applicable check has an `effect.only` clause. Runs with and without it never compare.
- `effect-ambiguous-attribution`: every committed effect that decided an `effect.exists` pass, or any one an `effect.count` pass counted, also fits a selector of an earlier check. It may be that check's late effect, so the pass reads inconclusive.
- `settlement-unobserved`: an observer that decided an `effect.none`, `effect.count` or `effect.only` pass could not decide absence in a later window: the window failed, was partial (for example a sink request still in flight at the final mark), or, for a net-only snapshot, was not exact for the selector. A late effect could have been missed, so the pass reads inconclusive.

Only a pass is withheld. A boundary check withholds it under every finding. An allowed-use control keeps its verdict and carries the finding as a `settlement` tag, as it does for custody, except a positive pass (`effect.exists`, or `effect.count` of at least 1) whose deciding effect carries another check's correlation token (`effect-correlated-elsewhere`): a control establishes its actor only on its own effect, so that pass is withheld, as background attribution withholds it. Selector-only ambiguity (`effect-ambiguous-attribution`) stays a tag on a control. It is raised whenever the control's effect also fits an earlier check's selector, including a prohibition's actor-wide clause, so it does not by itself mean the pass rests on another check's effect; that risk exists only where an earlier check could produce the effect the control pins. Pin each control's positive clause to its own `resource`, run controls before broad prohibitions where the order allows, or declare `correlation` for egress. The onboarding examples show it: their own-refund controls are pinned to their own order and still carry the tag, from the earlier prohibitions' actor-wide clause. A fail stays a fail, and no settlement finding fails a pass, the correlated ones below included. Effects committed after the final mark are outside every window and every claim: no result says an effect never happened later. Keep checks' effects apart by pinning a `resource` or `actor` on each clause, and put an allowed twin whose effect matches a prohibition's selector before the prohibition, or pin both: an unpinned twin after it withholds the prohibition's pass. A run saved before settlement existed (HTTP evaluator `cc13de98` and earlier) that has effect windows is refused with `effect-pre-settlement`; take a new baseline.

**Correlation and per-check settlement (opt-in).** By default one run cannot keep two independent checks' effects apart: a later check's own send withholds an earlier check's absence pass, because it could be that check's late effect. Correlation does not change that: the token an application forwards is its own account, so it can only add withholding. A target can declare a correlation header and, on top of it, per-check settlement:

```json
"correlation": { "header": "traceparent" },
"settlement": { "mode": "per-check" },
"observers": [{ "id": "sink", "type": "egress-recorder", "destinations": [{ "host": "hooks.chat.example", "correlation": { "header": "traceparent" } }], ... }]
```

- `correlation.header` is `traceparent` (W3C Trace Context; an app with OpenTelemetry propagation forwards the trace id on its outbound calls) or an `x-` header of your own (`x-request-id`; the app forwards the value unchanged, and a value with any uppercase letter records no token). Every sent check request carries a fresh per-request token; identity probes and witness requests carry none. At least one egress-recorder destination must declare the same header, and only those destinations record tokens. SMTP sinks, audit logs, database snapshots and traces record none. The recorder checks the format only: it records any well-formed value the application sends in that header, whether or not the connector sent it, and nothing is re-cased or trimmed. The value is stored in the event's `correlation.settlementToken`, which no selector or pairing pin reads, so a `traceId` selector never selects it; a correlated target refuses a `traceId` selector an egress recorder could see, in an effect clause or a claim rule (`correlation-token-not-selectable`).
- The token is something the application forwards, so it is the application's own account of which request caused a send. Scopehaven never treats it as evidence on its own: it never releases a pass that settlement or pairing withholds, never passes or fails a clause, and never fails a pass. It can only name a sharper reason for a withheld pass, or withhold one more:
  - `effect-correlated-late`: a send carrying a check's own token arrives after its window (in a later window, a gap, the tail or its own barrier) and the absence clause judged with it would fail. The pass reads inconclusive; an allowed-use control carries it as a tag. The rules above already withhold that pass (`effect-outside-window`); the token only names whose late send it may be.
  - `effect-correlated-late-unsettled`: such a send could change the clause but would not decide it (for example it is inside an `effect.only` clause's expected set). The pass reads inconclusive.
  - `effect-correlated-elsewhere`: every send an `effect.exists` pass rests on, or any send an `effect.count` pass counted, carries another check's token. The pass reads inconclusive. On such a positive clause this reason is read first, before a late own-token send or a selector finding, so a reason that only tags an allowed-use control never hides it.
- `"settlement": { "mode": "per-check" }` (needs `correlation`) adds a drain barrier after each check with effects or claim rules: Scopehaven waits the largest declared `settleMs`, marks every observer and seals that barrier window before any later request, so the run takes one more settle per such check (at most 600000 ms in all). A check's late effects then land in its own barrier instead of the next check's window, where they would otherwise decide that check. Every rule above reads the barrier windows too: a send in a barrier withholds the earlier check's absence pass like any later send, and a failed or partial barrier withholds it (`settlement-unobserved`). Per-check mode releases nothing: a later send that fits an earlier check's absence clause withholds it whatever token it carries and whatever the later check's own clauses say, and a send that fits an earlier check's selector stays ambiguous for the later check whatever its token.
- What this means for layout: several effect checks against one destination in one run still withhold earlier absence passes, with or without correlation. Pin a `resource` or `actor` on each clause to keep checks apart, or use one run per case. Without correlation every rule above is exactly as before, and runs with and without it, or in the two modes, never compare (both are part of the profile digest).

**Late effects: a declared effect horizon and run budget (opt-in).** `settleMs` is at most 30000 ms, so a send an application makes 35 to 45 s after its reply (a retry backoff, a queue that flushes later) misses its own check's window and lands in a later one, where it fails a check it did not cause or decides it. A target can declare how late its effects may land, and how long the whole run may take:

```json
"timing": { "effectHorizonMs": 45000, "runBudgetMs": 900000 }
```

- `effectHorizonMs` (250 to 120000, and at least the largest declared `settleMs`; at least one observer must declare one) is held after each response instead of the settle, so a check's effects within it land in its own window. Each check with effects or claim rules also starts only once the horizon has passed since the end of every earlier request of the run (checks, identity probes and witnesses), so their effects within it land in their own window or a gap, never in that check's window.
- `runBudgetMs` (60000 to 7200000) replaces the computed run budget and bounds every request, probe, witness and wait the run starts. It must hold a linear plan, or the profile is refused at load with both numbers (`timing-budget-below-plan`): 60000 ms of slack, every applicable check's request budget (its `timeoutMs`, or 3000), every identity probe at the longest identity or surface control budget, and per check with effects or claim rules two horizons (its lead-in and its own window), its witnesses' close (each witness request plus that sink's `witnessWaitMs` and ten times its `quietMs`) and, in per-check mode, its barrier, then the final settle. Without a declaration nothing changes.
- Scopehaven keeps the final settle and the identity probes still to send in reserve, sends the end-of-run identity probes before the final settle, and sends a check only when its request, lead-in, horizon, witness close and barrier still fit. A check that does not fit is not sent and reads inconclusive (`run-budget-exhausted`), and so does every later check; earlier rows keep their verdicts and their identity proof. Which check was cut is Scopehaven's own reading of its clock: no other evidence recomputes it, so a saved run cannot prove it, and a cut row only ever reads inconclusive.
- If a wait is still cut short (observer marks or collections took longer than the slack), every authoritative window it held open reads partial (`effect-horizon-truncated`): an absence or count clause it decided reads inconclusive, and so does every earlier boundary check's absence clause from the same observer (an allowed-use control keeps its verdict with a `settlement-unobserved` tag); a send it did record still decides (a forbidden send fails, an expected send passes). Every later check is cut. The run's `timing` record states how long each window, barrier and the tail were held, and the validator checks the windows against it.
- An application can always delay an effect past any horizon: an effect later than the horizon after its request is outside that check's claim and is settled by the rules above (it withholds an earlier absence pass it fits, and can decide a later check). Declare a horizon above the longest tail you expect. The declaration is part of the profile digest and the exported suite, so runs with and without it, or with another horizon or budget, never compare; `suiteHash` and `policyHash` do not move. Observer marks and collections already in progress can finish after the budget, within each observer's own limits; the dashboard waits for the largest budget plus 60 s.
- `"lateFails": "withhold"` (optional) adds the late rules (`src/http-attribution.mjs`), with or without background sources: a fail a late effect could explain is not charged to the check and reads inconclusive (`late-unattributed`). That is an `effect.none` or `effect.only` fail resting only on effects that fit an earlier check's selector (they could be its late effects), an `effect.exists` fail whose own effect was recorded after its window, and an `effect.count` fail those effects could account for. They run after settlement and only where no background rule applied, so a background effect keeps its own reason; an allowed-use control keeps such a fail with the tag. They never touch a pass. The cost is detection: a forbidden effect that also fits an earlier check's selector reads inconclusive, not fail, so pin a `resource` or `actor` on each clause to keep checks apart. The option is part of the declaration, the record and the exported suite.

**Background sources (opt-in).** A sync worker, queue or cron job commits effects on its own schedule, and one that lands in a check's window would otherwise decide that check: a worker's send can fail an innocent `effect.none`, or satisfy an `effect.exists` the check itself never caused. A target can declare those sources:

```json
"attribution": { "background": [ { "id": "crm-sync", "select": { "operation": "send", "name": "crm.example" } },
                                 { "id": "order-sync", "select": { "actor": "svc-sync", "operation": "update", "name": "orders" } } ] }
```

- Each source (1 to 16, unique `id`) names its effects by `actor`, `operation` and `name` only (at least one; a `name` is exact or `{ "prefix" }`). `source`, `resource`, `outcome`, `traceId` and `fields` are refused: one effect recorded by two observers (an audit row and a snapshot) differs in its source and often its resource, and every copy must classify the same. One exception: an egress source (`"operation": "send"` and an exact host `name`) may pin `resource` to one resource the egress recorder names its sends by, `"<METHOD> <declared path>"` or `"<METHOD> *"` for a path outside the declared ones, and only one that the host's egress-recorder destinations produce (`attribution-resource-unproducible` otherwise). Then only sends to that path are background; a send with no resource still is, and a send to another path stays decisive for clauses about the host. A copy of such a send another observer records under another resource is not background. An `actor` pin also takes an effect whose actor is unknown or not a declared principal, so list each worker principal in the audit observer's principals, and declare one source per vocabulary its effects appear in (a table name and an audit action are different names).
- A committed effect that fits a source is attributed to no check and never decides a clause, in either direction. A pass stands only when it still holds with every such effect removed and none of them, in the check's window or any later window (barriers and the run-end window included), could be the clause's own effect. An `actor` or `traceId` pin on the clause never excludes one, since a background principal can act for any requester, under its own trace. A fail stands only when it still fails with them removed, and with them added. Anything else reads inconclusive with `background-unattributed`. An absence resting on no background effect also reads inconclusive (`background-unobserved`) when an authoritative observer that could record one (it sees the clause's effect once the `actor` pin is dropped, such as a snapshot beside an audit log) did not decide absence in the check's window or a later one. An allowed-use control keeps an absence pass or a fail and carries the reason as an `attribution` tag; its positive pass is withheld, because a repair is released only on passing controls, and that holds when settlement has also tagged it.
- The cost: declaring a worker means its effects never decide anything, including work it does for a check. With an egress source naming a host, every send to that host is background, so a clause about that host can no longer fail: a forbidden send there reads inconclusive, not fail. A clause stays decisive only where its own pins (`resource`, `fields`) exclude the source's effects, and then only as a pass. Declare narrow sources, and test work a worker does on a check's behalf without declaring that worker.
- The declaration refuses protection that would be silently off: it needs declared observers and an applicable check with effects or claim rules, and every applicable write check (`POST`, `PUT`, `PATCH`, `DELETE`) must declare effects or claim rules, since a write without them has no window and no selector (`attribution-unobserved-write`). A source no started observer can see is refused when the run starts (`attribution-background-unobservable`), before any request. The run-end window is collected in final mode: an egress recorder or payments double with a request arriving at the final mark, or when the window is collected, leaves it partial. An SMTP sink sees a message once its transaction starts (`MAIL FROM`), so a session that had not reached it at the final mark (it cannot be told apart from an idle connection) does not.
- The run keeps an `attribution` record (`scopehaven-attribution/1`), the exported suite carries the declaration, and the validator recomputes every tag. The declaration is part of the profile digest and of the comparison signature, so runs with and without it never compare. Without `attribution` every rule above is exactly as before. An undeclared background process, or a declared one recorded under another name, is attributed by selector as before, and an application that stamps its own effects with a worker's principal turns its fails into inconclusive results, never into passes.
- **Returned ids narrow attribution.** They decide only `effect.exists` passes that background attribution withheld, and nothing else. With forwarded destinations that declare `ids` (above) and a target that declares `correlation`, each check's own selected sends (in its window, carrying the check's own correlation token, not from a declared background source, fitting one of its own clauses' or claims' selectors and no earlier check's) whose outcome is applied seed that check's closure with their minted ids. Without `correlation` nothing seeds. The application writes the token, so an application that stamps the current request's token onto another job's send can still seed a closure; requiring it only removes seeds. A later send whose minted or referenced ids are in exactly one closure belongs to that check and adds its minted ids (one pass in recorder order, per egress recorder). An id minted twice, or echoed anywhere, ties nothing anywhere, and a recorder with any incomplete window ties nothing in that run. Then a matched background-possible send that belongs to this check keeps this check's `effect.exists` pass (unless it also fits an earlier check's selector). Nothing else changes: a returned id says which object a send concerns, not which request caused it, and a check whose request makes the application act on another check's object (the defect an absence check exists to catch) produces a send tied to that other check. So a tie never decides a fail, never excuses a send tied to another check, and never touches an absence clause, `effect.count` or `effect.only`: a background false alarm on an absence clause stays inconclusive. Deciding it would need a signal the application cannot write, such as background traffic arriving through its own route.

**Background writers in the database (`platform`, `ignore`, `queues`, `runLease`).** A real database is never quiet while your app runs. The platform's own services write to it: Supabase Auth logs every sign-in, pg_cron logs every run, pg_net stores every response. Your own workers take jobs off a queue after the app has replied. A second run against the same database writes too. Each of these could fail an absence check on noise, or keep it from ever passing, so the database observers (`pg-snapshot`, `pg-wal` and `sqlite-snapshot`) take four declarations. **Status:** built into the observers; a profile can set them once the connector wiring lands. Until then they are observer options, and a profile that declares none reads exactly as before.

- **Platform ignore lists.** `platform` names a checked-in list in `integrations/observers/ignore-lists/` (`supabase` for Postgres, `litestream` for SQLite). Each entry names a table, the service that writes it, and why its writes carry no effect of your app. `ignore` adds your own background tables (`"public.worker_heartbeats"`, or a whole schema your app never writes; on SQLite, table names). These rules hold for every observer:
  - A table you declare, or declare as a queue, is never ignored. A platform entry that would cover it is overridden for that table (the window record names the override). An `ignore` entry that names it is refused, and so is a schema-wide entry on a schema that holds one.
  - Tables that carry an effect stay off the Supabase list on purpose: accounts and identities, one-time login tokens, files and buckets, realtime broadcasts, scheduled jobs (`cron.job`), outbound pg_net requests (`net.http_request_queue`) and secrets. Declare and observe them, or list them yourself if your checks are not about them.
  - An ignored table's changes never decide a check in either direction.
- **Every other table is accounted for.**
  - **pg-wal:** it sees every logged table's changes. A change to a table that is neither declared, a queue nor ignored makes its window inconclusive (`unlisted-table-changed`), because the effect could have gone there; a table nobody declared is never ignored. A logical decoding message does the same (`logical-message`). Writes to unlogged and foreign tables never reach the WAL, so while such a table exists and is neither declared, a queue nor ignored, absence is held back too (`table-not-in-wal`). On Supabase with pg_net installed this is every window: pg_net keeps its outbound request queue (`net.http_request_queue`) unlogged. List it in `ignore` only once those requests are observed on the wire (an egress recorder in a confined run), since `pg-wal` cannot read them. Large objects stay unseen.
  - **sqlite-snapshot:** the same once it declares a list. It then reads every other table as a digest at each mark, except SQLite's own `sqlite_` tables and virtual tables (whose content is in their shadow tables, which are read), and compares names without case, as SQLite does.
  - **pg-snapshot:** it cannot see other tables. With a list, a writer still open at the end mark stops making its window inconclusive when every write lock it holds is on a table the platform's checked-in list names, or in another database. Your own `ignore` entries do not count here, because your workers can write an app table after their heartbeat, before they commit. A table-wide or prefix absence still needs a cluster in which nothing at all committed, and background writers never allow that: use `pg-wal` for it.
- **The end barrier (`queues`).** List your job tables. A queue whose worker deletes each finished job needs only `{ "table": "jobs" }`. Otherwise name the pending rows: `{ "table": "job", "schema": "pgboss", "pending": { "column": "state", "in": ["created", "retry", "active"] } }`, or `{ "column": "finished_at", "isNull": true }`.
  - **The wait:** each mark waits up to `drainTimeoutMs` (default 10000, polling every `pollMs`) for the queues to drain, then reads them again as part of the mark. A refund a worker makes after the reply therefore lands in the check's own window.
  - **When it reads inconclusive:** a window whose end mark still saw pending work reads `queue-not-drained`. With the every-row default, or a `pending` rule that lists its state, a job scheduled for later counts as pending, and so does a failed job left in the table.
  - **How exact the cut is:** `pg-snapshot` and `sqlite-snapshot` read the queue in the same snapshot or copy as the mark's rows. `pg-wal` reads it on a second session just before the mark, and treats a queue change committed between that read and the mark as `queue-not-drained` too. That check reads the WAL, so `pg-wal` refuses a queue that is unlogged, temporary, a view or a foreign table (`queue-not-in-wal`).
  - **Grants:** the observer's role needs `SELECT` on the queue tables (and only those, for `pg-wal`).
- **One run per database (`runLease`).** Each observer holds a run lease: a shared advisory lock on Postgres, a lease file per database under the machine's temporary folder on SQLite. It is on by default for `pg-wal`.
  - **What it does:** a run refuses to start while another run holds a lease on its database. A window either of whose marks saw another run's lease reads inconclusive for absence (`shared-database`). Its events stay, so a fail stays a fail: anything can take a lock of that class, the app under test included, and must not erase its own fails that way. A fail in such a window can be the other run's write, so re-run that check alone. A `pg-snapshot` whose lease session ended takes the lease again at its next mark, and the window ending there reads `lease-lost`, since a run that started and ended in the gap was never seen.
  - **Order of steps:** start the observers before you reseed, so a second run is refused before it writes anything.
  - **What it misses:** runs that hold no lease are not seen: an older version, an observer with the lease off, or a reseed script on its own.

**Schema changes during a run (catalog fingerprint).** A migration that lands while a run is going changes what the checks after it were tested against. Dropping the trigger that writes the audit row, switching off a table's row-level security, or replacing a function a policy calls can each make a later check pass for the wrong reason. So the database observers (`pg-snapshot`, `pg-wal`, `sqlite-snapshot` and `sqlite-audit`) read the database's catalog fingerprint at every mark (`integrations/observers/catalog.mjs`) and compare it with the one they read at the run's start. **Status:** always on in the observers, with nothing to declare. Recording it in the run and the exported suite, and the retest flag below, need the connector wiring and the comparison rule, neither of which is wired yet.
- **What it covers.**
  - **Postgres:** every schema but the system ones, as the server prints its objects, with each definition reduced to a sha256 in the server. That covers its relations (with grants, owner, row-level security, replica identity, access method and inheritance), their columns, constraints and indexes, policies, triggers, rules, functions, types, extensions, event triggers, foreign servers, publications, default privileges, operators and casts. Names and definitions never leave the database; the record keeps counts and sha256 digests.
  - **How it is read:** on its own short session, before and after each mark's own reads, so each mark opens one more connection. Printing a view or a policy locks the tables it names, so the read waits for a lock at most a second, and a read that cannot finish reads `catalog-unreadable`, never a failed mark.
  - **At the start:** the reading just before the first mark is the run's baseline. One that does not read is tried again a few times; if it still does not read, the observer refuses to start (`catalog-unreadable at start`), since no window could be judged.
  - **SQLite:** every `sqlite_master` row but SQLite's own, with `user_version` and `application_id`.
  - **In the run and the suite:** the run records each database observer's catalog record, and a sha256 over them, as `catalog`; an exported suite names the observers that read one (`catalogSchema`, `catalogObservers`), and a run checked against it may carry records only for those. A suite exported before this field existed refuses every new run that recorded a catalog, which is any run whose `pg-snapshot`, `pg-wal`, `sqlite-snapshot` or `sqlite-audit` observer started (`unexpected-suite-evidence`), so export the suite again after upgrading.
  - **Left out:**
    - the schemas a platform's checked-in list names whole, when the profile declares `platform`. On SQLite, its tables are left out; on Postgres, a platform table's grants, policies and triggers stay in;
    - partitions as relations, so a platform's daily partitions are not a migration. A partition's own grants and column grants, row-level security, policies and trigger state still count, at every level of partitioning.
    - An extension's own objects stay in, read like any other: they change only when access to them changes or the extension is updated.
    - A table you declare is always in.
- **When a window reads inconclusive.**
  - **`schema-drift`:** when either of its marks differs from the start, when the catalog changed between its marks, or when it changed while a mark was read. The middle case catches a change made and changed back to an object that exists at both marks, such as a trigger disabled and enabled again, or row-level security switched off and on. Its events stay, so a fail stays a fail.
  - **After a migration:** every later window differs from the start too, so nothing passes for the rest of the run. Restart the run after migrating.
  - **`catalog-unreadable`:** a window without a readable fingerprint reads this, including one whose catalog read waited past its second for a lock the application held.
- **What is not a change.**
  - **Data operations:** inserts, updates and deletes, `ANALYZE`, `VACUUM`, and the rewrites `TRUNCATE`, `VACUUM FULL`, `CLUSTER` and `REFRESH MATERIALIZED VIEW` (`CONCURRENTLY` included).
  - **Partitions:** a new partition made like the others, by any role, including one of a table a foreign key references.
  - **Reseeds:** two databases built by the same migrations read the same fingerprint, so a reseeded database is not a migration.
  - Checked live on PostgreSQL 15, 17 and a Supabase 17.6 image.
- **Retests across a migration.** A retest compares two runs. When their fingerprints differ, the comparison is to say `migration-between-runs`, and a repair it verifies is reported with that flag, never as an unqualified `FIXED_VERIFIED`. This rule waits on a follow-up change to the comparison; until it lands, a comparison does not read the catalog.
- **Limits.**
  - Role attributes and memberships (`BYPASSRLS`, superuser) are the server's, not the database's, and are not covered.
  - A session setting that stops triggers (`session_replication_role = replica`) changes no catalog row.
  - An object created and dropped inside one window leaves no trace. Only a change to one that exists at both marks shows.
  - One window can read `schema-drift` without a schema change: `VACUUM FULL` or `CLUSTER` on a table with a column added with a default since its last rewrite, `REINDEX CONCURRENTLY`, and `ANALYZE` on an inheritance parent left without children.
  - An index dropped and recreated the same inside one window leaves no trace.
  - Lasting reads with no change by your app:
    - a partitioned table whose partitions differ from one another (a grant, row-level security) reads a change when a partition with a combination of its own is added or dropped, and when its first partition is made;
    - an extension that makes tables as it runs (TimescaleDB's chunks) reads each new one as a change.
  - A role at its connection limit cannot open the catalog's session: a mark reads `catalog-unreadable`, and at the start the observer refuses.
  - A partition's owner is not part of its parent's set (so a partition made by another role is not a change): a partition's owner changed reads only in its own window.
  - A server major upgrade can print some definitions differently, and then reads as a change.
  - On SQLite the schema cookie is the whole database's, so the first `ANALYZE` (it creates `sqlite_stat1`), `VACUUM`, and a platform table created during the run each make their own window read `schema-drift`.

**Absence selectors need a positive twin.** An `effect.none` clause (or `effect.count` expecting 0) on a boundary check passes when its observers saw nothing matching its selector. A selector's `source`, `operation` and `name` are vouched for by the observer's declared vocabulary (a name the observer does not log reads unobservable), but an `actor`, a `resource` or a `traceId` is checked against nothing: a selector naming a wrong actor or resource selects nothing and would pass vacuously. Each such pin therefore needs an allowed-use control carrying an `effect.exists` or `effect.count` clause that shows it: for an `actor` (which must be the check's own principal), the actor's own allowed action pinned to the same principal, with every other key of the absence except its `resource` and `traceId` (its `source`, `operation` and `name`) the same, so the observer is shown to attribute that principal for that kind of effect; for a `resource`, the same selector but the actor (the twin may pin more keys), typically another actor's allowed action on the foreign resource, or the actor's own allowed request on a route only its actions reach. The twin must have been sent and have matched a committed effect in a window of an observer that decided the absence; a twin control that was not sent (a capture it uses was unavailable) shows nothing. Without a twin the clause reads inconclusive (`selector-unpaired`); with twins that matched nothing it reads inconclusive (`selector-not-shown-to-match`); a fail stays a fail, and controls are never paired. An observer that sorts the effects of one destination name into a fixed set of classes can declare that set for that name, as its `resources` vocabulary keyed by name (the payments double declares its provider host's classes). A resource pin on a selector that names that exact name and a declared class then needs no twin, as long as every committed effect of that name (and the selector's source and operation, when it gives them) in the deciding window carries a declared class; another name, a class outside the set, or an unclassified committed effect of that name (with the selector's source and operation, when it gives them) in the window (an unmodelled path) still needs the twin. `./scopehaven assess --check-config` lists the pins of a profile that have no twin as `unpairedSelectors` before any run. It cannot see run-time vocabularies, so it also lists a pin that a vocabulary vouches for at run time; such a pin reads inconclusive (`selector-unpaired`) only when the vocabulary does not vouch for it in that run. Pairing shows non-vacuity, not relatedness: that the selector selects something in this observer's format, not that the check's own request could cause the effect, so an absence clause about an effect its request can never produce still passes once its selector is shown. The examples above already pair every pinned clause: the per-order prohibition on `orders/A-1` with Acme's own refund of it, and the actor-pinned one with Globex's own refund.

**Every prohibition needs an allowed-use control that does something.** An absence that pins nothing pairing reads (no `actor`, `resource`, `traceId`, `fields` or `upstream`) needs no twin, but on its own it shows nothing about the app: an app that does nothing, or one that only says it acted, passes it. So in a boundary check that expects a success status (`status.equals` 200 to 299) and has no positive clause of its own, such an absence (an `effect.none`, an `effect.count` expecting 0, an `effect.only` or an unpinned claim rule) passes only when a required allowed-use control of the same actor passed a positive effect (`effect.exists`, or `effect.count` expecting at least 1) in the run; otherwise its pass reads inconclusive (`allowed-use-not-declared`). That control fails when the app does nothing, and then the prohibition reads inconclusive whatever else holds, `restsOn` included (a guard that failed only on a coverage gap does not count). A check that expects a refusal or a redirect is not guarded: a do-nothing app answers success and fails it. `./scopehaven assess --check-config` lists the absences that lack one as `unguardedAbsences`. The quickest profile with an observer is therefore an identity control, one allowed action of the actor with its `effect.exists`, placed before the prohibitions (a later one's effect that fits an unpinned prohibition's selector withholds that prohibition's pass, as settlement above describes), and the prohibitions. Pinning the prohibition's `resource` or `fields` and declaring the allowed-use twin, as above, is stronger: the twin must also match in the deciding observer's window.

**When nothing can be observed,** keep `evidenceRequirement: "response"` and no `effects`, as in `response-only.example.json`, and report the limits with the results: backend effects are unverified, a write the app commits behind a refusal passes, and a write twin cannot rule out a build that answers success without acting.

**Apps you don't own.** On a practice install of someone else's software, describe the evidence as what the app returned to each test user, plus what that local install recorded for the checks you ran when an observer was declared. Keep it to that install and those checks.

### Account changes mid-run (lifecycle)

A profile can suspend, remove or demote a test user partway through a run and check that the user's old credential stops working. Declare it at the top of the target:

```json
"lifecycle": [{ "changeCheckId": "ADMIN-SUSPEND-CAROL", "actorId": "carol", "after": "refused" }]
```

- `changeCheckId` is the check that makes the change: a required allowed-use control sent by another actor, usually an administrator (for example `POST /api/admin/users/{{carolId}}/suspend` expecting 200), or by the changed user herself (a self-change: `POST /api/sign-out`, revoking her own key, deleting her own account). A self-change must not be a GET, because the user's required GET controls are re-sent at every probe point. It sits outside the user's probe points: all of them come before it, and its login rests on her whole pre-change proof. Give it a predicate only an accepted credential produces when the app has one (the sign-out answer naming the user), since a sign-out route that answers success for anyone still confirms the change. On a forwarded or remote target a self-change uses up the test credential (a revoked key or a deleted account stays that way), so issue a fresh one for each run.
- `actorId` is the changed user. It needs a `credentialEnv` and an identity control before the change.
- `after: "refused"` is the declared policy after the change: the app refuses the user's pre-change credential. It is a per-application policy, not a universal rule. An app whose sessions or tokens stay valid until they expire (many JWT setups) does not meet it, and this field does not test such an app.

Every check of the changed user after the change check is a post-change check. It re-sends the user's unchanged pre-change credential, must expect only the refusal (401, 403 or the user's declared `signInRedirectStatus`) and must declare at least one `effect.none` clause, because a refusal status alone does not show that nothing happened behind it. Put the user's allowed-use controls before the change. The user's identity proof completes strictly before the change check: the closing bracket, the anonymous and invalid-credential probes, and every cross-actor probe that carries the user's credential or tests the user's slot. A credential that still works fails the row from the harness's own observation of the status, and an effect behind the refusal fails it from the observer's record. If the change check did not pass when it was sent, no post-change check is sent and each reads inconclusive (`change-not-confirmed`). The change check is sent by a credentialed actor with an identity control (a profile whose changer has none is refused), and the change is attributed only when that actor's login was proven for the change check: otherwise the post-change checks, already sent, read `changer-login-unproven` (the third state when their refusal was observed), never pass, and the entry records `changerLoginProven: false`. Other users' checks after the change run as usual. Work already in flight or queued when the change happens is not tested by this field. See `integrations/core-practice/profiles.mjs` for a complete profile against the owned practice app.

### Resources one actor creates and another acts on (typed captures)

A check can capture values from its own response for later checks, so a profile can test one user acting on a record another user created without hard-coding ids:

- On the creating check: `"capture": { "aliceNote": { "pointer": "/id", "type": "id" } }`. Its actor is the creator. `type` is `id` (a plain identifier or a non-negative integer), `string` or `integer`. A captured value is a plain identifier (letters, digits, `_`, `.`, `:` or `-`, at most 200 characters, never only dots) or a safe integer.
- On a later check: `{{aliceNote}}` as a whole path segment, a whole query value, or in body string values (a body value that is exactly the placeholder keeps the captured JSON type). Optionally `"precondition": [{ "name": "aliceNote", "type": "id", "createdBy": "alice" }]`, checked when the profile loads: the capture comes first, its type matches and its creator is that actor.
- Declare one check per (creator role, actor role) cell, each on its own captured record and with its effect pinned to that cell, as in `integrations/core-practice/profiles.mjs`.

The capture records never hold the value: they keep `{ name, type, createdBy, captureCheckId, valueDigest }`, where the digest is keyed with a secret the run does not keep, and the request path hash is the declared template's. Observer evidence is separate: an observer's events keep the resource identifiers the application reports (an audit log's request path, a snapshot's row key, a sent request's resource) and digests of what it recorded, so a captured id can appear there, as any id a check touches does. Keep saved runs as private as the profile. A capture misses when the creating check's response is not complete JSON, its status assertion did not pass, or the pointer is absent or holds another type; every check that uses it is not sent and reads inconclusive (`capture-unavailable`). A check using a value created by a user whose login was not proven at the capturing check reads inconclusive (`creator-login-unproven`); the creator's identity is judged at that check, so a later identity failure of the creator does not unsettle it. The creator is the capturing check's declared actor; the app's own record of who created the resource is not read. A surface control cannot use a captured value, as an identity control cannot: the probe points would re-send the raw placeholder.

### Two identities by default (tenant-scoped resources)

A cross-tenant check run by one user shows one side of the boundary. A profile that declares tenant-scoped resources (`tenantValues`, above) therefore needs at least two credentialed identities in two different declared tenants: actors with an `identityValue`, a `tenantId` that `tenantValues` declares, and an identity control. With fewer, `--check-config` prints a warning on stderr (it still exits 0) and marks the target `"singleIdentity": true` in its `twoIdentities` entry, and `assess` refuses the target before anything is authorized or sent (exit 2, `Single identity refused`). `assess --single-identity` runs it anyway, and its output then says that the cross-tenant checks ran from one side only; on any other target the flag only prints a note, and it is refused with `--list` and `--check-config`. A target without `tenantValues` is unaffected and prints what it printed before.

**Mirrors are opt-in.** A target that declares no `"mirrors"` object gets no mirror and runs exactly its declared checks, with the same profile digest as before; the two-identity requirement above still holds. With two identities and a `"mirrors"` object (below), each boundary check (any severity but `control`) of an identity can get a generated mirror under the second identity: an identity in another declared tenant with the same declared `role` and the same refusal declarations (`refusesWith401`, `signInRedirectStatus`), the one whose tenant the check names, else the first by actor alias in that tenant. The mirror is a check of the profile after the declared checks, in its source's order, with the id `<check id>-mirror`, the title `<title> (mirror under <alias>)` and `"mirrorOf": "<check id>"`, and it is sent in the mirror phase (below), after everything the declared checks send. Its `json.noForeignValues` assertions read the second identity's tenant, so its results feed the same TENANT checks from the other side: an app that leaks one tenant's records to the other but not back passes the declared check and fails its mirror. Mirrors are part of the profile, its digest and its check count; a check that declares `mirrorOf` by hand must be exactly the generated mirror, or the profile is refused, and declared mirrors are always put back in the canonical order. Do not commit generated mirrors to a profile file: when the mirror rules change, a hand-declared mirror no longer matches and every target in that file is refused.

A mirror is generated only where the profile's own checks show what the second identity's request reaches: it must not read a refusal as a leak, the second identity's own record as another tenant's, or one tenant's plan, settings or record state as the other's, and it must not write what a correct application accepts. It rests on the profile's declarations: the two tenants are configured alike (the same plan, features and settings), each counterpart pair is two records of the same kind in the same state (with the same refunds, attachments and shares) that no declared check changes by any route (mirrors run after every declared check; ScopeHaven sees a write that names the record anywhere in its path, query or body, in any letter case, inside a longer part such as `ORD-2002.json` too, or as a JSON number written as the declared value, but not one that reaches it otherwise: an assistant told to act on "my latest order", a cascade from a deleted parent, a link that expires when used), every declared value is one no other tenant holds (a value both tenants hold but only one declares reads as a leak in the other's mirror, and a declared check that sends one tenant's value to the other, such as a cross-organisation message, an invite or a share, makes it held by both), and a GET changes nothing. Pair records the profile only reads, or set `"mirrors": "off"`. **Only declared values are rewritten**: each declared counterpart pair between the two tenants, whole and written exactly, in the path, the body and the predicates. Declare the counterparts on the target: `"mirrors": { "counterparts": [["ORD-1001", "ORD-2002"], ["ada@acme.example", "bob@globex.example"]] }`, each pair a value one tenant (and only that tenant) declares and its equivalent in the other. Nothing else in the check changes, so a check is left unmirrored, with its reason in check-config, when:

- **it names either identity** (`names-an-identity`): an actor's alias, `principalId`, `identityValue` or `tenantId`, in any letter case, anywhere in the path, the body (keys included) or a predicate, outside the declared values (a name under three characters only as a whole text). A profile's labels are not the application's values, and a route word or a field (`/api/agent/chat`, `agent_id`) can share a label's spelling;
- **a declared value of either tenant is not swappable**: written in another form (another letter case, percent-encoded, inside a longer word, as a JSON number), without a counterpart, or declared by two tenants;
- **the request holds an identifier the profile did not declare** (`undeclared-identifier`): a path segment or query part holding a digit (`/api/records/7`, `?page=2`; an API version such as `v2` aside), a JSON number or a one-word string that is not a declared value in the body, or, in a check that expects a refusal, a word holding a digit in the body's text;
- **a predicate describes the first identity's view** (`predicate-names-own-view`): a `json.equals` or `json.notContains` whose expected text is not a swapped value, or any `json.equals` or `json.exists` in a check that expects a success (a swapped value there would assume the pairs also match each other's relations, such as which customer placed which order; in a refusal they describe the refusal's body and stay; `json.noForeignValues` always stays);
- **the request names no declared value of either tenant and is not an answer probe** (`resource-owner-unknown`): such a request says nothing about whose record it reaches, so it is mirrored only with `json.noForeignValues` as its only predicate and an expected 2xx `status.equals`, such as an assistant turn asking for every order;
- **a refusal that is not across the boundary, a read and beside the first identity's own allowed twin**: a refusal is mirrored only with a boundary status (401, 403, 404 or the declared sign-in redirect; a 409 or 422 is about a record's state, `refusal-not-boundary-status`), only when the request names a value of the second identity's tenant (a refusal that names only the first tenant's values is about its own record or its settings, `own-record-refusal`), only as a GET (a refused write the application might accept is never sent on a guess, `refusal-not-a-read`; declare the reverse write refusal by hand), and only beside the first identity's own allowed twin (`refusal-twin-not-shown`): an applicable success of that identity with the same method and route, part for part, holding the counterpart wherever the refusal holds the other tenant's value of the pairs (its own records, in the same relation). `GET /api/orders/ORD-2002` refused, beside the first identity's own `GET /api/orders/ORD-1001`, is mirrored, and so is a search or filter whose twin is the same search for the first identity's own value; a workspace or folder name the twin does not share (`/api/workspaces/beta/…`, `…/history?workspace=beta`) is not, because the refusal may turn on that name rather than on the record. The second identity's own allowed twin of the mirror is needed too (below): by the same rule, the source's request in its own form. A correct application then refuses the mirror for the source's reason, with its status, and nothing is written;
- **a success that is not a read**: a success is mirrored only on the first tenant's own values (`foreign-record-success`) or as an answer probe, and only as a read (`success-not-a-read`): a GET, or a POST answer probe answered 200 on a route the target declares read-only, `"mirrors": { "counterparts": [...], "readOnlyRoutes": ["POST /api/chat"] }` (each route `POST /path` without a query, used by a declared check). A declared route covers every query on it. Where its path holds a declared value, declare the counterpart's route too: the second identity's own turn on an undeclared route counts as a write, and the mirror is then skipped as `counterpart-written`. Declare a route read-only only when every check on it only asks: a mirrored assistant turn resends the same message under the second identity, so a turn that asks the assistant to act (`cancel my latest order`) acts on the second tenant. A create route that answers 200, or an acting turn, is never mirrored unless declared so;
- **a declared write changes a record it names** (`counterpart-written`): mirrors run after every declared check, so a value named in the path, query or body of an applicable non-GET check that expects a success or a redirect (a declared cancel, delete, share, invite or assistant action; a POST on a declared read-only route aside) is no longer in the state its pair declares, and no mirror names it anywhere, in its path, query or body (an assistant turn asking about it included);
- **its route is not one the second identity is shown on** (`route-not-used-by-second-identity`): the mirror must have the method and route of one of the second identity's own applicable declared checks (a check that is not applicable shows nothing), every path segment and query value the same except where a declared value stands. A success mirror needs one there that expects a success within the mirror's statuses, and for a GET one on exactly the mirror's path (the counterpart record itself, so a sub-resource such as `/api/orders/ORD-2002/refund` is mirrored only when the second identity is shown reading it), so a route the second identity is shown refused on, such as a feature its plan lacks, gets no success mirror. A refusal mirror needs the second identity's own allowed twin of the mirror: its own success with the same method and route, holding the counterpart wherever the mirror holds the first tenant's value (so its own record through the first tenant's workspace is not one). Give the second identity its own checks on the routes you want mirrored (its own order, its own assistant turn);
- **the second identity's own check contradicts it** (`contradicts-second-identity-check`): the second identity declares the same request (method, path and body) with statuses none of which the mirror expects.

Never mirrored: allowed-use controls, checks with effect clauses (their pairing twins and guards are the first identity's), checks that capture or use captures, or declare a `precondition`, `restsOn`, a `webhook` or claim rules, checks that are not applicable, and every check of a target that declares a `lifecycle` or a `timing` plan (the change order and the declared budget were written for the declared checks). A check the second identity already declares is not duplicated. `"mirrors": "off"` turns generation off, as leaving `"mirrors"` out does.

**The mirror phase and per-user limits.** Mirrors are sent in a phase of their own: after every declared check, the final settle and mark, the observers' stop and every identity's refusal probes (its identity control without a credential, with a look-alike and with the other identity's credential), outside the identity brackets. Each mirror identity's identity and surface controls are re-sent before its first mirror and after each of its mirrors, and those probe points vouch for its mirrors only. So a mirror never changes a declared check's request, window, probe point, identity or verdict: the declared rows are the ones the run gives with mirrors off. The phase has a run budget of its own after the declared run's, so no declared wait keeps time for it. `--check-config` prints the requests it adds per identity (`twoIdentities.extraRequests`: each mirror, and one probe point more than the identity has mirrors). A per-user rate or question limit without that headroom over the declared profile's own requests answers the mirrors, never a declared check:

- a mirror answered 429, or with a status the declaration names, reads inconclusive with its own assertion (`Mirror answered by the tenant boundary, not a per-user limit`), whatever else it read, unless the limit's own answer names the other tenant's values (`json.noForeignValues` fails, and the mirror reads FAIL). Declare the statuses besides 429 the application's limits answer with: `"mirrors": { "counterparts": [...], "rateLimitStatuses": [503] }`, at most four, each from 400 to 599 and never a boundary refusal (401, 403 or 404, which a mirror expects). The run and its exported suite carry them (`mirrorPhase.rateLimitStatuses`);
- a mirror-phase probe point the limit answers withholds the mirrors it covers, and one it refuses (401, 403 or the declared redirect) withholds every mirror of that identity;
- the gate then reads exit 1 where the same run was clean with mirrors off: `inconclusive-evidence`, and also `prohibition-observed-identity-unproven` when the limit runs out between a mirror the app answered and the probe point after it (or answers an identity's own probes), and `comparison-incomplete` against a baseline. It never reads `identity-not-established` because of a mirror, and no mirror reads FAIL on a 429 or a declared status.

A limit that answers 401, 403 or 404 cannot be told from the boundary: a refusal mirror reads it as the boundary's answer, withheld (prohibition observed, identity not established) when the limit also refuses the probe points after it, and a success mirror (an answer probe, or a read of the second identity's own record) reads FAIL on it. For such an application leave the headroom `extraRequests` gives, or keep mirrors off.

`--check-config` lists, per tenant-scoped target, each mirrored check and each check left unmirrored with its reason (the full list is `MIRROR_SKIP_REASONS` in `src/two-identities.mjs`), and both `--check-config` and `assess` warn when a tenant-scoped target that declares a `"mirrors"` object has two identities but gets no mirror at all; `--list` lists the same targets without either warning. A mirror that would break one of the profile's rules (the check, timeout and request limits among them, or an invalid mirror) is left out on its own, in canonical order, and listed as `profile-rule`, so a profile that loaded before still loads. The dashboard and the library entry (`runHttpAssessment`) generate the same mirrors; only the CLI's `assess` refuses a single-identity target.

### Assistant-turn checks (part of every profile with a chat surface)

Permission rules that hold on the direct API can fail when an assistant fetches data or acts for the user. If the app has a chat or agent endpoint, give the profile checks that go through it, next to the direct checks. An assistant-turn check is an ordinary check: a POST to the chat route as one test user, with a message asking for something that user may not have.

- **Disclosure.** Plant a distinctive synthetic value in another tenant's records and add `{ "kind": "json.notContains", "pointer": "/reply", "expected": "pat.lee@acme.test" }` on the reply. `json.notContains` is an exact, case-sensitive substring test of that one string field: the same value in another field, in different case, spelled out or encoded passes. Prefer an opaque planted token, such as a random code no answer would contain by chance, and report a pass as one sample of that string in that field. Or declare the tenants' synthetic values once and add `{ "kind": "json.noForeignValues", "pointer": "/reply" }`, which reads every declared value of the other tenants under the allowlist rule in the assertion list above. It fails only on another tenant's identifier written literally (its exact declared characters) as a whole token; it passes only when every leaf at the pointer is in the plain form, the response body repeats no member name, and no other tenant's value occurs in any reading. Everything else reads inconclusive, never pass: another letter case, other spacing or punctuation, an encoding, markup, look-alike letters of another script, a number written differently and a value split across leaves are not matched as leaks, they only withhold the pass. A pass is one sample of the declared values in that field.
- **Actions.** Where the assistant can act, add the same effect assertions as the direct check, for example `effect.none` on `refund.create` by that user and on the target resource, with `"evidenceRequirement": "backend"`. The assistant's tool path must write the same audit row as the direct route, or an audit observer cannot see it; use a database or activity observer, since a request log sees only the chat request.
- **Allowed-use twins.** Give every forbidden action its own required allowed-use control, listed in `requiredControlIds`: run as the same actor, on the same surface (direct API or assistant), and of the same kind (a read for a read, a write for a write, with the same effect assertion pinned to that actor's own record). Put a twin of the same action before and after each prohibition, so a refusal of that action that starts or stops partway through the run still fails a required control. A refusal that varies request by request can still make a prohibition read fixed; before acting on a restored row, re-run it alone as that user's first request. A twin run as a different user, or only for reads, cannot show that a fix did not simply lock the forbidden actor out of that action. Assert a value only a real answer carries. There is no "contains" predicate, so a free-text model answer cannot be required as such: use `json.equals` on a structured field the app returns, or the twin cannot rule out an assistant that refuses everything. An echoed request field, such as the order id, is not enough. A write is a real change on the target: a DELETE, PUT or PATCH can use up or alter the record the next run probes. So before every destructive probe of another user's record, also put a required control in which the record's owner reads it, and reset the target to the same seed before every run a comparison uses. A record used up by an earlier run then fails that control and blocks the comparison instead of reading as restored.
- **Request budget.** Give each assistant-turn check a `timeoutMs` (1000 to 120000). A model turn usually dominates the run time; declared timeouts may add up to at most 600000 ms per profile.

A model's reply can differ between runs. One passing turn is one sample, not proof that the assistant never discloses; a failing turn is a confirmed failure in that run. For repeated turns, use the conversation connector in `integrations/conversations`: it runs trials, and its canary checks (`reply.notContains`) normalize case, Unicode forms and HTML entities across the whole reply body and its stream events.

The `sqlite-audit`, `http-audit` and `sqlite-snapshot` examples have seven assistant-turn checks: agent A's read twin; agent B's read twin and refund twin before the prohibitions; the action check and the disclosure check; and B's read twin and refund twin after them. The `response-only` example has six: it leaves out the action check, which it cannot observe. To see all four profiles run against the example app's builds (`examples/observed-support-app.mjs`: loopback, synthetic data, a fixed-text assistant and no model; secure, leaky, and drill builds that lock agent B out, lock or hide the assistant's refunds, suspend B's writes partway through, echo a refusal, record a refund under the wrong actor, or leave the leak open behind a refusal that starts partway through the run: a suspension, a rate limit, a question limit or a first-refund confirmation), run `node --test test/onboarding-profiles.test.mjs` from the `scopehaven` folder with Node 24.22.1 or newer in the 24 line (`>=24.22.1 <25`). Plain `node` skips the launcher's version check, so confirm `node --version` first. To start your own profile from one, copy it to a private location and replace the origin, paths, actors, routes and planted values with your app's.

### A first engagement, end to end

Sign each test user in through the app's own login, and put the session values in a private env file (mode 0600) as the `SCOPEHAVEN_TARGET_` variables the profile names. Record the signed rules of engagement as an authorization record ([RULES-OF-ENGAGEMENT.md](RULES-OF-ENGAGEMENT.md)) and seal it. Then, from the `scopehaven` folder:

```sh
set -a; . /absolute/private/myapp.env; set +a
./scopehaven check-config --config /absolute/private/myapp.targets.json
node integrations/roe/cli.mjs check /absolute/private/authorization.json --config /absolute/private/myapp.targets.json --target my-app
./scopehaven assess --config /absolute/private/myapp.targets.json --target my-app --out /absolute/private/evidence --authorization /absolute/private/authorization.json
```

`check-config` should show the target `available: true`. The assessment prints the run ID and counts. To verify a repair, keep the baseline and the retest in **one gate directory**, because `--baseline` only finds runs saved there:

```sh
./scopehaven gate --config /absolute/private/myapp.targets.json --target my-app --out /absolute/private/gates/round1 --authorization /absolute/private/authorization.json
./scopehaven gate --config /absolute/private/myapp.targets.json --target my-app --out /absolute/private/gates/round1 --baseline BASELINE_RUN_ID --authorization /absolute/private/authorization.json
```

The first command saves the before-repair run; its `current.runId` is the baseline. Run the second after the repair. Then export the deliverable from that same directory with `--data`. Each output file must be new, and its folder must be yours with mode 0700:

```sh
mkdir -m700 /absolute/private/deliverable
./scopehaven export --data /absolute/private/gates/round1 --run CANDIDATE_RUN_ID --baseline BASELINE_RUN_ID --format html --out /absolute/private/deliverable/report.html
./scopehaven export --data /absolute/private/gates/round1 --run CANDIDATE_RUN_ID --baseline BASELINE_RUN_ID --format json --out /absolute/private/deliverable/comparison.json
./scopehaven export --data /absolute/private/gates/round1 --run CANDIDATE_RUN_ID --format sarif --out /absolute/private/deliverable/findings.sarif
```

The SARIF file has no standards tags for your profile's checks, because their IDs are yours. To add them, write a map in the format of `src/standards-map.json`, keyed by your suite ID (`<profile id>-contracts`), and add `--standards-file /absolute/private/maps/standards.json` to the SARIF export. It is checked like the bundled map, and more strictly: every identifier must exist in the pinned release (OWASP LLM 2025 and 2026, OWASP Agentic 2026, MITRE ATLAS 2026.09 techniques, CWE 4.20 weaknesses, so a CWE category such as CWE-840 is refused); every ASI and ATLAS tag needs a rationale; the relationship is `relevant` or `subset`; notes and rationales are at most 500 characters, with no control characters and no compliance or certification wording; and the map may cover only your own suites, never one ScopeHaven's bundled map reviews. The map selects each vocabulary; the name, version and organization in the SARIF file always come from ScopeHaven. If the map's role for a check disagrees with the run (for example it tags a check the run marks as an allowed-use control), that check gets no tags and the SARIF file carries a warning. The map applies to that export only and never changes run hashes. A tag says the check is mapped to that identifier, not that a framework requirement is met.

**Signing.** Exports and evidence packs are signed by default with the operator's local Ed25519 key, into `NAME.dsse.json` beside each file (`--unsigned` skips it for a single export; a pack is always signed). That signature shows only that whoever holds the key produced these bytes, so a pack signed on the application owner's machine is self-attested. ScopeHaven can add a second signature: a countersignature over hashes only, with a key published at `https://scopehaven.dev/.well-known/scopehaven-keys.json`, and an RFC 3161 timestamp from freetsa.org ([SIGNING-KEYS.md](SIGNING-KEYS.md)). Signing, the countersignature and both verifiers are available but not yet in this release's tested modes.

**Signed exports.** `scopehaven export` signs each export into `NAME.dsse.json` beside it (here `report.html.dsse.json`, `comparison.json.dsse.json` and `findings.sarif.dsse.json`) with a local Ed25519 key in `~/.config/scopehaven/signing`. The first export creates the key. `--signing-key-dir /absolute/dir` uses another key directory, and `--unsigned` skips signing. The command's output names the envelope, the key id, the public key and both verify commands. A recipient verifies with `python3 integrations/attest/verify_envelope.py --key DIR/scopehaven-signing-key.pub.pem --envelope NAME.dsse.json --dir DIR`, or `node integrations/attest/cli.mjs verify` with the same arguments, where DIR holds the export and your public key, whose key id they confirm with you over a separate channel. A signature shows the key holder produced these exact bytes, not that the results are correct. A key or key directory with a wrong mode or owner is refused (`signing-key-unsafe`), never repaired, and a failed sign leaves no export behind (exit 2). The HTML report and the comparison report carry a "Signed evidence" paragraph inside the signed bytes, and SARIF names the key id; the run JSON export stays byte for byte the record. The GitHub Action and the scheduled drift runner (`integrations/schedule/run-local.sh`) export with `--unsigned`, and library callers of `exportRun()` sign only when asked. See [integrations/attest/README.md](../integrations/attest/README.md).

**Coverage in the reports.** The HTML report and the comparison exports have a "Coverage and residual" section ([Reading results honestly](#reading-results-honestly)). For the full pre-run coverage report ([integrations/coverage-report/README.md](../integrations/coverage-report/README.md)), give an HTML report or comparison export the operator's inventory, stated contract and targets manifest: `--coverage-inventory /absolute/private/inventory.json --coverage-contract /absolute/private/contract.json --coverage-targets /absolute/private/myapp.targets.json`. The three come together, as absolute paths. The targets file must name the run's target. A refused file stops the export before anything is written (`coverage-inputs`). If that profile's digest is not the run's, the report says the coverage is of the profile as it is now.

**One folder for the hand-off.** To hand the evidence to a reviewer, one command replaces the three exports above:

```sh
./scopehaven evidence-pack --data /absolute/private/gates/round1 --run CANDIDATE_RUN_ID --baseline BASELINE_RUN_ID --out /absolute/private/deliverable/evidence
```

`--out` must be a new absolute path in its plain form (no trailing slash, no `.` or `..` segments, no doubled slashes); its parent and the store named by `--data` must be existing directories of yours, not symlinks. The new folder (mode 0700, every file 0600) holds `run.json`, `run.html`, `run.sarif`, `summary.html` and `residual.json`, and with `--baseline` also `comparison.json` and `comparison.html`. Each comes from the same exporter as `scopehaven export` and is signed beside it with one key. A pack takes no `--standards-file`, so its `run.sarif` has no tags for your profile's checks; if you need them, export that SARIF on its own as above. The folder also holds your public key (`scopehaven-signing-key.pub.pem`), a copy of `integrations/attest/verify_envelope.py`, a `VERIFY.md` with one verify command per envelope and what a signature does and does not show, and `evidence-pack.dsse.json`, one envelope over every other file. The same three `--coverage-*` files go to the HTML report and both comparison exports. A pack is always signed: `--signing-key-dir` picks the key, there is no `--unsigned`, and the key directory may not be `--out`, sit inside it or hold it. `--retest-history ABSOLUTE_DIR` adds `retest-history.json` and its envelope from a folder made by `integrations/retest-ledger/cli.mjs export` with the same key; a history signed by another key, an envelope naming any other file, a missing, symlinked or oversized file, a file that is not a retest history, or a history with no finding on the run's application and suite refuses the pack, and a payments pack takes no history. The pack is built in a hidden staging folder beside `--out`, and every envelope is verified again from disk before the folder takes its name, so a refused or failed pack writes nothing at `--out` (exit 2). The recipient still gets your key id from you over a separate channel and checks that every command in `VERIFY.md` prints it. For a reviewer who needs a signature from someone other than you, ScopeHaven can countersign the pack: only the hashes of `evidence-pack.dsse.json` leave your machine, and two files, `evidence-pack.countersign.dsse.json` and `evidence-pack.countersign.tsr`, come back into the folder. The reviewer checks them with `--scopehaven-keys`, `--countersignature` and `--timestamp` on either verifier, against the key set published at scopehaven.dev ([SIGNING-KEYS.md](SIGNING-KEYS.md)). A pack signed only on your machine is self-attested.

For a run of the payments pack ([integrations/payments-pack/README.md](../integrations/payments-pack/README.md#exporting-a-saved-run)), `./scopehaven payments export --run /absolute/DIR/<run-id>.json --format sarif --out /absolute/private/deliverable/payments.sarif` writes the run's SARIF and its envelope. The pack form takes absolute run files and no store, run id or coverage files, and recomputes the comparison from both runs:

```sh
./scopehaven evidence-pack --payments-run /absolute/DIR/<run-id>.json --payments-baseline /absolute/DIR/<baseline>.json --out /absolute/private/deliverable/payments-evidence
```

It holds `payments-run.json`, `payments-run.html` and `payments-run.sarif`, and with `--payments-baseline` also `payments-comparison.json`; the HTML then carries the before-and-after section.

If the app caches permissions (n8n caches project memberships, for example), a permission change made directly in its database takes effect only after the app restarts. Restart it before the retest, or the retest still sees the old behaviour.

If a profile is rejected, the message names the target, check, assertion and field, for example `target "lab" > check "allowed" > assertion 2 (json.exists): unsupported or missing fields (missing field "expected" ...)`. It never repeats configured values.

Use `evidenceRequirement: "response"` for response claims. Use `"backend"` on a check whose verdict needs backend evidence: it passes only when an authoritative observer (not `otel` or `mcp-log`) decided every effect the check declares (see [Observe what the app recorded](#observe-what-the-app-recorded-the-default)); otherwise it stays inconclusive. Missing/non-string values for a `json.notContains` predicate are inconclusive, not proof of absence.

Profiles must be regular JSON files of at most 2 MiB and cannot be symlinks. Only GET, POST, PUT, PATCH and DELETE requests and literal numeric loopback HTTP origins are supported, plus an `operator-remote` https origin under an authorization record naming it (see remote mode below). Defaults bound request bodies to 8 KiB, responses to 64 KiB, individual requests to three seconds and the run to sixty seconds. Requests run once with no redirects or automatic retries. Scopehaven connects to a remote endpoint only in remote mode, under an authorization record that names its exact origin; otherwise, to test your own staging, use in-network mode below. Do not treat an exported redacted suite summary as an executable profile.

**Warm up development servers first.** Development-mode servers, such as `next dev`, build each route the first time it is requested. On a busy machine that first request can take longer than three seconds, and the first check then ends as an error rather than a pass or fail. Before a run, request each GET path in the profile once, for example `curl -s -o /dev/null http://127.0.0.1:<port><path>`, or open the app in a browser. If the app redirects signed-out requests before they reach the route, as Auth.js middleware does, send the warm-up as one of the test users; otherwise only the redirect gets built. Keep the session value off the command line and out of shell history. Write it to a private header file with the shell's built-in `printf`, which does not appear in process listings, then remove the file:

```sh
umask 077; printf 'Cookie: authjs.session-token=%s\n' "$SCOPEHAVEN_TARGET_EXAMPLE_TOKEN" > warmup.headers
curl -s -o /dev/null -H @warmup.headers http://127.0.0.1:<port><path>
rm warmup.headers
```

Never warm up with POST, PUT, PATCH or DELETE requests, since they can change data. Alternatively, give only the first check for that route a `timeoutMs`.

A POST, PUT, PATCH or DELETE check is a real change on the target, and a timeout does not undo it. A DELETE, PUT or PATCH can use up or alter the record the next run probes: a record a vulnerable build deleted in the first run is gone in the second, so the prohibition's 404 reads as a refusal and the comparison can read restored with nothing fixed. Reset the target to the same seed before every run a comparison uses, and put a required owner-read control of the probed record before every destructive probe (see Allowed-use twins), so a missing record blocks the comparison instead of reading as restored. Inspect the target before manually retrying, and reset test data deliberately when needed. Unlike the built-in fixture, the HTTP connector does not create a fresh target or automatically reset it between checks.

### Start from your own declarations (policy import)

Writing every expected permission by hand is slow. If your application already declares who may do what, `./scopehaven policy` can read those declarations and draft the checks for you. A person still confirms every drafted check before anything runs.

It reads three kinds of declaration, from local files only:
- **Postgres row-level security.** The authoritative input is a catalog dump: run the `CATALOG_DUMP_SQL` query from `integrations/policy-import/README.md` on a test database, then pass the file with `--catalog`. Replaying migration files (`supabase/migrations` and similar) is best effort, and any statement it cannot follow makes the affected cells `unknown`, never a guess.
- **OpenAPI security requirements**, from an OpenAPI 3.0 or 3.1 JSON document, with an optional role map.
- **Open WebUI access grants**, from an export of a private copy of `webui.db`.

It never connects to a database or service and never changes the application. Outputs are new files with mode 0600. Keep them private: they describe your permission model.

The loop:
1. `import` builds a cited permission matrix: one cell per role, resource and action, each `allow`, `conditional`, `deny`, `undeclared` or `unknown`. Undeclared never becomes deny.
2. `draft` turns `allow` and `deny` cells into GET-only checks (allowed-use controls and refusal checks) through a binding file that maps roles to your profile's actors and resources to requests. Conditional, undeclared and unknown cells are listed for you to write by hand.
3. `confirm` takes a named person, re-drafts from the same matrix and binding, adds the checks to your profile, makes the controls required, and writes a sealed confirmation record.
4. Run the confirmed profile as usual with `./scopehaven assess` or `./scopehaven gate`.
5. `explain` lines a saved run up with the declarations it came from. `diff` compares the matrices of two releases and exits 1 when access widened or a cell became unknown or undeclared.

Run it through the launcher with absolute paths, because the launcher works from the project folder:

```sh
./scopehaven policy import rls --app my-app --roles anon,authenticated --catalog /private/catalog.sql --out /private/matrix.json
./scopehaven policy draft /private/matrix.json --binding /private/binding.json --out /private/draft.json
./scopehaven policy confirm /private/draft.json --matrix /private/matrix.json --binding /private/binding.json --profile /private/my-app.targets.json --confirmed-by "Your Name" --out-profile /private/confirmed.targets.json --out-record /private/confirmation.json
```

What it does not establish: a matrix is a reading of declarations, not an observation of behaviour, and declarations can be incomplete or wrong. What the application actually does is what the confirmed checks test, with the evidence limits described above. See `integrations/policy-import/README.md` for every rule and limit.

## Testing your own staging environment (in-network mode)

**Status:** available under an authorization record that names the forwarder's destination (below). It is not part of this release's tested modes; read its limits in [KNOWN-LIMITS.md](KNOWN-LIMITS.md#operator-forwarded-staging) before relying on a result.

In this mode Scopehaven connects only to a literal `http://127.0.0.1:PORT` origin. To test a staging environment you control this way, run a small forwarder on the same machine. It listens on a loopback port and forwards to your staging. Scopehaven still sends every request to loopback, and the forwarder decides where it goes. That makes the forwarder part of your test setup, the same way your test credentials are.

**Before you start (authorization checklist):**
- You have written permission to test this environment, from whoever owns it.
- It is a staging or test environment, not production, and it holds no real customer data.
- Every actor uses a dedicated test account. Never use a real person's login.
- POST, PUT, PATCH and DELETE checks can change data. Agree in advance which actions may be exercised, and how to reset the environment afterwards.
- The environment may call its own providers (payment, email, AI models). Testing can trigger them, so check costs and side effects first.

**Set up the forwarder.** Use whichever of these fits your network:
- **SSH tunnel:** `ssh -N -L 127.0.0.1:4500:staging.internal:80 jump-host`. This is for plain-HTTP staging inside a network you can reach over SSH.
- **Local reverse proxy:** use this for HTTPS staging. Configure a proxy you already trust (Caddy, nginx) to listen on `127.0.0.1:4500`, connect to staging over TLS, and set the `Host` header staging expects. Scopehaven speaks plain HTTP to the proxy; the proxy handles TLS.

Keep the forwarder bound to 127.0.0.1 only, and stop it when the run ends.

**Declare it in the profile.** Set the target's `origin` to the forwarder (`http://127.0.0.1:4500`). Set `"targetContext": "operator-forwarded"`, and give a short `"targetLabel"` such as `"acme staging (forwarded)"`. Never put a URL or hostname with credentials in the label. The run, gate, report and SARIF then all state that the evidence came from a forwarded target, so nobody mistakes it for a local app. Runs with different target contexts never compare as compatible.

**Name the destination in the authorization record.** A forwarded target runs only under a record ([RULES-OF-ENGAGEMENT.md](RULES-OF-ENGAGEMENT.md)) whose `origins` list the forwarder's loopback port and whose `forwarded.destination` names where the forwarder sends traffic, as an origin (`"forwarded": { "destination": "https://staging.acme.example" }`). Without it, `assess`, the gate, the Action and the dashboard refuse the run (`authorization-forwarded`) before any request; a record that names a destination does not cover a target that is not declared forwarded. ScopeHaven cannot see where the forwarder goes: the destination is the operator's statement, bound by the record's checksum, and it stays in the record (the run carries only the record's id and checksum).

**Give every forbidden check a same-route control.** In a forwarded run, a boundary check's pass counts toward a clean gate, and toward a clean `assess` exit, only when a required allowed-use control with the same method on the same route passed in the same run (two different records on the same route, such as your own note and another user's, are the same route). Otherwise the gate reports `forwarded-pass-unpaired` and is not clean, and `assess` exits 1 and lists the checks as `forwardedUnpaired`. `check-config` lists them before any run. A forwarder that denies or strips credentials on one route denies or strips the allowed request on that route too, so the control fails instead of the forbidden check passing silently.

**Prove each login through the forwarder.** Identity proof works exactly as for a local app. Each credentialed actor needs a session-derived "who am I" control, and Scopehaven checks it before and after the actor's checks, without a credential, with a random credential and with each other actor's credential. If the proxy or staging rewrites cookies or strips the `Authorization` header, those actors' logins are not proven and their forbidden checks read inconclusive. If it redirects sign-ins, no login is proven and the rows read fail, not inconclusive: a 302 is outside the statuses the checks accept, and declaring `signInRedirectStatus: 302` does not change that. Read the identity rows first, and fix the forwarder before trusting any result.

**What identity proof does not cover.** It shows that each login reached whatever answers the identity route through the forwarder, and nothing more. The forwarder is operator trust.

- A forwarder that answers or alters one route itself (a deny rule, credentials stripped on that route only, the wrong upstream for it) can make a forbidden check on that route read pass, with every login proven. The same-route control rule above keeps the gate from reading clean: without a passing control on that route the pass does not count, and a forwarder that denies or strips on that route fails the control. The forbidden row itself still reads pass.
- A wrong upstream that serves the same accounts, a response cache kept across runs, and a gate that refuses only signed-out requests while letting the public page through cannot be detected in one run. Rule them out on the forwarder.
- A gate or WAF that answers every request with 401 makes a signed-out forbidden check read pass although nothing reached the app. Signed-out checks are protected only when the signed-out actor has a required control, such as a public page: that control then fails and the row is held back. Without one, there is no protection.

The pinned cases are in `integrations/forwarded/README.md`.

**Things that behave differently on staging:**
- **Secure cookies:** staging over HTTPS often sets `__Secure-` cookies. Use that exact name in `credentialCookie`.
- **Absolute redirects:** a redirect to `https://staging...` is recorded as a response and never followed. That is expected.
- **Slow first requests:** warm the routes up as described above, or give the first check a `timeoutMs`.
- **No observer:** without an observer configured on staging's own records, results are judged from responses only. A pass means "not reproduced through the responses checked", not "enforced in the backend".

**What in-network mode does not do:** Scopehaven does not connect to remote hosts, resolve DNS names, follow redirects or upload anything; the forwarder does. Testing a vendor-hosted service (a hosted support bot, for example) needs that vendor's permission and a sandbox, and is out of scope for this mode.

## Testing a staging environment directly over HTTPS (remote mode)

**Status:** available under an authorization record that names the exact origin (below). It is not part of this release's tested modes; read its limits in [KNOWN-LIMITS.md](KNOWN-LIMITS.md#remote-https-targets) first. Use it when a forwarder is not practical; the forwarder mode above keeps ScopeHaven on loopback.

**Declare it in the profile.** Set `"targetContext": "operator-remote"`, the `origin` to the staging origin itself (`https://staging.acme.example`, or with a port, `https://staging.acme.example:8443`; a host name or an IPv4 address, nothing else: no credentials, path, query or IPv6 literal), and a short `"targetLabel"`. Plain `http://` to anything but 127.0.0.1 is refused. Observers stay on loopback, as for any target.

**Name the origin in the authorization record.** The record's `origins` must list that exact origin, written as its origin (lower case, no default `:443`). If staging resolves to a private address (a VPN or an internal network), list each such address in the record's `addresses`: without that, a host that resolves to a loopback, private, shared, link-local, cloud metadata or other non-public address is refused before any request (`remote-address-refused`).

**What ScopeHaven does on the wire:**
- It resolves the host once before the first request and connects every request to that address for the whole run. Before each request it resolves the host again; if the answer is not the same set of addresses, the run stops (`remote-dns-changed`) and no run is saved. A host behind a DNS-rotating CDN may not be testable this way: use the forwarder.
- The record's window applies as to a loopback target: once it ends, no further request is sent and the host is not resolved again, and the run is refused (`authorization-window-ended`) with nothing saved or stamped. The window is checked before each DNS check and again after it, immediately before the connection, so a slow lookup that runs past the end sends nothing, and once more when the TLS handshake is done, immediately before the request is written, so a slow handshake that ends after the end sends no request either: the socket is closed with nothing written. Only the handshake itself can finish after the end, within that check's request timeout (3 s by default, up to 120 s for a check that declares `timeoutMs`).
- It verifies the certificate for the host against the system trust store. For a staging CA of your own, point Node at it with `NODE_EXTRA_CA_CERTS=/absolute/path/ca.pem`. TLS 1.2 or newer, no proxy, no connection reuse.
- It never follows a redirect: a 302 to another origin is recorded as the check's response, and nothing is sent there. Credentials (bearer tokens, cookies) go only to the pinned origin.

**Same-route controls.** A CDN, WAF or API gateway in front of staging can answer a route itself, exactly like a forwarder. So the same rule applies: a boundary pass counts toward a clean gate or a clean `assess` exit only when a required control with the same method on the same route passed in the same run (`remote-pass-unpaired` otherwise; `assess` and `check-config` list the checks as `remoteUnpaired`).

**What remote mode does not do:** it does not make the staging environment's own behaviour attested (which deployment answers at that origin is the operator's statement), it does not observe staging's database or outbound calls unless you run loopback observers for them, and it is never for production or for a service you do not own.

## Reading results honestly

| Result | What it means | Useful next action |
| --- | --- | --- |
| Pass | The check's required assertions were satisfied within its stated evidence scope. | Preserve the evidence and test permitted behavior again after a repair. A response pass says nothing definitive about hidden backend effects. |
| Fail | Available evidence contradicts a named requirement. | Inspect the failed assertion, repair the authorized test application and rerun the unchanged contract. A confirmed failure takes precedence over other missing evidence. |
| Inconclusive | Necessary evidence is missing, unsuitable or incomplete for a verdict. | Obtain the required observation or fix the predicate/context. Do not count it as a pass. Complete but invalid JSON can leave JSON assertions inconclusive. |
| Error | The harness or transport could not produce a usable completed observation, such as a timeout, network failure or response-size limit. | Repair setup/transport and inspect possible target effects before retrying. This does not establish that the application is safe or vulnerable. |
| Not applicable (`not_applicable`, N/A) | A configured check was explicitly excluded from scope with a reason; no request was sent. | Verify that the capability is genuinely absent and re-enable the check when scope changes. N/A is never a pass. |

**Claim types and the residual.** Every row of the HTML report, SARIF and the comparison exports carries a claim type that says what its verdict rests on. **Exact**: decided from records held outside the application (a request-path observer such as the egress recorder or SMTP sink that recorded the forbidden effect, or the response ScopeHaven itself received), and, for a verdict decided by absence (an absence or count pass, or a fail because a required effect did not appear: an `effect.exists`, a count below its number, a success claim; a count by applications is read by its applications, not its sends), only with every declared channel observed in its window by records held outside the application, with nothing unaccounted on them, in a confined run. **Risk-bound**: decided from records the application can write (a snapshot, an audit table, its own action log, or an effect clause with no custody record, as in a run saved before per-clause custody), from a sampled property (a conversation judged over trials, whichever way it went), from a fail resting on a declared field absent from the request body, or from a verdict decided by absence whose channels are undeclared (a sequence declares none), were read from net change or were watched only through the application's own records (so a declared database channel keeps such a pass risk-bound); it is only as good as the risk that those records or that sample are wrong. **Descriptive**: decides nothing (inconclusive, error, not applicable, or a pass the gate does not count). A response-only exact row is exact about the response and nothing else, and a claim type says what a verdict rests on, not whether the record is accurate. A count below its number that matched some effects stays risk-bound even then, unless another passing count or `effect.only` of the check selects those effects: the channel rule reads them as unaccounted, since only a passing clause accounts for its own. Each export also has a **residual** section: the declared channels not observed or carrying an unaccounted effect (or "channels undeclared"), every check that reads inconclusive with its reason codes (including each window that ran partial or failed, the identity, precondition and later-outcome reasons, and a sequence row's own verdict), the allowed-use controls whose absence the declared channels do not support, the allowed-use pairing that did not hold (required controls that did not pass, forwarded or remote passes with no same-route control, absence selectors with no allowed-use twin), and the declared observers that could not report, had no window or ran a partial window in a check (a sequence's from its sealed evidence), or that no observer is declared; for other origins (a conversation's victim views, the owned fixtures) it says observers are not read. Nothing in the residual is a pass. `./scopehaven export --run RUN_ID --format residual --out FILE.json` writes the claims and the residual alone; the JSON export stays the sealed run record and carries neither.

**Coverage and residual.** In the HTML report and the comparison report the residual sits in a "Coverage and residual" section, after a coverage part. From the run alone, that part lists, for each actor with a boundary check, the required allowed-use controls that ran as that actor. An actor with none is shown in red, because a fix that refuses that actor everything would read as a fix. The comparison JSON carries those actors (both sides together) as `coverage.actorsWithoutAllowedUse`, and SARIF as `runs[0].properties.coverage.actorsWithoutAllowedUse`. The full pre-run coverage report needs the operator's inventory, stated contract and targets manifest (`--coverage-inventory`, `--coverage-contract` and `--coverage-targets`, HTML report and comparison exports, see [A first engagement, end to end](#a-first-engagement-end-to-end)); without them the section says so. Coverage is presentation only: it feeds no verdict, count, comparison, gate outcome or hash. The compact summary keeps its "Residual" heading and carries no coverage.

HTTP profiles can optionally include `applicability: { "applies": false, "reason": "Capability absent in this test application" }` on a check. The reason is required; applicability is operator-declared, not automatically discovered. A check named in `requiredControlIds` cannot be excluded. Credential readiness requires tokens only for actors used by applicable checks. The SupportDesk fixture uses the four evaluated verdicts. HTTP profiles can declare N/A as described above. Changing applicability changes suite/profile identities and can make earlier runs incompatible.

Comparison requires compatible application, suite, policy, context, adapter, evaluator and evidence identities, plus passing required positive controls. The current connector is `loopback-response-contract/3` with assertion schema `http-contract/4`, which added declared observers and effects. Version 2 (`http-contract/3`) added cookie credentials, `status.in`, `timeoutMs` and the actor-identity rule. An upgrade changes run identities even for an unchanged profile, including `adapterVersion`, `assertionSchemaVersion`, `evaluatorHash`, `suiteHash`, `policyHash`, `profileHash` and `targetConfigHash`. Two saved runs from the same version still compare as before, but a run from an earlier version (`loopback-response-contract/1` or `/2`) never compares with a current one: the pair is incompatible and never reported as fixed. Version 1 evidence predates the identity rule, so a v1 pair can still show a refusal as restored even when the actor's login was never proven. The saved-run gate in the dashboard and `GET /api/runs/<id>/gate` checks a run against the target's current suite, so it refuses v1 runs once the profile is used with the current connector. The regression gate also refuses any HTTP run whose version pair is unsupported or mixed. Rerun the baseline after upgrading. Merely editing a declared build label does not attest that application code changed.

**Repair labels.** A comparison carries its scope's repair label ("Fixed", "Response contracts restored" and the others) only when five things hold: the pair is compatible, every required allowed-use control passed in the candidate (for an HTTP actor, with its login proven), at least one row was restored, no check that passed in the baseline failed in the candidate, and no row is unverified or not applicable. A check that passed or failed and became inconclusive or errored is unverified, so the pair carries no repair label, matching the gate's `comparison-incomplete`. A comparison saved by an earlier build for such a pair still carries the old label, and the gate refuses it as `invalid-comparison-evidence`; recompute it from the two runs. Otherwise:
- A compatible pair whose controls passed but that restored nothing, introduced a new failure or left a row unverified or not applicable reads "No verified repair".
- An incompatible pair, or one whose required controls did not all pass, reads "Unverified changes". A row that went from fail to pass in such a pair counts as unverified (`blocked-by-controls`, `incompatible` or `unverified`), never as fixed.

The label appears in the gate JSON (`comparison.restorationLabel`), the comparison export and the GitHub Action summary. The dashboard does not print it. It shows whether the runs are comparable and whether the allowed-use controls passed, and labels each row's transition, for example "Not verified: controls did not pass", "Not comparable", "Unverified" or "Not credited to the application". Model identity can change the label too (next paragraph). If either run carries an identity that cannot be read, a compatible pair whose controls passed reads "Not attributable to the application: a model identity was present but could not be read". With readable identities on both runs, attribution can replace the label of a compatible pair, "Unverified changes" included, or append a vendor-identity caveat.

**Which model served the runs.** An HTTP app can call a language model, and a model swap can flip checks with no change to the app. When both runs carry a model identity recorded by the model tap (`integrations/model-identity`), the comparison credits each verdict change to the application, the model, both (`confounded`), or neither (`unexplained`, run-to-run variation). A repair keeps its label only when the application is credited. The comparison report, the dashboard and the gate show the attribution; the gate fails such a repair with `repair-not-attributable`. Without identity on both runs the comparison says the model was not recorded, and a verdict change may come from the model. The HTTP connector records the identity when a model tap is configured. Set `SCOPEHAVEN_MODEL_TAP_UPSTREAM` (your local model server, a literal `http://127.0.0.1:PORT` origin) and `SCOPEHAVEN_MODEL_TAP_PORT` (a free loopback port), and point the app's model base URL at `http://127.0.0.1:<that port>`: each run then starts the model tap in Scopehaven's own process, marks it around the assessment and stops it. The app needs no tap control, only that base URL. Add `--require-model-identity` (with `--baseline`) to the gate to make identity mandatory: both runs then need a comparable identity held in Scopehaven's custody (`tap-memory`). A tap log file another process wrote (`SCOPEHAVEN_MODEL_TAP_LOG`) is a reading the app's user can rewrite, so the switch reads it unverified (`subject-writable-custody`). Every model reading, a weights digest included, is what the model server reported; a model server the app controls can report any model. The switch also reads a stored run's identity as the run's file records it: the run digest is a checksum, not a signature, so a baseline edited to the candidate's model and resealed passes; keep the baseline where the application and its authors cannot write it. The tap sees only calls sent to its port, so the policy holds only where routing enforced outside the application leaves that port its only way to the model server. Without a tap setting, runs carry no identity and comparisons read not recorded.

HTTP evidence keeps response metadata and predicate outcomes rather than raw request/response content or resolved credentials. Reproduction needs the original private profile and comparable target state. The profile can contain sensitive request bodies and expected values, so keep it private even when it has only environment-variable references for tokens. Review exported metadata before sharing it. Local integrity checksums are not signed attestations or protection against a malicious process running as the same user.

Evidence storage requires real, owner-controlled directories with permission mode `0700` and bounded owner-controlled regular files with permissions no broader than `0600`. Existing directories with broader permissions are rejected rather than silently made acceptable. History is paginated, with 50 runs per page by default; use **Load older runs** to reach earlier evidence. Storage has bounded file/count/total-size quotas; reaching a quota rejects the new write and preserves existing evidence. Keep one writer process for a given evidence directory; the current quota coordination does not establish cross-process transactions.

## Testing is separate from enforcement and monitoring

Scopehaven runs bounded tests and records observations. Runtime enforcement belongs in the application's backend: authorization, approval validation, cache rules, budgets and idempotency must be implemented at the action boundary. The repaired fixture illustrates those controls; Scopehaven does not install them into your app, intercept all production requests or apply autonomous fixes.

The workbench is also not continuous monitoring, a production alerting service, general prompt-injection protection or a compliance certificate. A successful named regression suite is useful evidence about those scenarios and that context. Operating a real product still requires owner-reviewed integration, trustworthy observations and application-specific repair validation.
