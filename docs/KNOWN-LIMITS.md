# ScopeHaven 0.7.0 (open edition) known limits

This file lists what ScopeHaven 0.7.0 (open edition) does not do, what it withholds, and the limits of what a result can show. Read it before relying on any result. [SUPPORTED-MODES.md](SUPPORTED-MODES.md) lists the tested modes of this release.

This file documents limits. It is not an acceptance of the release. The acceptance rule is that no known unresolved false-clean case exists in the declared tested modes; a limit listed here does not satisfy that condition or excuse a false-clean case found in those modes.

## Withheld from this release

These exist in the repository, but are not part of this release's tested modes. No shipped default enables them. Do not rely on them for results.

| Mode | Why it is withheld | Where it stands |
| --- | --- | --- |
| **Second-opinion extension** (records a verdict beside an external judge) | Its review found known false-clean paths: cases where it can read clean on a run that should not be clean. | Withheld. Its code is in `integrations/evaluation-import/` (`second-opinion.mjs`, `verdict-service.mjs`, `records-desk.mjs`, `promptfoo/`). It can ship only in a later tag, after a new acceptance of that exact combined build. |
| **Generated coverage** (drafting checks automatically from a target) | Not accepted yet. | Its parts in the repository include the `./scopehaven policy statement`, `write-plan` and `write-confirm` subcommands. A later tag, after its own acceptance. Hand-written profiles are the tested path. |
| **Install-state isolation** | Not in this release. | Assessments save their runs in the directory given by `--out` (or the gate directory). `test/install-state-boundary.test.mjs` checks that the owned fixture's CLI assessments write nothing outside that directory; no such whole-workbench check exists yet for the HTTP connector. |

## Operator-forwarded staging

`"targetContext": "operator-forwarded"` (a loopback forwarder in front of your own staging, ONBOARDING, "Testing your own staging environment") was withheld from the tested modes because a known case could pass falsely. It now runs only under an authorization record that names the forwarder's destination (`forwarded.destination`), and a boundary pass in a forwarded run counts toward a clean gate or a clean `assess` exit only when a required control with the same method on the same route passed in the same run (`forwarded-pass-unpaired` otherwise). It is still not part of this release's tested modes. What remains:

- **The row itself.** A forwarder that answers or alters one route (a deny rule on `/admin/*`, credentials stripped on that route) still makes the forbidden row read pass. The gate, the exit code, the comparison (which reads that candidate pass as `unverified`, never restored or preserved) and SARIF (kind `review`) hold it back, through the same-route control: read the gate, not the row.
- **Not caught by any single run:** a wrong upstream serving the same accounts (the control and the forbidden check both reach it), a response cache kept across runs, a gate in front of the app that refuses only signed-out requests while letting signed-in ones through (a signed-in control on the route passes while the signed-out forbidden row is answered by the gate), and a forwarder rule that matches one record id or one account's credential (the pairing is by route shape, so a passing control on another record of the route, or another actor's, pairs it). These are operator trust: the record's destination is the operator's statement of where the forwarder goes, and ScopeHaven cannot check it.
- **Signed-out rows without a control.** A gate or WAF that answers every request with 401 makes a signed-out forbidden row read pass; the same-route rule needs a passing control on that route, so the gate is not clean, but a profile whose signed-out actor has no required control has no other protection.
- **Redirected sign-in** reads fail, not inconclusive (302 is outside the accepted statuses).

Its tested behaviour is pinned in [integrations/forwarded/README.md](../integrations/forwarded/README.md) and `test/authorization.test.mjs`.

## Remote HTTPS targets

`"targetContext": "operator-remote"` reaches an https staging origin directly, only under an authorization record that names that exact origin. It is not part of this release's tested modes. What a run rests on, and what it does not show:

- **DNS pinning, not attestation.** The host is resolved once and every request connects to that address; a later lookup that answers differently stops the run (`remote-dns-changed`). The pin shows that every request went to one address, not which deployment answers there.
- **Non-public addresses** are refused unless the record lists them (`remote-address-refused`). A record that lists one is the operator's statement that the address belongs to the authorized staging.
- **Something in front of the target** (a CDN, WAF or gateway) can answer a route itself, as a forwarder can. The same-route control rule keeps such a pass from a clean gate (`remote-pass-unpaired`), and the comparison reads it `unverified` and SARIF as kind `review`, but the row still reads pass; a gateway serving a cached or wrong upstream for the same accounts, or a rule that matches one record id or one account's credential, is not caught by one run.
- **TLS** is verified for the host against the system trust store and `NODE_EXTRA_CA_CERTS`. Revocation is not checked.
- **The window and the handshake.** The record's window is checked before each DNS check, again after it, immediately before the connection, and once more when the TLS handshake is done, immediately before the request is written. A connection started before `validUntil` can still finish its TLS handshake after it (handshake bytes only, within that check's request timeout: 3 s by default, up to 120 s for a check that declares `timeoutMs`). Its request is then not written: the socket is closed, and the run is refused with nothing saved.
- **IPv6 literal origins** are not supported (a host name whose answer includes IPv6 addresses is).
- **The sequence and conversation commands** stay loopback-only.

Its behaviour is pinned in `test/remote-target.test.mjs`.

## Known open items in the tested modes

These were recorded as follow-ups when the release candidate merged, not as blockers. Until each one is resolved, read the affected results with these limits:

- **A captured value's creator in the baseline.** A comparison does not re-check a baseline row's `creator-login-unproven` precondition. A baseline row that used a captured value whose creator's login was not proven, and that failed, can still count toward a restored row. Before crediting a restored capture-using row, check that the baseline run proved the creator's login at its capturing check.
- **Post-change captures.** The connector's judgement of who created a value captured after a lifecycle change is provisional.

## The examples and the exercise

- **The onboarding examples do not show a verified repair under custody.** In the `sqlite-audit` and `http-audit` examples, the two refund prohibitions read inconclusive on the repaired build (custody), and in `sqlite-snapshot` a snapshot cannot show absence. In the `egress-recorder` example, the per-order clause passes with custody `independent`, but each prohibition's host-wide clause (no payment call at all in its window) is withheld by settlement, because the allowed refund after it makes a payment call that fits it. So all four comparisons carry no repair label (`No verified repair`), and only the `response-only` example reads `Response contracts restored`. `test/onboarding-profiles.test.mjs` pins this.
- **The n8n exercise** (a walkthrough kept outside this repository) is designed to reach a repair label under custody for a write-shaped prohibition: its prohibition's only effect clause is decided by the egress recorder, and no check after it sends to the same host. In one recorded run on 2026-10-10 (macOS; recorded on a private build, not reproducible from this repository) it read `Response contracts restored; backend observed where marked`; no merged test pins that label. It shows that the repaired workflow sent no page for an anonymous call, on one synthetic n8n 2.41.6 instance, for the checks it ran. It does not show that n8n has no other way out, or anything about n8n itself.
- **The exercise's observer needs Docker Desktop for Mac.** The container reaches the recorder on the Mac's loopback at `host.docker.internal`. On Linux, `host.docker.internal` maps to the Docker bridge, which does not reach a service bound to `127.0.0.1`, so the witness never arrives and the prohibition cannot pass there. The exercise was followed end to end on macOS only.
- The exercise's pinned n8n setup and its boot check were first verified on Linux GitHub-hosted runners; the macOS run above is a single recorded check, not a CI result.

## Custody: what a pass can rest on

A pass on a prohibition that rests only on records the application can write (its database, audit endpoint or log) reads **inconclusive** with `subject-writable-custody`. Only observers held outside the application can decide such a pass: in this release's tested modes, the egress recorder, the SMTP sink and, for sequences through the regression gate, the hold gate. Custody `independent` is a classification by observer source, not process or operating-system isolation, and windows built by the evaluator itself (as in the owned refund contract) can carry it.

- No shipped observer held outside the application sees an application's own database writes. A prohibition on a database write can fail (the write is recorded) but not pass on database evidence; it reads inconclusive on a correct build, and the gate is not clean.
- Allowed-use controls keep their verdicts and carry custody as a tag only. A record the application can write may show an allowed action happened when it did not. A control that declares effect clauses must include a positive one (`effect.exists`, or `effect.count` of at least 1); a control with no effect clauses is response only and cannot show the allowed use did anything.
- Runs saved before the custody rule are refused (`effect-pre-custody`, `sequence-pre-custody`). Re-run them.

## Declared channels

A target may declare its channels (`channels` in the profile, [ONBOARDING.md](ONBOARDING.md#connecting-a-local-application-you-own)). With a declaration, a boundary check's absence pass (including any exact count) counts only when every declared channel was observed in that check's window and no declared observer's window carried an effect (committed, or still open) the check's clauses do not select, and the run is a confined launch of a local app whose sinks and allowlisted ports are all declared channels' and whose kernel log was read through with no refused connection; otherwise the report, SARIF, the comparison and the regression gate read it **inconclusive** (`channel-unobserved:<channel>`, `channel-unaccounted:<channel>`, `channels-undeclared`).

- The declaration is the operator's statement. Confinement shows that the launched process tree made no outbound network connection outside its sinks and allowlist; nothing shows that the app wrote no undeclared file, local store or queue, or reached another process by IPC. A channel left out of the declaration that is not a network connection is detected only when a declared observer that no channel lists records an effect through it (`channels-undeclared`), or a listed one records it on no channel's names (`channel-unaccounted:<channel>` for each channel that lists that observer); one no declared observer watches is not detected. A `port` (on a store only) must be the port its pg or mysql snapshot connects to on this machine, checked when the profile is loaded; whatever listens there is reachable whole (every database on that server, say), and what reaches it is seen only as that snapshot sees it.
- Observed means watched, not trusted: a snapshot of the app's own database observes a store channel, but its records are ones the app can write, so a pass that rests on it is only as strong as the app's own records. An outbox or a queue is observed by an audit table the app writes, so it is observed only as completely as the app logs every entry; nothing checks that it does. Every effect that happened or may have (committed, started or unknown) in the window of a declared observer that can observe a channel, listed by a channel or not, complete or not, counts as unaccounted unless a passing `effect.count` or `effect.only` of the check selects it (a bounding clause selects only committed effects, so a started or unknown one always counts), so until per-platform ignore lists land, a background write (an auth audit row, a cron run) withholds the pass as `channel-unaccounted`. An effect no observer records is not seen at all; that is what `channel-unobserved` and confinement are for. A store read from snapshots is net change between two marks, so a write undone within the window is invisible. No shipped observer reads files the app writes, so a files channel always reads unobserved. The sequence CLI's `--files` option (report only) lists what the app added, changed or removed under declared directories between the start and end of a run, in a separate report beside the run; it decides no check and does not make a files channel observed.
- A declared observer that no channel lists counts every row it records in a boundary check's window, the app's own log of the request under test included, as an effect that may have gone by a channel the declaration leaves out (`channels-undeclared`): the rule cannot tell such a row from a stray write. Until per-platform ignore lists land, a profile that declares channels and keeps such an observer (an audit table for its audit-backed checks, say) needs a bounding clause that selects those rows, or its absence passes read inconclusive; a row the app logs as started or unknown no clause selects, so it withholds until those lists land. Likewise a channel watched by observers of two sources (an egress recorder and a provider feed) needs a bounding clause on each source, or the second observer's record of the expected effect reads unaccounted.
- `names` is checked against each observing window's declared vocabulary, not against what the app's database or host list actually holds.
- An allowlisted port that no declared channel names is a way out no sink sees, so an app that reaches a hosted model through a loopback relay gets no absence pass under a declaration until what the relay forwards is observed. The kernel's log of refused connections is a lower bound (macOS can drop a line even after the closing marker), so a single refused attempt that the log dropped is not caught. The confinement record calls that count informative: no row verdict reads it, but this rule, and so the gate, the comparison and the reports, do.
- Three fields of a saved run that no row verdict reads now decide whether an absence pass counts: a window's `coverage`, a window's `events` that no clause of the check reads, and the confinement record's `denials`. The run validator does not re-derive them, so a saved run edited in one of them and resealed (its `evidenceDigest` recomputed) can bring a withheld pass back and is still accepted. Trust a saved run's channel reading as far as the custody of its file; binding the denials at seal time, or signed runs, would close it.
- The rule reads the saved run: the sealed row keeps the status the effect rules decided, and the served dashboard, the compact summary's counts, the gate's counts and the GitHub Action's permission diff show that status. Allowed-use controls and fails are never withheld. A profile without a declaration reads as before, and its report says channels undeclared.

## Observers

- Every observer in the tested modes except the egress recorder, the SMTP sink and the hold gate reads records the application itself writes. They show what the application recorded, as the application recorded it; an application or agent that can edit those records can make them say otherwise.
- **Settlement.** Every observer window ends at its final mark, after the declared `settleMs`. A committed effect that matches a passed `effect.none` or `effect.count` clause but lands after that clause's window closed withholds the pass (`effect-outside-window`); one that also fits an earlier check's selector withholds a boundary check's `effect.exists` or `effect.count` pass (`effect-ambiguous-attribution`). On an allowed-use control that finding stays a tag. It is raised whenever the control's effect also fits an earlier check's selector, a prohibition's actor-wide clause included, so pinning the control's own selector does not remove it, and it does not by itself mean the pass rests on another check's effect: that risk is real only where an earlier check could produce the effect the control pins. Pin each control's positive clause to its own `resource`, run controls before broad prohibitions where the order allows, or, for egress, declare correlation, under which a control's positive pass whose effect carries another check's token is withheld (`effect-correlated-elsewhere`); an observer that could not decide a later window withholds the absence passes it decided (`settlement-unobserved`). An `effect.only` pass is an absence claim too: any later committed effect of an operation it judged, from an observer it reads, withholds it (`effect-outside-window`), whether that effect is expected, allowed or outside its set. A target may declare `"settlement": { "mode": ..., "outsideWindow": "judge" }` (judged late effects, opt-in; refused as `settlement-judge-unused` when no applicable check has an `effect.only` clause). Then each such later effect is counted as the check's own, added to its own window of the same observer, and the clause is judged again: the pass stands, carrying the note `effect-outside-window-judged`, only if it still passes, so a late effect that is allowed, or expected and still within its count, no longer withholds it. A late effect from an observer that is not authoritative or that cannot be placed after its own window, a combined window over the window event cap, and a later window its deciding observer could not cover, still withhold it; an `effect.only` clause that declares `countBy` is judged the same way, worst case: its own window's sends keep their keyed collapse and each later effect is its own application, so a late exact keyed replay of its own send counts again instead of being absorbed (a late keyed release is not built). Under the declaration, a later egress window whose only unattributed sends are allowed and not expected for the clause (the rule for its own window under destination-scoped coverage, below) does not withhold it as unobserved. The declaration changes nothing for `effect.none`, `effect.count` (keyed counts included), `effect.exists` or claim rules, never fails a pass, and reads no time, horizon, token or returned id; validation without the exported suite cannot tell a run whose declaration was added or stripped and its verdicts recomputed to match; the profile digest and the comparison signature still keep the two from comparing. Correlation is by selector, not by request. A target may declare a `correlation` header that egress-recorder destinations record, but the application writes the value (the recorder records any well-formed one, whether or not the connector sent it), so it is the application's own account of causation and never evidence on its own: no selector or pairing pin reads it, it can name a sharper reason for a withheld pass (`effect-correlated-late`, `effect-correlated-late-unsettled`) or withhold one more (`effect-correlated-elsewhere`), and it never releases a withheld pass or fails one. `"settlement": { "mode": "per-check" }` adds a drain barrier after each check with effects or claim rules, which keeps a check's late effects out of the next check's own window, and releases nothing. Several effect checks against one destination in one run still withhold earlier absence passes, with or without correlation, and one run per case (or a pinned `resource` or `actor` on each clause) stays the safe layout. Sends with no token, mail, audit logs, database snapshots and traces carry no token and are settled as before. Effects committed after the final mark are outside every window and every claim: a pass is never a permanent promise that no effect happened later. Background attribution (`"attribution": { "background": [...] }`, opt-in) names a worker's effects by actor, operation and name (and, for an egress send, by the recorder's resource for one declared path: the declaration, not evidence, limits which sends count as background, and the pin trusts the recorder's naming, the declared path prefix after one decode, which a provider normalising dot segments, case or encoded slashes differently may read as another path; a send in a window that flags its path as ambiguous fits every resource pin); a committed effect that fits one is attributed to no check and never decides a clause, so a fail resting only on such effects reads inconclusive (`background-unattributed`) instead of failing. Under attribution a fail no longer always stays a fail. The cost is detection: a source covering a whole host makes every clause about that host unable to fail, and a declared worker's work for a check is never credited. An undeclared background process, a declared worker recorded under another name, and effects after the run-end window are attributed by selector as before. An application that stamps its own effects with a worker's principal can turn its fails into inconclusive results, never into passes. Validation without the exported suite cannot tell a run whose declaration and tags were both stripped and its verdicts recomputed from an undeclared run; the profile digest and the comparison signature still keep the two from comparing.
- **Late effects.** `settleMs` is at most 30000 ms. A target that declares `"timing": { "effectHorizonMs", "runBudgetMs" }` holds each observed check's window for the horizon after its response and starts it only once the horizon has passed since every earlier request, so an effect within the horizon of its request is judged in that request's own window (or a gap), never in a later check's. An effect later than the horizon is outside its check's claim and is settled as above; an application can always delay past any horizon, so declare one above the longest tail you expect. Every request, probe, witness and wait the run starts ends by the declared budget: a check it cannot hold is not sent (`run-budget-exhausted`, inconclusive) and neither is any later one, and a window still held short reads partial (`effect-horizon-truncated`), so absence passes it decided, and earlier boundary checks' absence passes from the same observer, read inconclusive (an allowed-use control keeps its verdict with a tag). Which check the budget cut is the connector's own reading of its clock; saved evidence is unsigned, so a consistent edit can move the cut, and a cut row only ever reads inconclusive. Observer marks and collections already in progress, and the final mark, can run past the budget within each observer's own limits. Without the declaration the settles, barriers and the tail are not bounded by the run budget. With `"lateFails": "withhold"`, a fail that an earlier check's late effect, or the check's own late effect, could explain reads inconclusive (`late-unattributed`) instead of fail, so a forbidden effect that also fits an earlier check's selector is not reported as a fail.
- **Absence** ("this did not happen") is claimed only for an exact action name from an authoritative observer's declared vocabulary, over a complete, settled window. Anything less reads `missing`, `unobservable` or `observer-failure`: inconclusive, never a pass.
- **Selector pairing.** A pinned `actor`, `resource` or `traceId` on an absence clause needs an allowed-use control whose `effect.exists` or `effect.count` shows that selector matching a committed effect in a window of the same observer; otherwise the clause reads `selector-unpaired` or `selector-not-shown-to-match`. Pairing shows the selector selects something in that observer's format, not that the check's own request could cause the effect. A clause that names no actor or resource needs no pair; its scope is everything the observer reports under that name.
- **Allowed-use guard.** An absence that pins nothing pairing reads (no `actor`, `resource`, `traceId`, `fields` or `upstream`), in a boundary check that expects a success status (`status.equals` 200 to 299) and has no positive clause of its own, is vouched for by the observer's vocabulary but shows nothing about the application: one that does nothing, or only says it acted, passes it. (A check that expects a refusal or a redirect is not guarded: a do-nothing application answers success and fails it, and its pass rests on the refusal, which for a credentialed actor counts only beside a passed surface control.) Such a pass reads inconclusive (`allowed-use-not-declared`) unless a required allowed-use control of the same actor passed a positive effect in the run, or a required control of the actor was not sent (which withholds its rows itself). A guard that failed, on a coverage gap too, leaves the pass inconclusive, so identity option B (`restsOn`, below), which can release a row from a control that failed only on a gap, never releases it; the actor's prohibitions also read inconclusive (`control-not-passed`) when the guard fails. `check-config` lists such absences as `unguardedAbsences`. A saved run whose unguarded absence passed (sealed before the guard) is refused as `prohibition-no-allowed-use` when it was sealed under `actor-identity/5` or later; a run saved under `/3` or `/4`, whose pairing is not recomputed, keeps its reading. Re-run a stored baseline that is refused this way. On the SH-default shape (an identity control and one unpinned prohibition) an honest application reads like a do-nothing one, so declare the allowed-use twin. The guard shows the actor did something observable in the run, not that the prohibition's own request could cause the effect.
- **Catalog fingerprint** (`integrations/observers/catalog.mjs`). The database observers read the database's catalog at every mark, and a window whose catalog differs from the run's start, or changed between its marks, reads `schema-drift`, so after a migration nothing passes for the rest of the run. It is read on its own short session, and a read that waits more than a second for a lock the application holds reads `catalog-unreadable`.
  - **It does not see:**
    - role attributes or memberships (`BYPASSRLS`, superuser);
    - session settings such as `session_replication_role`;
    - an object created and dropped inside one window;
    - a relation's own catalog row changed and changed back in the same window as a rewrite of that relation, or a materialized view's;
    - an index dropped and recreated the same inside one window, or a C function's library replaced on disk;
    - a publication's schema membership (PostgreSQL 15), user mappings or access methods.
  - **One window can read `schema-drift` without a schema change:** `VACUUM FULL` or `CLUSTER` on a table with a fast-default column, `REINDEX CONCURRENTLY`, and `ANALYZE` on an inheritance parent left without children.
  - **Across a server major upgrade,** the fingerprint can read as a change.
  - **Lasting reads with no change by the application:**
    - a partitioned table whose partitions differ from one another reads a change when a partition with a combination of its own is added or dropped, and when its first partition is made;
    - TimescaleDB's chunks read as changes.
  - **The catalog's own session** is one more connection per mark. A baseline that cannot be read after a few tries refuses the observer's start.
  - **A partition's owner changed** reads only in its own window: owners are left out of the parent's set, so that a partition made by another role is not a change. On SQLite, the first `ANALYZE`, `VACUUM` and a platform table created during the run make their own window read `schema-drift`. The fingerprint is not yet recorded in the run or the exported suite, and a retest across a migration is not yet flagged: both wait for the connector wiring and the comparison rule.
- `sqlite-snapshot` cannot show absence: its `effect.none` rows read inconclusive even when nothing happened, so it is for detection, not a clean gate. Its events carry no actor.
- `sqlite-snapshot` table size. Until 2026-10-29 a table over 200,000 rows failed every mark (`row-limit`), so a real app's large tables (bookings, ticket legs) could not be observed at all. That limit is gone. A declared table of up to 2,000,000 rows is now read in key order (by its index where it has one) and kept as one 32-byte digest per row plus its key. The cost grows with all the rows you declare, not just the largest table. Every mark reads every declared row: about 5 seconds per mark for 2.3 million rows on a laptop under load, so a run with many checks takes minutes longer. Memory, as peak for one process on a synthetic database shaped like one large test app (2.3 million rows declared, largest table 1,045,726; small writes between marks): 244 MiB at 2 marks, 463 MiB at 20, 708 MiB at 60. Marks share the rows a write did not touch, so an update costs little, but a delete or insert near the start of a table moves every later row and costs more: an estimate of about 47 bytes per row of that table for that mark (calculated from the stored digest, key and offset, not measured on its own). The measured peak with a delete near the start of the largest table at each of 20 marks was 1,136 MiB. The peaks above are the process's maximum resident memory as the operating system reports it, one run each on a shared laptop. The earlier version of this reader peaked at 4,947 MiB per process (median 1,902 MiB, 106 processes) in an internal bench on that app, against 1,025 MiB (median 434 MiB, 163 processes) before large tables could be read at all; that bench sampled each process's resident memory every 5 seconds, so a shorter spike would not show. The current reader has not been re-measured on that bench. One row past 2,000,000 still fails the mark (`row-limit`). A table whose primary key spans columns can be declared with `key: "rowid"`. A `VACUUM` in the window can renumber the rowids of a table without an `INTEGER PRIMARY KEY`, so its rows then read as deleted and inserted. An unlisted table (with `platform` or `ignore`) of over 200,000 rows is read into one scan-order digest, so the same rows in a new order read as changed (never as unchanged). One over 2,000,000 rows cannot be shown unchanged. This is still a full read at each mark, not a delta of only the changed rows: SQLite keeps no change log a copy can read, which is what the change-column mode is for.
- `sqlite-snapshot` compares net state at each mark: a write made and then undone inside one window is not seen, at any table size.
- `pg-snapshot` sees inserts and deletes as net changes; a row added and removed within one window is not seen. The exception is a quiescent window, where no transaction id completed and none was in progress anywhere in the cluster: nothing committed there, so an insert or delete absence is exact. `mysql-snapshot` is net-only by default; its source-checked change-column mode can establish no update to an existing row under its stated rules. Custody still prevents a prohibition pass resting only on either.
- An `http-audit` credential scoped to one tenant can omit a write to another tenant. `check-config` marks the target not ready when a declared audit credential is missing or unusable, but it does not connect, so it cannot tell how much the credential sees.
- The request log observer (`audit-file`) is not used in onboarding: it reads the application's logged answer as the effect in both directions.
- OpenTelemetry traces (`otel`) and MCP logs (`mcp-log`) are outside this release's tested modes, and presence-only: they can fail a check, never pass one.
- The egress recorder and SMTP sink prove the declared route was live for the witness request, not that the application has no other way out. HTTPS through the recorder's proxy mode records the host only, and the window is partial. The SMTP sink offers no STARTTLS. An event name holds at most 128 characters, so a destination host or recipient domain longer than that is no event and leaves the window partial (it is never shortened into another, possibly declared, name); a send to such a host therefore reads missing on a clause it would fail, never pass. Declare names of at most 128 characters: a longer declared name fails every window.
- **Routing declared, not shown exclusive.** Every absence pass an egress recorder or SMTP sink decides (`effect.none`, `effect.count` 0, `effect.only`, a refusal claim) shows that the declared route was live and carried no matching send, not that the application made no such call by another way out: a direct connection, another address, port or unix socket, HTTP/2 with prior knowledge, a client that ignores proxy variables (Node's `http.request` and `fetch` by default, or a `NO_PROXY` entry) or a child process that sends around the route is in no window. Each such pass says so on its row (the report, SARIF, the comparison export and the gate summary) and in the run's limitations, which the compact summary prints. Run the application where the sink is its only way out before reading such a pass as proof that no call was made: on macOS, `./scopehaven assess --confine` does that (below), and its passes read `routing confined` instead. The pass is also bounded in time: it covers sends recorded from its check's start through the run's final mark, and says nothing about one made later (a send timed from the witness can always land after any horizon).
- **Other names of a declared provider** (`egress-recorder/11`). A send to an undeclared host that shares a declared destination's registrable domain (`api-eu.pay.example` beside `api.pay.example`, read with a vendored 55-suffix subset of the Public Suffix List) makes that destination's clauses read missing, never pass, including a fail that rests on no send (`effect.exists`, a count): in a check window as a scoped entry on that destination (`egress-undeclared-sibling-host`), elsewhere for the whole recorder window. So one such background send between checks (an honest app polling `status.pay.example`) withholds earlier absence passes on that recorder until the host is declared, as a destination or as one of the destination's `aliases`. A provider name under another registrable domain (`pay-eu.example`, a CDN name) is no sibling: without a declared alias a send there still passes the prohibition, and only the clause text, which lists the undeclared hosts the recorder's windows saw, shows it. The subset is the list's ICANN section only, so hosts on a shared platform (private-section rules such as `herokuapp.com`, `vercel.app`, `myshopify.com`, `cloudfront.net`, `azurewebsites.net`, `s3.amazonaws.com`) and hosts under a ccTLD suffix outside its 55 rules (`com.co`, `com.pl`, `co.at`, `gob.mx`, `edu.au`) are one family: a send to another tenant there makes the destination's clauses read missing, a fail included. Declare that host as its own destination to separate them. The ICANN-only choice is deliberate, so the same company's other name on a platform (`myapp-eu.herokuapp.com` beside `myapp.herokuapp.com`) is still caught. Since `egress-recorder/13` siblings and declared names are read across a run's egress recorders: a recorder also reads the destinations the run's other recorders declare, so a send through it to one of those hosts (or its alias) fails that destination's clause, a send to its sibling holds it at missing, and its text names the undeclared host. That recorder never captures, keys or forwards such a send, so a clause pinned to body fields or an upstream outcome reads missing on it, never fail; and its silence vouches for nothing it does not declare. A presence-only recorder's sibling send, committed or open, holds no clause: it keeps its own name and that recorder opens no gap, so the destination's absence rests on the authoritative observers (a send to a declared alias is recorded under the destination's name, so it fails the clause, or holds it at missing while its outcome is undecided).
- **Confined launch (`--confine`).** ScopeHaven starts the application under macOS `sandbox-exec` with every outbound connection refused except TCP over IPv4 to the declared egress recorders' and SMTP sinks' ports and a recorded allowlist, for the launched process and every process it starts, and seals a confinement record into the run. Its limits, which the record and the report repeat:
  - Only outbound connections are confined. The profile allows everything else, so a process outside the launched tree that the application reaches by IPC (a mach lookup, a launchd job, another application it opens), by a file it writes, or by an inbound connection is not confined, and what that process sends is outside every window.
  - `sandbox-exec` cannot name one address, and its `localhost` means every IPv4 address of this machine (`127.0.0.1`, each interface address and the wildcard), not loopback alone; measured 2026-10-18: with one allowed port, `127.0.0.1`, the `en0` address and `0.0.0.0` at that port were admitted, while `127.0.0.2`, `[::1]`, `[::ffff:127.0.0.1]`, another port and the gateway got EPERM. A process outside the tree listening on an interface address or the wildcard at a sink port needs no administrator rights and would receive what the application sends there, so ScopeHaven checks that it is itself the only listener on each sink port before the launch, about once a second during the run and at stop, and refuses the run otherwise. A listener that binds and unbinds between two checks, or one run by another user (`lsof` lists only this user's processes), is not caught. `[::1]` at a sink port is refused by the rule, and the self-test checks that; the self-test also records what the rule admitted at an interface address.
  - Name lookups through the system resolver are refused with every other connection, so the application must reach its sinks by a literal loopback address.
  - An allowlisted port is a way out no sink sees. A declared provider-side port (a forward upstream, a request feed or a provider feed) is refused in the allowlist. An application that needs a service off the machine, such as a hosted model, reaches it only through a loopback relay on an allowlisted port (the model tap is one), and whatever that relay forwards is outside every window.
  - macOS only, and not inside another sandbox (the 2026-10-10 observation below). On Linux, or when the application is started by its owner rather than by ScopeHaven, the launch is refused; it never falls back to an unconfined run. A declared container network is not implemented yet.
  - The sink ports are listed about once a second, and the run is refused when no listing arrives for 2.5 times that interval (`sink-port-check-stalled`), so a port watch frozen for less than that still seals as confined: the gap between two listings can stretch to just under 2.5 seconds.
  - A refused launch saves no run. It writes a refusal receipt (`confine-refusal-<time>.json`: the code, the message, the platform) into the evidence directory and exits 2 with the code on stderr, so the attempt is on record beside any declared run made afterwards.
  - A SIGKILL of ScopeHaven cannot be handled: the application, still confined, survives it in its own process group until stopped by hand (Ctrl-C, SIGTERM and SIGHUP do stop it).
  - The application must listen on the target origin and should not need its sinks before the first check: it starts before the sinks do.
  - Kernel denials come from the unified log for information only; no verdict reads them.
- **Mail through the recorder only.** A vendor mail SDK with a compiled-in endpoint ignores base-url routing and sends straight to its provider, so an egress-only mail prohibition passes while the email went out. A run whose routed egress destinations name mail (by host or declared path) and that declares no provider feed and no SMTP sink carries a limitation line saying so. Declare the provider's feed beside the recorder and select both sources, or an SMTP sink for an SMTP client.
- **Declared body fields** (an egress destination's `capture`) are read only on the destination's declared `paths`: from JSON bodies in UTF-8, uncompressed and within `maxBytes`, and from form-encoded bodies only where the destination declares `capture.encodings: ["json", "form"]` (see the form bullet below). A send on another path of the host records `path-undeclared`, and compressed, oversized, duplicate-key or otherwise unreadable bodies leave every declared field unknown, so a `fields` clause over such a send reads missing. A field absent from a body read in full stays unknown unless its pin declares `absent: "fails"`, the operator's statement that the receiver neither defaults nor aliases that field; then the absence reads as not the pinned value only toward a fail (an `effect.exists` or `effect.count`, or a success claim, that would read missing). The operator owns that statement. Such a fail is wrong where the receiver applies a default for the omitted field that equals the pinned value; reads an alias or another naming policy (`amountCents` for `amount_cents`, Pydantic aliases, Jackson `@JsonAlias`, ASP.NET's camelCase policy); reads a key in another letter case (`Amount` for `amount`), which the record does not keep; or when the same pointer typo is in both the capture and the pin, so every send reads absent. A JSON field missing from a request whose URL has a query (some receivers merge the query under the body), or from a body whose root is not a JSON object, is recorded unusable (`absent-query`, `absent-root`) and never decides, declaration or not. A fail decided that way is never the baseline of a credited repair: `compareRuns` reads such a row as unverified. In `effect.only`, a send that no expected selector matches but whose pinned field reads unknown under a `fields`-pinned expected selector holds the clause at missing even when an allowed selector without that pin would fit it, and even when it would be within the expected count (it could be one more of the expected effect, so the allow cannot decide it); a fail from another effect stays a fail. A send that does match another expected selector is allocated as before, so beyond that selector's count it is a fail even when its unknown field might have let it fill the pinned one (a fail-closed limit). A captured string, JSON or form, reads as different from a pinned string only where no common receiver reading makes the two one value: a receiver may read `"105.50"` as `"105.5"`, `"$105.50"` as `"$105.5"`, `"Refund"` or `"refund "` as `"refund"`, or `"yes"` as `"true"`. So such a pin reads missing whenever the application spells the value another way, and an `in` member of another type than the value reads unknown unless it is a string beside a number that no reading makes equal (a string with no digit beside a number other than 0 and 1, or a plain integer of another value). Not modeled: a receiver that reads only a number's prefix of a pinned value that is not itself a number (`"5 USD"` against `"5 EUR"` reads as different), and money written with its currency on the other side (`"USD 105.50"` against `"105.50 USD"`). Captured values are stored in run records and exports.
- **Returned ids** (a forwarded destination's `ids`, proof version 2) decide only `effect.exists` passes that background attribution withheld, and nothing else. They tie a send to the check whose closure holds an id its proven reply minted or names. That is an object, not a cause, so it is used in that one place only: a matched background-possible send tied to the check's own closure keeps the check's `effect.exists` pass. A closure is seeded only by a check's own selected send that carries the check's own correlation token, so without a declared `correlation` header nothing is decided. The application writes that token: an application that stamps the token of the request it is serving onto another job's send (an earlier check's late work run inline during a later request, a pattern of lazy-cron stacks that propagate trace context ambiently; a check sent with a safe method that still writes; an undeclared background source) can still seed this check's closure when that send fits this check's own selectors and no earlier check's. A background job acting on an object the check's own send created can also make that pass. Ties never decide a fail or an absence clause, so background false alarms on absence clauses stay inconclusive. Echo detection catches a minted value the request carried literally, re-cased, or behind JSON, form, percent or base64 encoding, and a minted value that contains a request value or a run of 8 or more request letters and digits; it does not catch every transformation (a value joined from short parts, or reversed); a reference is as good as the upstream's own check of it. A recorder with any incomplete window ties nothing in that run. Closures are per egress recorder, and ids shorter than 8 characters or not strings are never used.
- **Mail recipients** (SMTP sink and provider feed, `src/mail-address.mjs`). A declared address is matched only by a canonical mailbox: a plain printable-ASCII dot-atom local part without `%` or `!`, compared after the envelope rules (case, one trailing dot, the domain's A-label). A recipient written another way (quoted, commented, escaped or non-ASCII), routed through a relay (`%`, `!`), at an odd host (a second trailing dot, an IDNA deviation character), or that could be a declared mailbox under common alias rules (a `+` or `-` subaddress, the local part without dots, or without `.`, `_` and `-` as Proton reads it) leaves the window partial, so a resource-pinned absence reads missing. Such a recipient at any domain makes the window partial, also for checks that pin no address. Declared addresses must be canonical. Provider-specific aliases beyond these (a catch-all, a forwarding rule, another domain the provider maps) are not modelled: pin the domain, not only the address, when they matter.
- **Provider feeds** (`provider-feed`) read a provider stub's or an operator-run adapter's signed `scopehaven-provider-feed/1` feed, never a real provider's API (Postmark, SendGrid, Mailgun and Stripe are not read directly; that needs a provider credential, a held decision). Custody rests on the stub's signing key never being in the application's environment and on the stub creating entries only when it accepts a message. Nothing in a run shows who holds that key, so it rests on the profile's `keySource` declaration (collector `provider-feed/7`): an undeclared source or an adapter that reads the application's own store never supports a pass, and no other observer's silence lifts it: a prohibition or count that would pass reads inconclusive when such a feed sees what it selects, whether the feed decided it or is presence-only (an export file, or an endpoint without a witness), beside an honest feed for another vendor or an SMTP sink too, and so does an `effect.only` pass that judges such a feed. So an honest profile's real stub must declare `"keySource": "stub"` before its feed can support a pass, and an undeclared presence-only feed beside another observer of the same domain holds that absence inconclusive until it declares one. A feed declared `provider` or `stub` whose key the application in fact holds would still be counted as independent (a same-process check of the feed port, or reconciling the feed with a confined egress route, would catch some of these; neither is built). The witness proves this provider's pipe was live, not that the application has no other way to send mail. An export file (`feed.file`) has no signed head and is presence-only: it can show a send, never absence or a count. An export-file entry stamped in the start mark's own millisecond (or by a provider clock behind ScopeHaven's) is read as before the window: the file route compares its stamp to the start mark with no skew, so its outcome reads unknown (`provider-feed-time-outside-window`). A send whose outcome no observer decided, from any window that sees the clause, presence-only included, holds an absence, a count it could still reach and an `effect.only` it is not allowed by at missing, never a pass. So such a send reads inconclusive instead of failing the clause: behind a provider clock that runs behind ScopeHaven's, every forbidden send the file records reads inconclusive unless another observer records it committed. On an endpoint feed with a witness, a send after the witness request is a destination-scoped entry (its recipient domain and address) instead of leaving the whole window partial: only a clause it could fit reads missing, and only once a later window of the feed or the feed's run-end drain follows it. The drain reads to a signed head until nothing accepted is unread and the feed has been quiet for `quietMs`, so a feed the app keeps mailing through at run end is never quiet and its last check's late entries read window-wide. A saved run under `provider-feed/3` to `/7` may carry a drain recorded quiescent just after an entry arrived (a background read could fall between its quiet check and its confirming head; `/8` holds that head to the read it found quiet). A lone late entry whose signed template is a declared label a template pin does not accept is outside that clause; `effect.only` judges every late feed send without narrowing its expected selectors by template; only the check's one late feed entry, a single signed send whose template is a declared label, is covered by an allow it matches template included (collector `provider-feed/4`; a run judged under `/3` keeps reading it missing). A message accepted after the run's final mark is not observed. An operator adapter over a real provider whose records arrive late cannot promise acceptance order, so it must not declare a witness. An entry stamped outside its window is kept with an unknown outcome. On an endpoint feed with a witness the window then reads partial, so an `effect.none` it would fail reads missing, not fail; on a presence-only feed (an export file, or an endpoint without a witness) that unknown send holds the clause at missing, as above, whatever the other observers saw. A feed that declares a template vocabulary reads one more signed field, the provider's id of the stored template it accepted the message with, and stores only the operator label of an id it names exactly: an absent, undeclared or differently written template reads unknown, so a template-pinned clause reads missing on it, never pass. The template is the one the provider was asked to render; what dynamic data put into it is not seen. A provider whose records carry no template (Postmark's Messages API, SES events) can fill it only through a stub or adapter on the send path. Two declared ids for one provider template (an alias and its numeric id) cannot be told apart: declare each template once, in the form the stub records. A template pin must name a declared label (checked when the profile loads). In `effect.only`, a send whose template reads unknown under a template-pinned expected selector holds the clause at missing even when a recipient-only allow would fit it, as for egress body fields. A feed that declares `outcomes` (collector `provider-feed/5`) records the provider's later word on each send (a bounce, a drop, a reversal) only as far as the stub or adapter writes it and only until its later wait (at most `waitMs`, after the final mark) ends: a failure the provider records later (Stripe documents refund failures up to 30 days on), or one an adapter cannot link to the provider's message id (SendGrid's asynchronous bounces without one), is not seen. Under `provider-feed/6` those records only lower a positive pass (`effect.exists`, `effect.count` of at least one, a success claim). A matched send the provider later failed or reversed no longer credits it, and a boundary check reads fail where the rest of its windows decide absence. An unclear horizon, an ambiguous, conflicting or contested send, or an allowed-use control reads inconclusive, unless another send held outside the application still credits the clause and the clause, judged again without the others, passes. A pass means accepted and not failed within the horizon, not delivered: a send with no later word still credits. Absence clauses and `effect.only` count every accepted attempt, so a forbidden send that bounced still fails, and two attempts with one bounced still fail `expected: 1` even if the provider delivered one. A positive clause without a `source` pin is also credited by another observer's copy of the send, so pin `source: "provider-feed"`. A withheld control withholds its actor's other checks and blocks repair labels, as any control that does not pass does.
- **App action logs** (`appLogs`) are the application's own record of what it did, labelled app-reported. They are never custody evidence and never enter a custody decision: an application that writes a false log defeats them, and no cross-check makes a lie visible on a path no independent observer also sees. With `"use": "record"` they decide nothing; they are read and sealed beside each check's observer windows. With `"use": "admission"` the log is also read against the application, and only against it: a clause that did not fail reads **fail** when the log records, as committed, an action of the check's own actor in the check's own window that the clause forbids (finding `app-log-unobserved-admission`; the clause names the log as its source and its custody is the application's). An admission never makes, extends or rescues a pass, and a custody fail stays a custody fail. An admission rests on the application's word against itself: a wrong mapping or an action logged under the checking actor can fail a clause that custody would not, and an application that leaves its forbidden action out of its log is not caught by it. A baseline fail resting only on admissions is never a verified repair; the report labels such a fail `fail (app-admission)` and SARIF carries `scopehavenAdmission`, and an allowed-use control failed this way is not counted as over-blocking. A field read from the line is only as good as its word map: a word mapped to the wrong selector value can admit falsely, and a word the map does not list decides nothing. `distinctFrom` is the operator's statement that an action is never a source's effect; a wrong one can admit an entry the clause would have allowed. A background job's lines are told apart by path only where both its source and the host's rules name exact egress resources, and an entry that fits an earlier check's selector by the same actor is never admitted, so an earlier check whose selector names every message leaves a later check's message unread. `"lines": "per-application"` is the operator's statement: an application that logs one line per attempt without a shared key can be admitted on an honest retry. A background job that logs under the requesting user is told apart only where the check's own window names the job's principal (or custody saw nothing the job could be) and by the check's own correlation token; a job that, in one check's window, logs one send under its own principal and another under the user while inheriting the request's trace context can still be admitted against that request. The check's own sends of the job's shape also count as something the job could be, so a same-shape own line is admitted only in a window where the job also named itself, or where custody saw nothing of that shape. Admission profiles with an actor-pinned background source and no `fields.trace` no longer admit own lines of that source's shape. A late line of an earlier check by the same actor is set aside when that check declares an effect or claim it fits, whatever its token, or, with `fields.trace`, when it carries another check's token; an earlier check that declares neither can leave its late line to be admitted against the next one. Only lines written between a check's request and its observers' end marks, before any witness request, are that check's; a line flushed later is not, and lines written before the run started are never read.
- **Request feeds** (an egress recorder's `requestFeed`, `src/request-feed-rules.mjs`, `egress-recorder/8`) read a provider stub's or an operator-run adapter's signed record of the write requests the provider received, joined to the recorder's own sends by their exact idempotency key. The feed is the provider's account as its adapter writes it, and ScopeHaven holds only its public key: an adapter that signs an entry for a request the provider did not apply, omits one it did, or signs a watermark that is not true is trusted as declared, as with any other declaration. A confirmation needs an applied word for the send's own key, host, route and tenant, read after the run's start read and stamped between the first connected send's arrival and the last one's connection end plus the route's `settleMs` (each widened by `maxSkewMs`); another writer that uses the same exact key on the same host inside that interval (outside ScopeHaven; a profile where a second egress recorder forwards a feed host is refused) is credited as the application, which only key reuse across components can cause. A refutation needs `watermark: true`, the route's documented `settleMs`, the provider's signed watermark at or past every connected send's wall connection end plus `settleMs` plus `maxSkewMs`, the head read at or past its monotonic connection end plus `settleMs`, and a wall-to-monotonic offset that moved by at most `maxSkewMs`, and the key must list at least as many entries as the group has members with a proven reply (a positive control: a feed that omits a request the provider answered is not showing every request it received); a feed that declares no watermark or a route without `settleMs` only confirms. `notApplied` words must be final states: once the watermark passes, a refutation reads a declined word, like the absence of an applied one, as the request's final fate, so a word that can still change (say "processing") must not be declared there; `settleMs` narrows this but does not remove it. The monotonic times are the recorder's own process clock (`performance.now`), which the reader shares because the recorder builds it; they are sealed raw, not as offsets from the run's first mark. A key group decides only as one application's sends: no send to the host whose key could not be read anywhere in the run, the key's first use in the group, no other send under its fold anywhere in the run, one exact key, none in flight at once and one identity, read through the key collapse's own identity and retention function (`src/key-identity.mjs`); a group of same-identity retries is read as one application (the first in-doubt member confirmed and the rest refuted, or all refuted beside a proven applied member), so a plain count reads it once, as the key collapse does. On a host that declares `signing`, a member that arrived more than `dedupeSeconds` after the first is its own application to the collapse, so the request feed leaves its group in doubt. On any other host ScopeHaven knows no key retention: one application per key rests on the provider keeping keys for the whole run, so a provider that forgets a key mid-run and applies a later retry again to the same object is still counted once. Every entry for the key is read together: an applied word and a declined word together, a second object, an unlisted type or word, the key on another feed host, an entry for a case or quote variant of the key (a provider that folds keys could be recording this request under it), a key the feed held before the run, or more than 16 entries for one key leave the group in doubt. Tenancy binds only through a declared `tenant` header (an account header); on a feed without one, an entry that names a tenant leaves its key in doubt, and an adapter that drops the tenant of a multi-tenant provider is an operator error. Credentials are not bound beyond the group's one identity (the credential header is part of the request head). `keyReuse` and `retentionSeconds` are not built: a key reused with a different payload never collapses. A confirmed refund that later fails still passes an agent-write clause (the request feed confirms the application, not its later outcome). The run-end read happens once, after the final mark and the later wait, within a 6 s cap (`REQUEST_FEED_READ_MS`; a timing plan reserves it, and without one the computed budget grows by it); a feed with more entries than that read can fetch, a cut read, a start read that failed, a seq gap, a fault or reads of one recorder that disagree leave every request-feed resolution failed (in doubt). Reading a feed is loopback only in v1: a webhook relay is out (the application holds the webhook secret) and so is polling a real provider over TLS.
- **Read-back** (an egress destination's `readBack`, `src/read-back-rules.mjs`, `egress-recorder/9`) reads the system of record a forwarded destination writes to through its forward upstream on loopback, under a read credential the application never holds, each reply proven under forward proof /2. A refutation or a cap reads a missing new item, so read-back takes either only on a POST route whose host declares `forward.ids.minted`, and it rests on the operator's rule that each application of the write adds exactly one new item to the read collection: a POST that upserts, or one that also adds a second item matching the binding (by the same identity), is a declaration error ScopeHaven cannot detect, and it could refute an applied write or count one application twice; PUT, PATCH and DELETE routes, and hosts without minted ids, only confirm (a second item that does not match the binding, such as an audit entry, leaves the group in doubt). Read-back never leaves applied two members the key collapse reads as one application (one key, one body): on a backend that applied one key twice it decides nothing there, and keyed clauses keep the collapse's own premise that a provider applies a key once. A group with a proven member decides only when each such member's reply minted exactly one recorded id; an id the capture rules redact (a run of exactly nine digits, a card-like run, a long token) or one the request echoed is not recorded, so such a group decides nothing. The reply is the upstream's account under that proof: an upstream that hides an item, lists one that is not there or names a wrong author is trusted as declared, and so is every route guarantee (`consistency`, `completeness`, `removal`, `settleMs` and its `source`, `view`, `deferredFields`, `touches`): a backend whose view hides the write's own item while it shows the control item, or one that removes an item before the reads, can make a write that applied read refuted. A refutation and a cap need every positive control (each proven member's minted item visible, which needs `forward.ids.minted`; an item of the write credential's identity visible in the read or on the declared `control` object), so a view that hides every API-created item, or every item of that identity, refutes nothing. A confirmation rests on items the backend attributes to the write credential's identity (`author` with `serverAssigned`, mapped through `identities`): a writer outside ScopeHaven using the same credential in the window is credited as the write, and so is a backend that assigns authors wrongly; a recorded write under that credential, or under an unknown one, anywhere on the backend in the window leaves the group unconfirmed. Exclusivity and intervening writes are judged over the recorder's own sends only: a write that reaches the system of record around the recorder (another recorder, a direct connection, a job outside the run) is outside them, a profile where a second egress recorder declares a read-back host is refused, and an unlabeled forwarded destination is in every backend. The bound is the route's declared `settleMs` on the recorder's monotonic clock (`performance.now`, which does not advance across a host sleep, so a measured bound is never shorter than the time the backend had); a commit later than the run-end read is not seen, and one between the second read and the run-end read leaves the group in doubt only when nothing later sent to the object explains it. A group is decided only inside one window with every member in it, and its first write waits for the pre-image (at most min(1000 ms, `timeoutMs`), recorded per send); a pre-image within the route's `settleMs` of the recorder's start decides nothing, because writes before the recorder started were not recorded. An exact count is assigned to members only when they share one identity (the same path, query, body and captured fields: no clause can then tell which applied); members of another identity, or a count that is not exact, stay in doubt, and no clause reads a group interval directly in v1 (a count over a group that is not one identity stays missing where the design would have allowed an exact group count). The reads are requests to the system of record: an audit-log or database observer of that backend can record them, under the read credential's principal, in a check's window. A forwarded destination without a `backend` label is in every backend, and its writes declare no settle, so one of them holds every later group of the run in doubt. The control object is read at the recorder's start only on a destination that declares no scope headers (a view key is known only from a write) and always at run end. Completeness is one page in v1 (a snapshot cursor is deferred, offset pagination is never accepted), `readAs` per identity is not built (one read credential per destination), state reads and the duplicate and collateral checks are not built either, and reading a real provider over TLS is out.
- **Forwarded destinations** (an egress destination's `forward`) record the declared loopback upstream's answer, not the real provider's. An outcome decides only with a valid per-request proof under a secret the application is never given (a `proofEnv` that is also a profile credential is refused, but a secret the application can read from its own environment voids the proof), and only for a status the destination lists (applied: 200, 201, 203, 204 or 205 to a method other than GET, HEAD, OPTIONS or TRACE; rejected: a 4xx); everything else reads unknown, so a clause requiring `"applied"` reads missing there. The proof binds the method, path and query, body, content type and status, not `Host` or the other headers, and it shows that whoever answered holds the secret, not that it applied anything: an upstream that answers a listed 2xx without applying the request, or with a failure in its body (the body is never read), reads applied, and a secret leaked to the application voids the proof. A send still in flight at collect leaves the window partial, a forwarded body over 1 MiB gets 413 and is never forwarded, and a send the application makes to the upstream directly, around the recorder, is in no window. Outcome semantics are opt-in (`semantics` with `"upstream": "resolved"`, or an `effect.only` `outcomeJudged` selector) and under a recorder before `egress-recorder/7` read exactly as `"applied"`; from `/7`, the transport record applies on every run with nothing to declare: it refutes an attempt whose TCP connect to the declared upstream never completed, and nothing else; without a request feed or read-back (both below) a reset, a timeout after the connect, a cut reply or a 5xx stays in doubt (inconclusive). The run-end stage reads a later resolver's records after the final mark and before settlement, decides again every row with an opted-in clause that reads an attempt whose records arrived late, seals those records, and the validator binds them before it decides; those records reach only sends in a check's own windows, not sends in the settlement gaps or barriers between checks (those keep the transport record alone), and a lifecycle change check takes none (its post-change checks were gated on its status when it was sent, so its in-doubt attempts stay in doubt). The later resolvers are the request feed and read-back; with neither declared the stage changes nothing. Outcome judging needs the destination's own object declaration (`objectPaths` or `objectFields`): that declaration is operator trust, and a route template that really names a collection is an operator error ScopeHaven cannot detect; it refuses a template with no `{}` segment, unbound identifiers and pins outside `objectFields`. Only a send the recorder marked exact (not a sub-path) and query-free is judged by outcome; there is no declaration that a route's query is not identifying, so any query keeps a send an attempt. Object identity is the route and the body only: tenant and credential headers are not part of it until a later slice adds them (read-back's scope headers and credential digest), so a refused ch_A refund sent under `Stripe-Account: acct_B`, another API key or another `X-Tenant` is set aside like one in the right tenant.
- **Form-encoded body fields** are read only for destinations that declare `capture.encodings: ["json", "form"]`, and only from `application/x-www-form-urlencoded` bodies (no parameter, or `charset=utf-8`) sent as a POST whose target has no query or fragment and with no Cookie header, under strict parsing rules: anything a mainstream server parser could read differently (a repeated key in any letter case, a dot or bracket irregularity, a sparse or mixed index, a push key such as `items[]`) leaves the declared fields unknown. Multipart and compressed bodies stay unknown, a nine-digit form value is redacted, and a form value reads as a number only as a canonical integer of at most 15 digits. A form decimal (one `.` or `,`, at most 15 digits) never matches a number, and it reads as different only toward a fail: when a clause would read missing, a decimal that no common reading makes the pinned number (the separator as a decimal or a group mark, any rounding to the pinned precision and one unit more for floating point) decides it, and the clause reads fail if that decides it fail; otherwise it stays missing. So `amount=105.05` fails an `effect.count` or `effect.exists` pinned to `in: [105.5, "105.5"]`, `amount=105.50` stays missing, and an `effect.none` or an `effect.only` whose allow could absorb the send never passes on it. A string pin is read as a number only beside a number pin of the same value (alone, `"1.5"` may be a version that `"1.05"` spells too), a pinned 0 is never decided (a receiver may default an unparsable value to 0), operands are in the destination's wire units (no cents or other unit scaling is read), and ranges (`gt`, `lt`) on decimals stay unknown. Such a fail is an ordinary fail everywhere, because the decimal is read from the recorder's own capture of the request bytes, never from an application record: a baseline that fails this way and a candidate that passes compare as a repair, a row failing this way in both runs is still-failing (an inconclusive row would have held the restoration label back), and evidence bounds read it as a fail. A non-ASCII value is read only under an explicit `charset=utf-8`, and a value with a control character or edge whitespace never reads as different from a string. Readers follow mainstream server parsers; a receiver that keeps `+` literally or decodes twice may read a `+`-bearing or escaped value differently.
- **Profile size.** A profile lists at most 200 checks (50 required controls), 32 assertions per check (31 response predicates), 32 effect clauses per check and 1000 effect clauses and claim rules in all, and 64 captures; its file is at most 2 MiB. Before anything is sent, the planned requests (one per check, the identity probe points, the cross probes and the witness requests) are counted from the connector's own plan, and a profile planning more than 2500 requests or 1000 cross probes is refused at load, which keeps a run within the 2 MiB saved-run cap (about 600 to 760 bytes per request). A saved run file is still at most 2 MiB (the export and ledger caps are lower), so a very large run is refused at save rather than truncated.
- **Destination-scoped egress coverage**. A late or path-ambiguous send to one declared egress host no longer makes the whole recorder window partial for every other host: it becomes an entry naming its host and resource, and only clauses that entry could fit read missing. A send after the witness request counts as late only when a later check window of the same recorder follows it, or the run-end drain does; a forward still pending at its check's collect counts only when the drain follows it. Otherwise the row is decided again with the window read window-wide. The drain runs only when the target declares attribution or a forwarded destination: before the final mark each egress recorder waits, under one shared cap that never runs past the run deadline less the end-of-run identity probes, until no request is arriving, no record is pending and its quiet period has passed since the latest arrival, forward settle or reply. A saved run under `egress-recorder/3` to `/11` may carry a drain recorded quiescent just after a request arrived (a request read, recorded and answered in the turn before the drain's last look; `/12` checks quiet again there). It follows only when it ended that way with the listener up, the final mark was clear, and the recorder made no close after the first check collect that left a late entry (a failed forward, a destroyed reply or a keep-alive idle close could have swallowed late bytes), so a run whose late work outlives the 5 s keep-alive idle timer gets no follow. A saved run records each drain; the validator checks its shape and that the target declared it, and cannot check that the recorder really was quiet, the same trust boundary as a stored coverage value. Everything that could hide a send to another host stays window-wide: a host mismatch, an address literal, a tunnel, an over-limit or aborted body, an unfinished request, an undeclared host, and any window in which the recorder closed a connection the client had not asked to close (bytes written after such a close are lost unseen). Once its late entries are followed, the window reads complete for a clause none of its entries could fit, whatever the clause's verdict: an `effect.exists` or `effect.count` that would fail on that selector now fails there instead of reading missing (the selected effect itself arriving after the window is the limit every window has; timing `"lateFails": "withhold"` withholds a fail whose selected effect is recorded later). An `effect.only` clause reads such a window complete toward a pass only, and only when every entry has a resource, fits none of its expected selectors (for a `countBy` clause, no entry on the host of an expected selector or on any host that records keys) and definitely fits one of its allowed selectors that pins nothing beyond source, operation, name and resource: a send allowed in any number cannot offend or fill a count, whether or not it happened. An allowed selector that also pins body `fields` lifts only an entry that is exactly one completed after-witness request on a host that declares capture: the recorder keeps that request's own captured record on the entry, and every pinned field must read known and equal on it (unknown, path-undeclared or over a capture cap keeps the window partial; two late requests to one path, a path-ambiguous one or one still in flight carry no record, so a field pin never lifts them). An allowed selector with an actor or upstream pin, or a path-ambiguous entry, keeps the window partial. Each egress and SMTP observer record carries a digest of the recorder files that built its windows and the Node version, so a recorder change compares as a different collector.
- **Keyed retries** (`countBy: "idempotency-key"` on an `effect.count`, or on an `effect.only` for its expected count) apply the declared provider's dedup rule to the bytes the egress sink received; the sink never forwards, so no real provider is observed. One key source is read per destination, a header or a JSON body pointer (an outbox or webhook event id); key expiry and per-endpoint key scoping are not modelled, and anything ambiguous (a changed request under one key, case or quote variants, concurrent sends, a key used before the check's window, or any unreadable key to the host) reads inconclusive. Redeliveries that re-sign (a new timestamp or signature header per attempt) collapse only when those headers are declared `volatile` from the fixed signature list; otherwise they read as changed requests. The recorder does not verify signatures, so declaring a timestamped webhook signature or timestamp header volatile asserts that the destination verifies one signing secret per URL: a send of the same body under the same key, signed under a second secret in another second, reads as a re-signed redelivery of the first. `x-hub-signature`, `x-hub-signature-256`, `x-shopify-hmac-sha256` and `x-twilio-signature` may be declared but have no effect and stay bound: each is a MAC with no timestamp, so a redelivery under the same secret repeats it exactly. A destination may instead declare `idempotency.signing` (verified signature headers, the recommended route when you hold the secrets the destination verifies with): the recorder then verifies each send with HMAC-SHA256 on the raw body bytes it received, and a re-sign collapses only when both sends verify under exactly one and the same declared secret, inside the run window, with timestamps that never go back; on such a destination every collapse, exact replays included, also needs each later send to arrive within the declared `dedupeSeconds` (default 300) of the first send's arrival, or of its signing timestamp when that verified and is earlier, which asserts that the destination keeps a delivered key at least that long and reads the timestamp only for its tolerance check. A verified signature shows which declared secret signed a send, not who signed it (the application holds its own signing secrets). Signature acceptance, the destination's timestamp tolerance and secret rotation are not modelled: a send signed under a rotated secret, under two secrets at once or under an undeclared one reads as its own application (inconclusive), as do Stripe test-mode `v0` signatures, Slack's retry headers and Svix headers sent beside Standard Webhooks ones. A declared secret that is missing or unusable when the run starts only leaves its sends unverified; the run records which declared secrets were usable, never a secret or anything derived from one. On a signing destination any chunked trailer makes a send unverified and is bound; on other keyed destinations a field sent as a chunked trailer is not part of the comparison. On a forwarded destination, a rejected attempt drops out of the count only when its proven status is in the destination's declared `rejected` list (empty by default); any other outcome, unproven forwards included, keeps the count open, and a key stays in flight until its forward settles (for the rest of the run when the forward ends without a complete reply, since the upstream may still apply it). 408, 425, 429 and 499 can never be declared rejected; a provider that answers a listed status such as 402 or 409 after a partial application makes the declaration wrong, so list only statuses the provider documents as applying nothing. `countBy` never decides an absence: `effect.none`, `effect.exists`, claim rules and settlement still count every send, and an `effect.only` with `countBy` drops only an exact keyed replay of a send it judges (any other resend under a reused key keeps it inconclusive).
- **JSON body fields ignore the URL query.** Some receivers (Rails `params`, for example) merge URL query parameters over JSON body parameters, so an app could send `?amount=50000` beside a JSON body whose `amount` reads 5. Form-encoded capture refuses any query; JSON capture does not yet (a follow-up).
- **Claim rules** see only declared field values or declared sentences. Free-text claims decide only on exact declared sentences: a `text` trigger decides only when the whole reply, after NFKC, lowercasing, collapsing whitespace and dropping one trailing `.` or `!`, is exactly one declared sentence, optionally followed by exactly one declared `courtesy` template as a separate sentence. Free text is not parsed; anything else (another word, a greeting first, a second sentence, a control, format or bidi character, a quote mark or apostrophe, a question mark, markdown or another symbol) reads inconclusive. Recall on free text is intentionally minimal, so most honest replies read inconclusive and a claim stated in other words is not seen. What remains: a declared sentence that itself states a plan or a condition decides as declared, and a declared courtesy template is trusted as written. A reading only selects the records requirement; the records decide. Use structured fields where possible (a `field` trigger).
- **Host sleep** (`src/suspend-clock.mjs`). On macOS, Node's clock and timers keep counting while the host sleeps, so a settle, horizon, barrier or final wait that spans a sleep ends at wake with less awake time than it declared. ScopeHaven sees a suspend only on macOS (the CPU tick counters against Node's clock), and only when it is longer than 2 s and than 2% of the sampled interval. Each such wait is owed the awake time the suspend took from it (at most its own length) and is extended by it. Awake time a later sleep takes from the extension, as the awake clock reads it, is owed again, so an extension can last longer than the wait itself: it is bounded only by the room it has, and never runs past the run deadline. Without a timing plan a check's settle or barrier extension first uses only spare budget: it keeps in hand the final settle, the end-of-run identity probes and each later check's request, settle and barrier, but not witness round trips, bracket or lifecycle probes, the run-end drain or the later-outcome wait. A wait still owed time then goes on into the time kept for the later checks (up to the run deadline less the final settle and the end-of-run identity probes). Once it has, that check is the last one sent whether or not the wait was restored, and its windows' record says so (`reserveMs`); a wait restored that way held its declared awake time, so its check is decided on its own windows. The sealed evidence cannot tell a restored wait from a forged one: on a record that carries `reserveMs` the stop no longer binds the shortfall, so dropping `shortMs` and its code and storing the window complete still validates wherever no row's text reads that window's coverage (a presence-only row, or a barrier no settlement verdict reads through). No verdict moves unless the rows are rewritten too, which is a full forgery of unsigned evidence. **A wait the extension could not restore in full reads short:** under a timing plan the horizon, barrier or tail is sealed as the awake time it held, and reads truncated (`effect-horizon-truncated`); without one, the windows it held carry the shortfall and read partial (`host-suspend-wait-short`). Either way no absence passes on the time the sleep took. **A sleep ScopeHaven sees cannot move an earlier request's send into a later check's window** (to within one tick of the awake clock): under a timing plan the lead-in before each check with effects or claim rules is also held in awake time (the horizon since the end of the last request, less the time the host slept), and a check whose lead-in is still short after its extension is not sent, nor is any later check (`run-budget-exhausted`, as when the budget cuts a check; the rows' words say a host sleep cut them, as do those of rows cut after a horizon or barrier a sleep left short). Without a plan, a check whose settle or barrier the spare budget could not restore after a sleep is the last check sent: every later check is not sent and reads inconclusive (`host-suspend-run-stopped`), and the validator recomputes that stop from the sealed windows. A send the sleep displaced past the short check's end marks therefore lands in a gap, where settlement judges it, never in a later check's window. A window a suspend overlapped carries a record of it, which its gap basis names, and so does the text of a row decided on that window's coverage. **A sleep can lose a send even when every wait held:** a request in flight when the host slept, or one an application timer (counting the sleep) gave up on at wake, can fail before any observer sees it, on this host as well as off it. When the application's sends originate off this host (a sink or provider on another machine, or a target reached through a port-forward), sends made and lost there during the sleep are never seen at all. Such a pass rests on what the observers received. An awake clock that has moved during the run but reads no movement at all, or gives no usable reading at either end, across a sampled interval longer than 2 s (a sleep that began the instant a wait did, or one an unreadable CPU counter reading hid) is read as a suspend of that whole interval, so the wait is extended or reads short. **Where the run's timers count sleep but the awake clock has not yet been seen to move across a sampled interval** (no awake clock can be read, it never moves during the run, or each of its early readings has one unusable end, as when the host sleeps during the first request and the first reading at wake fails), no suspend is seen and a wait it cut short would read complete, as before this check existed; the rows decided on that coverage say so. A record whose cause is a clock discontinuity (no elapsed clock: a sleep or a forward wall-clock step) is never counted as lost time, so nothing extends a wait for it, and the row's text says its waits may have held less awake time than declared. Runs sealed before these rules (any evaluator before `3ed66f46`, such as `0f17f616` or `5b42796f`) that sent a check after a wait was left short, or whose rows carry the earlier unchecked or clock-discontinuity note, no longer validate: re-run them. A timed run sealed before these rules on a host that may have slept still validates on its own, because a sleep in a lead-in leaves nothing on record, so it cannot be told apart from a clean run: re-run it too. Runs sealed by `3ed66f46` or `33449ad9` still validate as those evaluators wrote them. Run comparisons already refuse every run sealed before these rules by its evaluator identity.
- **Postgres read-back** (a pg-snapshot table's `readBack` and a check's `readBack` tables, `src/http-readback.mjs`). In a boundary check it can only fail or read inconclusive, never pass: the application can write the database it reads. What a saved run cannot prove, even with its exported suite:
  - A sensitive column that is not revealed is sealed with a salt the observer draws fresh for each run, so neither the profile, the suite nor the validator can recompute its seal. Someone who can edit a saved run can replace a sealed expectation in the record with the seal the row actually holds and relabel the row: an allowed-use control's read-back FAIL then validates as a pass, and a boundary FAIL as inconclusive. An expectation on a column kept in clear is bound to the profile's declared value, and through the suite to the declaration; a sealed one is not.
  - The values the observer read (each row's before and after) are not bound to anything outside the run, as for every observer window: an edited record can move any read-back verdict.
  - The defence is a signed export (`scopehaven export`, under "Evidence and reports"): a run edited after it was exported signed no longer verifies. A signature does not detect an edit made before the export or by the signing key's holder, and an unsigned run (`--unsigned`, or a path that does not sign) has no such defence. Named follow-up: seal sensitive expectations under an operator-held key, so the suite can name each sealed expectation and the validator can refuse one it does not name.
  - The profile hash and the suite hash read a read-back declaration only through its value-free view, so no sealed expected value sits in an unsalted digest. Two profiles that differ only in a sealed expected value share both hashes.
- **pg_net on the wire** (a pg-wal observer's `pgNetWire`, `integrations/observers/pg-net-wire.mjs`; [PG-NET-WIRE.md](../integrations/observers/PG-NET-WIRE.md)). A window counts pg_net's unlogged queue as observed only when it is complete and observer-held. Otherwise an absence on it reads inconclusive (`table-not-in-wal`), as without the wire.
  - Observer-held rests on your `programRoles` declaration: the login roles that can act as a superuser or run a server program are yours, and the application holds none of their passwords. The run reads those roles at each mark and refuses one you did not declare. It also refuses a declared role the application's declared `requestRoles` reach, through `SET ROLE` and `SECURITY DEFINER` calls, any number of steps, and lists the declaration beside the verdict. It cannot see whether the application knows a declared role's password, or reaches a role through a request role you did not declare: on a local Supabase stack the defaults are public, so rotate them first. On stock Supabase apps whose RPC functions `postgres` owns, expect subject-writable.
  - The custody readings (roles, extensions, functions) are taken at the two marks, so a power gained and dropped between them is not seen. To cover that, the roles reading also counts, through everything a login role can act as (`SET ROLE` and `SECURITY DEFINER` calls, any number of steps), every role that could give itself such a path between marks:
    - a role with CREATEROLE on PostgreSQL 15 and earlier;
    - a role with CREATE in the database while a trusted extension outside the no-network list is available, or, on PostgreSQL 16 and later, with `pg_create_subscription`;
    - a member of supautils' privileged role while its extension list names one outside it;
    - a role that can reach any of these powers through `SECURITY DEFINER` calls, directly or through other such functions.

    An existing subscription keeps every window subject-writable.

    A grant made by a declared role, or a way to gain such a power that this list does not name, is a documented limit. supautils is read from the witness's session. If it is not loaded there but some role or database has its own preload or supautils settings, the window is subject-writable. Loading supautils for the application's sessions by any other means takes a superuser, which is a counted role. Also documented limits: trigger and event-trigger functions (EXECUTE is checked when the trigger is created, not when it fires), functions an extension owns, server file writes, `LOAD` from the plugins directory, `ALTER EXTENSION UPDATE` of an allowlisted extension, `GRANT SET ON PARAMETER`, other extension whitelists, and a container sharing the database's PID namespace.
  - Other containers in the database's network namespace are read at the tap's start and at the end probe. One that joins and leaves between them is missed. A process the operator runs in the namespace (`docker exec`) and a background worker loaded through `shared_preload_libraries` (a superuser setting) are outside the readings: they are the operator's to keep out.
  - The tap sees the database container's network only. A service in another container that acts on what it reads from the database, through a channel pg-wal does not decode (a sequence, LISTEN/NOTIFY, a large object, a poll of a table it does not declare), is outside it.
  - A request pg_net sends after the quiet period lands in the next window, which its own start witness bounds. One sent after the run's last window is not observed.

Full observer limits: [ONBOARDING.md](ONBOARDING.md#observe-what-the-app-recorded-the-default) and [integrations/observers/README.md](../integrations/observers/README.md).

## Identity

- Logins are proven per check (identity schema `actor-identity/5`), at the probe points immediately before and after it. An outage strictly between the two points that cover a check, or a session that recovers between them, is not detected.
- A "who am I" route that accepts credentials the protected routes reject (for example one that skips the expiry check) is caught only through a surface control: a required GET allowed-use control on a protected route. A surface control on a public route satisfies the rule without showing the credential was accepted anywhere protected.
- **Rests on (identity option B, `actor-identity/6`).** A boundary check may declare `"restsOn": ["<control id>", ...]` (1 to 8 required allowed-use controls of its own credentialed actor). A failed required control of the actor then withholds it (`control-not-passed`) unless every listed control served its record on the check's route at another record (the served record: its declared 2xx, a clean JSON object, a passing record predicate and its own identity proven at every probe point, beside a declared partner on another record of the route that answered the same keys and a different value on the same field) and passed untagged, every failed required control of the actor served its record the same way and failed only on a positive effect or success claim that coverage gaps alone left missing (or whose pass background attribution withheld), with no matching commit under another actor, no failed control shares a route word, pairing twin, selector name or captured value with the check, and a listed control was sent after the check and after every failed control. Every later identity step still applies. So only a check with no body can rest on controls, in practice a read of another record (`GET /notes/9` beside allowed `GET /notes/3` and `GET /notes/4`); a write with a body, a role boundary with no allowed use on the same route, an uncredentialed actor's check and any failed control that was refused, answered an error or failed a predicate keep the actor-wide withholding. The listed control's served record is taken as showing that the allowed use was accepted; an application that refuses that use but still answers both records in the record's shape with the declared values is not seen. A run that rests on a release validates only against its exported suite (`rests-on-needs-suite`). The route, anchor, served-record and relation rules are in `src/http-rests-on.mjs`. A release never lifts an unpinned absence's own guard: when the actor's guard control failed, on a gap too, that clause still reads inconclusive (`allowed-use-not-declared`, see Allowed-use guard).
- A boundary check whose own predicates and effects passed but whose identity or allowed use was not established reads inconclusive with decision `prohibition-observed-identity-unproven`. It is never a pass and never a repair.
- A status outside 100 to 599 is recorded without a usable status, and the gate refuses the whole run as invalid evidence.
- **Two identities by default** (`src/two-identities.mjs`, docs/ONBOARDING.md). Only `assess` refuses a tenant-scoped target with fewer than two identities in distinct declared tenants: the CLI's (waived by `--single-identity`) and the GitHub Action's assess mode (waived by its `single-identity` input). The Action's gate mode (`baseline-run`), `scopehaven gate`, the dashboard and `runHttpAssessment` run it without refusing and take no waiver, and a run made with `--single-identity` records nothing at rest that says so (only the command's output does). The exported suite's per-check view carries each mirror's `mirrorOf`, and a run validated against it must record exactly those mirrors; a run main recorded before the mirror phase (its mirrors ordinary bracketed checks) validates on its own and against the suite it was recorded with, not against a current suite of a target that declares `"mirrors"`. A generated mirror rests on the profile's declarations: a counterpart declared wrongly is swapped as written, and the route rule trusts the second identity's own applicable declared checks: the routes they are on, and, for a success mirror, the status they expect there. Checks with effect clauses are never mirrored, and every mirror is a read (a refusal of a GET beside both identities' own allowed twins, or a successful GET or read-only POST), so cross-tenant writes, refused or accepted, are mirrored only by hand. Beyond those declarations a mirror assumes the tenants are configured alike, each counterpart pair is two records of the same kind in the same state that no declared check changes (a write that names the record in its path, query or body, in any letter case or as a JSON number, is seen; one that reaches it otherwise, such as an assistant told to act on "my latest order" or a cascade, is not), each declared value is held by its tenant alone (a declared message, invite or share that sends it to the other tenant makes it held by both), a GET changes nothing, and every route in `readOnlyRoutes` is free of side effects (a mirrored assistant turn resends its message under the second identity, so a declared read-only route whose turn acts writes). Mirrors run in a phase of their own, after the declared checks, the final mark, the observers' stop and the identity-refusal probes, with probe points that vouch for mirrors only and a run budget of their own, so they never change a declared row, an identity or a declared wait. They add requests per identity (check-config's `extraRequests`): a per-user rate or question limit without that headroom answers the mirrors, which read inconclusive on 429 or a declared `rateLimitStatuses` answer (FAIL only when that answer names the other tenant's values), and the gate then reads exit 1 where it was clean with mirrors off: `inconclusive-evidence`, with `prohibition-observed-identity-unproven` when the limit runs out between a mirror the app answered and the probe point after it, and `comparison-incomplete` against a baseline. A limit that answers a boundary status (401, 403 or 404) cannot be told from the boundary: a success mirror reads FAIL on it, and a refusal mirror reads it as the boundary's answer, withheld when the limit also refuses the probe points after it. The run-level records still span the mirror phase, as they spanned main's mirrors: an authorization window that ends during it refuses the whole run, declared rows included, and so does a remote target's DNS change during it; a mirror's model call still in flight at the run's end leaves `modelIdentity` unknown. A limit answered with a 200 (a question limit that replies in plain text) is read as the boundary's answer, as it is for any check. Mirrors are opt-in: a target without a `"mirrors"` object gets none and runs exactly its declared checks. The mirror is one more check, judged by the same rules: it never makes the declared check pass, and a passing check with a failing mirror is reported as the mirror's failure, not as a paired finding.

## Responses and checks

- A response pass means the response met its contract. It says nothing about what the application wrote internally, and its row records `backendEvidence: "unavailable"`.
- `json.notContains` is an exact, case-sensitive substring test of one string field. The same value in another field, in different case or encoded passes.
- `json.noForeignValues` sees only values the profile declares in `tenantValues`. The value at the pointer is read as leaves (every string, every object key, and every JSON number as the response body writes it) under an allowlist rule. It fails only on another tenant's identifier written literally (its exact declared characters, spaces at its ends trimmed) as a whole token, in an occurrence that no value of another set of owner tenants overlaps, that the check's own request does not carry. It passes only when every leaf is in the plain form, the response body repeats no member name, and no other tenant's value occurs in any reading, except that under "attributesAlone": "ignore" an attribute seen as a whole token does not prevent a pass. Everything else reads inconclusive, never pass. A response body with a repeated member name in any object reads inconclusive, never pass, because JSON parsing keeps only the last of the repeated values (the connector counts repeats on the raw body); another tenant's identifier written literally in the parsed value still fails. The connector also keeps each JSON number's source text, so 7.50, 731e-400 and 12345678901234567 are read with the digits the body shows; a transport that reports neither, and a body nested too deeply for the connector's second parse, read inconclusive unless another tenant's identifier is written literally as a whole token, which still fails. The plain form: ASCII letters and digits, the other letters and decimal digits that occur in some declared value (only those that Unicode assigns to one of these scripts: Latin, Greek, Cyrillic, Armenian, Georgian, Cherokee, Hebrew, Arabic, Syriac, Thaana, NKo, Han with kana and Bopomofo, Hangul, Thai, Lao, Khmer, Myanmar, Devanagari, Bengali, Gurmukhi, Gujarati, Oriya, Tamil, Telugu, Kannada, Malayalam, Sinhala and Ethiopic; never Common, Inherited or default-ignorable ones; and in a script with letter case only letters that have an uppercase or lowercase partner), U+0020 spaces, U+000A line feeds and the punctuation . , ; : ! ? ' " ( ) - / @ # $, in a leaf that Unicode NFKC normalization leaves unchanged and that does not hold ASCII digits beside other decimal digits. An object member name that is an array index (0 to 4294967294, written without leading zeros) is outside the form when the object has another member, since JavaScript lists such names first and the body's order of the members is not known. Across the whole value at the pointer, every letter and every number character other than an ASCII digit, in every leaf and in every other tenant's declared values, must be of one script group (Han, kana and Bopomofo count as one; a script not listed counts as a group of its own); otherwise every leaf holding such a character is outside the form, since a reply in one script can show another script's value in look-alike letters. Likewise, when right-to-left letters or digits occur anywhere at the pointer together with left-to-right letters or digits (ASCII digits are left-to-right), or the response body holds anywhere a character of the right-to-left blocks (U+0590 to U+08FF, U+FB1D to U+FDFF, U+FE70 to U+FEFF, U+10800 to U+10FFF, U+1E800 to U+1EFFF) or a bidi control, every leaf at the pointer holding a letter or digit of either direction is outside the form, since the display order of one leaf depends on the text around it. Any escape (a backslash, a percent sign, an HTML entity), any markup character (< > * _ ~ `), any control, format, bidi, default-ignorable or combining character, a compatibility form such as fullwidth letters, any letter or digit no declared value uses (small capitals, IPA letters, spacing modifier letters, letters drawn like punctuation, the katakana long vowel mark, the Arabic tatweel), letters or numbers of two script groups (in the reply, or the reply's and another tenant's values), a tab, a carriage return and any other symbol puts its leaf outside the form, and such a leaf reads inconclusive unless another tenant's identifier is written literally in it (accepted recall loss: replies with curly quotes, markdown, emoji, accents written as combining marks, Indic and Thai text, any accented or non-Latin letter that no declared value uses, katakana words with the long vowel mark, a leaf that mixes scripts, such as a Cyrillic name in an English sentence, and every reply with a letter when other tenants' values use another script group or more than one, such as a Latin reply when another tenant holds a Cyrillic name, read inconclusive). The loose reading keeps only letters and number characters, each after Unicode NFKD decomposition with every combining mark removed, before and after a full case fold (the capital and the small sharp s both read ss), with ligatures and letters with a stroke or bar read as their base letters from a fixed list in src/tenant-values.mjs (æ ae, œ oe, þ th, ø o, ł l, đ d, ħ h, ƶ z, ғ г and others), Hebrew final letters as their base letters, the Persian yeh and keheh, the alef maksura and the teh marbuta as yeh, kaf, yeh and heh, katakana as hiragana, an iteration mark (々, ゝ) as the letter right before it (one with no letter right before it in its leaf reads as nothing and puts the leaf outside the form), the ideographic zero as 0 and every decimal digit as its ASCII digit; a declared value with ä, ö, ü, å or ø is also read with those letters spelled ae, oe, ue, aa and oe, and one with ae, oe, ue or aa also with those written a, o, u and a; a value seen there anywhere but inside its own whole literal occurrence (in another letter case, with its accents removed, with other spacing, punctuation or line breaks between its characters, or glued to more letters or digits) reads inconclusive, never fail. The joined readings are the loose reading with the leaf boundaries removed, in order (array items in order, each object key before its value, object members in JavaScript property order), once over every leaf and once over the leaves that are not object keys; a value seen there across a leaf boundary (["REF-", "5150"], {"REF": 5150}, {"first": "Grace", "last": "Hopper"}) reads inconclusive, never pass. The number readings are the loose reading and the joined readings with the zeros at both ends of every run of ASCII digits removed (a run of zeros vanishes); a value with a digit, read the same way, seen there reads inconclusive, never pass, unless an end of it that is a digit meets, past any zeros written right beside it, another digit written right beside it, so 17310 and 7.51 are other numbers than 731 and 7.5 ("Order 731", "Order 731 2 items" or "Order 7.31e2" for "00731", "7.5" for "7.50", "INV-42" for "INV-0042", "1,000" for "1000.00"; accepted recall loss: 7310 reads like 731, 1, 10, 0.1 and 100.00 read alike, and "ABC" reads like "ABC-000"; a value made of zeros only, such as "0.00", has no number reading). A token edge is open at a leaf edge, beside a space or line feed, or beside a run of the listed punctuation that ends at a leaf edge, space or line feed. No edge closes: any other neighbor is glue and reads inconclusive (a letter or digit of any case, a character outside the form, or punctuation that meets a letter or digit: "orderREF-5150", "REF-51501", "REF-5150-B", "/orders/REF-5150", "myjdoe42" for "jdoe42"; accepted recall loss: a longer word that holds a value, such as "Hoppers", "Anne", "annual" or "Joanna" for "Hopper" and "Ann", reads inconclusive too). A value whose first or last character is not a letter or digit ("@example.net") has an open edge there unless its neighbor is a character other than a letter, digit, space, line feed or listed punctuation. Also inconclusive: a value the actor's tenant shares with another tenant, an identifier two or more other tenants share (an attribute that only other tenants share counts as an attribute), a value seen only in occurrences that overlap an occurrence of a value with another set of owner tenants (the actor's own "Grace Hopper" holding another tenant's "Hopper", or another tenant's "5150" glued inside the actor's "REF-5150"), another tenant's identifier whose loose reading occurs in the request's decoded path, query, body keys, strings or numbers (an echo: "I can't share REF-5150" and a reply that returns that record cannot be told apart), a leaf that is a number (a JSON number, or a string of decimal text alone) equal to a declared decimal value written differently, leading zeros included ("7.50" for 7.5, "02134" for 2134, the string "7.5" for "7.50"). Declared values with the same loose reading are one value, and it is an identifier when any tenant declares it as one, so the result does not depend on declaration order. A declared value that Unicode NFKC normalization changes (decomposed accents, compatibility forms) is refused. Not seen: a value the profile did not declare, a paraphrase, a value spelled out or written in another spelling than these readings give ("Mohammed" for "Muhammad"), a value split across leaves in another order or with another leaf between its parts ({"num": 5150, "prefix": "REF-"}), a number rounded to other digits ("7.49" for "7.5"), a value written in look-alike letters of its own script group, a value with a letter replaced by another letter of the plain form (an accented letter some declared value uses, or an ASCII look-alike such as "O" for "0"), a number a renderer computes, such as the item numbers of a Markdown ordered list, and a display that sets a right-to-left direction itself. Attributes seen as whole tokens on their own read inconclusive by default, or are ignored under "attributesAlone": "ignore"; an attribute seen only partially, or only as a number written differently, reads inconclusive under either policy. The scan reads at most 131072 characters (524288 in its loose reading) and judges at most 262144 matches; past either bound it reads inconclusive. Capture placeholders are filled before the echo check, so a captured id the request sent is an echo. The evidence names which bound stopped a scan.
- A JSON assertion on a response that is not complete, valid JSON reads inconclusive (`Complete valid JSON unavailable`), never pass.
- There is no "contains" predicate for free text. An allowed-use control on a model answer must assert a structured field, or it cannot rule out an assistant that refuses everything.
- A model's reply can differ between runs. One passing turn is one sample; a failing turn is a confirmed failure in that run.
- Requests run once, with no redirects or retries. POST, PUT, PATCH and DELETE change data, and a timeout does not undo them. A DELETE, PUT or PATCH can use up or alter the record the next run probes. The connector does not reset the application between checks or runs.
- Defaults bound request bodies to 8 KiB, responses to 64 KiB, each request to three seconds and each run to sixty seconds (plus declared `timeoutMs`, up to 600000 ms per profile).
- N/A is never a pass, and the gate rejects it.
- **Signed webhooks** (`webhook` on a check, `src/webhook-driver.mjs`) use each provider's documented algorithm with a synthetic key the profile names. No provider is contacted. A passing signed check shows only that the application accepted a request signed with the key it was given. It does not show that the application would accept the provider's own deliveries: the provider's configured URL, proxy headers and source-address rules are not exercised. Twilio is signed over the declared or origin URL in a URL parser's form. Twilio GET webhooks, Stripe test-mode `v0` and rotation (several `v1`) signatures are not built, and content types carry no charset. The run records each key's variable and a salted digest, never the key, but a guessable key could be confirmed against its digest. The egress recorder verifies only the HMAC-SHA256 schemes of an application's outbound sends (`idempotency.signing`); inbound signatures are the application's to check. A Telnyx re-sign and a Twilio signature under another key stay bound under keyed retries (see that paragraph). Which checks declared a webhook, and what each declared, is known only from the exported suite: in a row whose seal was then recomputed, a run validated without it cannot tell whether the row's webhook record, or its absence, matches what its check declared (a record removed, added, moved between rows or keys, switched between signed and omitted, or changed in what it declares), so validate a saved run against its suite.

## Lifecycle, captures and constrained effects

- **Lifecycle** tests the declared policy that a changed user's pre-change credential is refused. The change may be sent by another actor or, as a self-change, by the changed user (signing out, revoking their own key; never a GET, since required GETs are re-sent at every probe point). A self-change has no probe point after it, so its login rests on the user's pre-change proof, and a sign-out route that answers success without accepting the credential still confirms the change. An access that ends by time (an entitlement past its period, a token at expiry) is not a lifecycle change: no request makes it, and this field does not test it. Checks by other actors can run between the user's last probe point and her self-change, and the self-change row's own acceptance of her credential is proven only by the predicate you give it: a change one of those checks made would be read as the self-change's, so give the self-change a predicate only an accepted credential produces, or keep other actors' checks out of that gap. It does not test work already in flight or queued when the change happens, and it does not test an application whose sessions stay valid until they expire. If the change check did not pass, no post-change check is sent and each reads `change-not-confirmed`. When background attribution withholds the change check's own pass after the run (its effect could be a declared background source's), the change is not attributed: the run records it unconfirmed and no post-change check already sent can pass (`change-not-attributed`): one whose refusal held reads inconclusive, and a credential that still works still fails.
- **Captures** keep a digest of each captured value, never the value. The creator is the capturing check's declared actor; the application's own record of who created the resource is not read. Observer events can still carry a captured id, so keep saved runs as private as the profile.
- **`effect.only`** covers only the operations and names its observers report. In a prohibition it can pass only when every deciding observer is held outside the application (a request-path one or a provider feed); a database, audit or log observer among them holds it at inconclusive. It does not show that the expected effect happened: pair it with an `effect.count` control.

## Comparisons

- Runs compare only when application, suite, policy, context, adapter, evaluator and evidence identities match and every required control passed. Changing a check, its applicability, its observers or the connector version makes earlier runs incompatible: rerun the baseline.
- **Model identity.** Without a model tap configured, a run records no model identity, every comparison of connector runs reads the model as not recorded, and a verdict change may come from a model change. With a tap, the identity is what the model server reported; a model server the application controls can report any model. The tap sees only calls sent to its port. `--require-model-identity` accepts only an identity held in Scopehaven's custody (`tap-memory`); a stored run's identity is protected by a checksum, not a signature, so keep baselines where the application cannot write them.
- A repair label requires every condition in [Reading results honestly](ONBOARDING.md#reading-results-honestly). An HTTP fail-to-pass transition is a restored response contract, with backend observation only for rows marked observed; it is not a certified backend fix.

## Sequences and the owned refund contract

- **Sequences through the regression gate** judge status rows and effect assertions over the observers a sequence declares. A status row shows what the application answered, not what it did. A row that would pass on a 401 or 403 counts only when an earlier request by the same actor in the same run got a complete 2xx answer; otherwise it reads inconclusive. Runs of a different sequence evaluator never compare.
- **Declared refusals at the hold gate** (`rules[].rejected`, opt-in): a call answered in full with a status its rule lists reads denied and leaves its window complete, so a held tool call that the tool service refuses can pass an `effect.none`. That pass rests on the operator's declaration that the upstream answers those statuses only when it did not apply the call. The gate sees the status, not what the upstream did, and nothing proves it, as a proof does for a forwarded egress destination: an upstream that applies a call and still answers a listed status passes. Do not declare `rejected` for an upstream inside the application's trust domain (the same codebase or deployment, or one that shares its credentials or data). There the application chooses the status, and the row still reads custody `independent`, because custody follows the gate's record, not who chose the answer. Without a declaration, any answer other than 2xx keeps the window partial and the row inconclusive, as before. See [integrations/sequences/README.md](../integrations/sequences/README.md#declared-refusals-at-the-hold-gate-rulesrejected).
- **The owned refund lifecycle contract** (`refund-clean` and its variants) is an owned synthetic workflow, not a profile for your application. Acceptance timing is an application ledger control only, baseline comparison for refund results is unsupported, and no real provider, settlement or production claim follows. See [integrations/temporal-contracts/README.md](../integrations/temporal-contracts/README.md).

## Evidence and reports

- Saved runs are internally consistent but not signed. Someone who can edit an evidence directory can forge a consistent record. Keep evidence directories private and owner-only, with one writer process per directory.
- Exports keep metadata and predicate outcomes, not raw bodies or credentials, but they describe your application. Review them before sharing. Local checksums are not signatures.
- **Signing.** Exports and evidence packs are signed by default with the operator's local Ed25519 key, into `NAME.dsse.json` beside each file (`--unsigned` skips it for a single export; a pack is always signed). That signature shows only that whoever holds the key produced these bytes, so a pack signed on the application owner's machine is self-attested. ScopeHaven can add a second signature: a countersignature over hashes only, with a key published at `https://scopehaven.dev/.well-known/scopehaven-keys.json`, and an RFC 3161 timestamp from freetsa.org ([SIGNING-KEYS.md](SIGNING-KEYS.md)). Signing, the countersignature and both verifiers are available but not yet in this release's tested modes.
- **Signed exports.** `scopehaven export` signs each export into `NAME.dsse.json` beside it with a local Ed25519 key in `~/.config/scopehaven/signing` (the first export creates it; `--signing-key-dir ABS` uses another directory; `--unsigned` opts out). Verify with `python3 integrations/attest/verify_envelope.py --key DIR/scopehaven-signing-key.pub.pem --envelope NAME.dsse.json --dir DIR`, or `node integrations/attest/cli.mjs verify` with the same arguments. A signature shows the key holder produced these exact bytes, not that the results are correct. The operator's key is protected by file permissions only, with no rotation or revocation, and trust in it comes from confirming its key id out of band, or from a ScopeHaven countersignature that names it ([integrations/attest/README.md](../integrations/attest/README.md#limits)). A key or directory with a wrong mode or owner is refused (`signing-key-unsafe`), never repaired. A signed export's file name may use only letters, digits, `.`, `_` and `-`. The GitHub Action exports unsigned, because report-only marks `report.html`, `comparison.html` and `scopehaven.sarif` in place after export; it has no signing option. The scheduled drift runner (`integrations/schedule/run-local.sh`) also exports unsigned, dashboard downloads are not signed, and library callers of `exportRun()` sign only when asked.
- **Payments exports.** `./scopehaven payments export` signs as `scopehaven export` does. A payments run's JSON export (`--format json`, without `--baseline`) is signed with the run's identity: id, schema, times, target, application, build, pack digest and the run's own checksum. Both attest verifiers recompute that identity from the run file, after the checks of the pack's own reader. The HTML, SARIF and comparison exports are covered by their digest only. The payments run's own `sha256` is an unkeyed checksum: a forger who edits a run consistently and recomputes it is not stopped by the export or by the verifiers. Envelopes signed before payments runs had identities name none and still verify when the run passes those checks, with the run listed in `unclaimedRuns`. An envelope that names a payments identity needs an attest verifier that knows payments run identities (this release's does): an earlier one rejects it with `run-identity-mismatch`, as if it were edited.
- **Evidence packs.** An evidence pack's folder envelope (`evidence-pack.dsse.json`) covers the files it names; a file added later is not covered. The verifier copy and the public key in the folder came from the sender; trust rests on the key id the verifiers print matching the id the signer gave over another channel. The operator signature's time is the signer's clock. A countersigned pack also carries `evidence-pack.countersign.dsse.json` and `evidence-pack.countersign.tsr` beside the folder envelope, which does not name them. The verifiers check both against the published key set, and the timestamp gives a time neither signer controls. A countersignature shows that ScopeHaven's key signed those hashes for the named licence before that time. It does not show that ScopeHaven ran the checks, or that a run was not edited before it was packed. In this build countersigning is a local CLI run by ScopeHaven with an interim key and no licence check ([SIGNING-KEYS.md](SIGNING-KEYS.md#limits)). A pack is always signed (it has no `--unsigned`) and takes no `--standards-file`, so its SARIF has no tags from your own map; export that SARIF on its own. A refused or failed pack leaves nothing at or beside `--out` (a first use may still have made the signing key in its key directory), but a process killed mid-way can leave a hidden `.<uuid>.evidence-pack.tmp` folder beside `--out` (and, killed between the last two steps, an empty folder at `--out`), never a partial pack.
- **Coverage in exports.** Every HTML report and comparison export has a "Coverage and residual" section. From the run alone it lists, per actor with a boundary check, the required allowed-use controls that ran as that actor; an actor with none is shown in red, because a fix that refuses that actor everything would read as a fix (the comparison JSON carries `coverage.actorsWithoutAllowedUse`, SARIF `runs[0].properties.coverage.actorsWithoutAllowedUse`). A row that records no single actor is counted, not placed. The full pre-run coverage report (`integrations/coverage-report`) needs the operator's inventory, stated contract and targets manifest: `./scopehaven export ... --coverage-inventory ABS --coverage-contract ABS --coverage-targets ABS` (HTML report and comparison exports). It says which cells have a check, not what the application does. Coverage is presentation only: it feeds no verdict, count, comparison, gate outcome or hash. The compact summary keeps its "Residual" heading.
- SARIF and comparison exports do not mark which rows were backend observed; keep the single-run JSON export for that.
- **Claim types** (exact, risk-bound, descriptive) are a reading of the saved run: they say what a verdict rests on, not whether its record is accurate. An exact response row is exact about the response only. A fail is exact on an effect clause only when a record held outside the app shows the forbidden effect; a fail because a required effect did not appear reads the declared channels the way an absence pass does (risk-bound when they are undeclared). Evidence origins that record no custody per clause (the owned fixtures) read risk-bound whenever they decide a row, and a conversation row is risk-bound whichever way it went, since its row does not say whether a reply or a state the app serves decided it. The served dashboard page does not show claim types or the residual (its report download does), and the JSON export (the sealed record) carries neither: use the HTML report, SARIF, the comparison exports, the compact summary or `--format residual`.
- **The residual** lists inconclusive checks by reason code (custody, settlement, pairing and attribution tags, the row's decision, each window that ran partial or failed, and the channel and forwarded readings); a check with none of them reads `unverified`, with its assertion names in the full report and SARIF. Identity, precondition and later-outcome reasons and a sequence row's own verdict are named; a reason recorded only in free text elsewhere is not, and the compact summary prints a reason only when it is code-shaped. The residual reads observers for HTTP and sequence runs only; for other origins it says they are not read. "Observers not running or incomplete" lists, per declared observer, the checks where it could not report, had no window or ran a partial window. A sequence's residual says it declares no channels; other non-HTTP origins state nothing about channels.
- The compact summary is not anonymized and is not a standalone record; it accompanies the full report and run JSON.
- Browser print layout, page counts and the file mode of a saved PDF have not been verified for this release. Scopehaven has no PDF helper.

## The zero-egress script

[DATA-HANDLING.md](DATA-HANDLING.md#how-this-is-checked) describes `integrations/data-handling/zero-egress.mjs` as running every available built-in target and the test suite with outbound network denied except loopback. That sheet is generated from `integrations/data-handling/render.mjs` and does not carry the limit below. The script is outside this release's tested modes.

- **A bare zero-egress pass is not evidence** (open item ZERO-EGRESS-UNEXECUTED-SUCCESS). The script records each command's exit code (`zero-egress.mjs:66`), but its verdict and its own exit code come only from logged non-loopback attempts and kernel denials (`zero-egress.mjs:94`, `:98`). A command that failed before it ran therefore still yields `no-non-loopback-connections` and exit `0`. It also reads clean when `./scopehaven assess --list` reports no available target (`:72`, nothing is assessed), and `--skip-suite` (`:74`) leaves the test suite out.
- **Observed on 2026-10-10 (macOS, on a private build; not reproducible from this repository).** Started inside another macOS sandbox, every child stopped at `sandbox-exec: sandbox_apply: Operation not permitted` with exit `71`: all 17 listed assessments exited `71`, the connection log had 0 entries, and the script still printed `no-non-loopback-connections` and exited `0`.
- **What to check instead.** Read `ZERO-EGRESS.json` in the `--out` directory, not the exit code or the last line:
  - `targets` lists the targets you meant to cover;
  - every entry in `commands` has exit `0` or `1` (an assessment exits `1` when its target has failing or inconclusive checks, `src/cli.mjs:41`). Exit `2` is a setup error (`src/cli.mjs:47`), and any other code, such as `71`, means the command never ran. Treat any such entry as no evidence for that target;
  - `test suite` is in `commands` unless you passed `--skip-suite`, and its log in `logs/` shows the run's final counts;
  - `evidence/runs/` holds one saved run per assessment that completed;
  - `nodeLog.entries` is above 0. Assessments make loopback connections, and the logger records those too, so 0 means it saw nothing run.
- Run it from a normal shell, not inside another sandbox. On Linux it uses `unshare` and reads no kernel log; only Node processes that loaded its logger are recorded.

## Scope of the product

- Scopehaven connects only to `http://127.0.0.1:<port>`, except an `operator-remote` target, which it reaches over HTTPS at the one origin its authorization record names, resolving that host to a pinned address. It never follows redirects or uploads anything. It does not test hosted vendor services or production.
- It is a test workbench, not runtime enforcement, monitoring, alerting, general prompt-injection protection or a compliance certificate. It does not install controls in your application or apply fixes.
- The GitHub Action has run on GitHub only in this repository's own workflow, against the owned synthetic lab, and backend observers are not part of it; its README lists what was and was not verified.
- Windows is not verified. The project-local runtime path the launcher looks for is the macOS Apple Silicon build; other platforms select Node with `SCOPEHAVEN_NODE` or `PATH`.
