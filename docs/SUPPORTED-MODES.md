# ScopeHaven 0.7.0 (open edition) supported modes

This file lists the tested modes of ScopeHaven 0.7.0 (open edition), all through the shipped CLI and regression gate. Anything not listed here is outside the tested modes of this release, whatever else is in the repository. [KNOWN-LIMITS.md](KNOWN-LIMITS.md) gives the limits of each mode and what is withheld.

## Tested modes

| Mode | Entry point | What it gives you | Main limits |
| --- | --- | --- | --- |
| Zero-dependency launcher | `./scopehaven doctor`, `check-config`, `assess --list` | Node 22.23.4+ or 24.22.1+ check and source, local readiness, configuration validation. Installs and contacts nothing. | `connectionTested` is always `false`; readiness is not a passed check. A clean clone has no runtime until you add one ([DEPENDENCIES.md](DEPENDENCIES.md#runtime)). |
| Owned synthetic fixture | `./scopehaven assess --target demo-vulnerable` and `demo-repaired`; `./scopehaven gate-demo` | A failing and a repaired build of Scopehaven's own synthetic support app over loopback, with its own backend observer, for rehearsal (suite 2.3.0, 44 checks). | Synthetic, deterministic, no model. Not evidence about any other application. |
| Authorization record | `--authorization RECORD` on assess, the gate and sequences; the Action's `authorization` input; `SCOPEHAVEN_AUTHORIZATION_FILE` for the dashboard; `node integrations/roe/cli.mjs seal` and `check` | ScopeHaven won't run a configured target without a matching authorization record: the target, every endpoint the run contacts, every credentialed test account and a validity window, checked before any request. The run and its exports carry the record's id and checksum. | The checksum is unkeyed, not a signature; the record is the operator's statement (docs/RULES-OF-ENGAGEMENT.md). The window is checked at the start, before every request and observer call, and once more before the run is saved; a run whose window ends before it is saved is stopped and not saved. |
| HTTP connector on a local application | `./scopehaven assess --config PROFILE --target ID --authorization RECORD` | GET, POST, PUT, PATCH and DELETE checks against a literal `http://127.0.0.1:<port>` origin: one status assertion per check, JSON predicates, bearer, cookie or header-key (`credentialHeader`) credentials, per-check `timeoutMs`, operator-declared N/A. | A response pass says nothing about internal effects. Writes run once and are not undone. |
| Identity proof, per check | Required "who am I" controls and surface controls in the profile | Each credentialed actor's login is proven at the probe points before and after each of its checks, and refused without a credential, with a random one and with every other actor's (`actor-identity/5`). An unproven login turns the covered checks inconclusive; a boundary check that behaved as required but whose identity was not established reads `prohibition-observed-identity-unproven`. | Proven at the probe points only. |
| Allowed-use controls | `requiredControlIds` with `severity: "control"` | A repair is credited only when every required control passes in the retest, so blocking everything is not a repair. | As broad as the controls you declare. |
| Observers on the application's own records | `sqlite-audit`, `http-audit`, `sqlite-snapshot`, `pg-snapshot`, `mysql-snapshot`, with `effects` on checks | A committed forbidden effect the application recorded fails the check even when the response looked like a refusal. Each row records `backendEvidence`. | Under custody, a prohibition pass resting only on these reads inconclusive. Per-observer absence rules apply. `audit-file` is not used. |
| Request-path observers | `egress-recorder`, `smtp-sink`, with `routing` and a `witness` | Outbound HTTP calls and mail sent to a loopback sink the application cannot alter, which can decide a prohibition under custody. An n8n exercise (a walkthrough kept outside this repository) uses the egress recorder; in one recorded run (macOS, on a private build; not reproducible from this repository) it read `Response contracts restored; backend observed where marked` on one synthetic n8n 2.41.6 workflow (no merged test pins it). | Proves the declared route was live for the witness, not that no other way out exists. The exercise's container route is verified on Docker Desktop for Mac only. |
| Custody on verdicts | Applied to every HTTP run | Shows which observer decided each clause; refuses to pass a prohibition on records only the application keeps. | Leaves database-write prohibitions inconclusive on correct builds. |
| Constrained effects (`effect.only`) | An `effect.only` assertion in a check's `effects` | "This request may cause exactly these effects and nothing else": one committed effect outside the declared set fails the check, from any observer. | Covers only what its observers report; in a prohibition it passes only on observers held outside the application (request-path ones or a provider feed). |
| Lifecycle | `lifecycle` entries on the target | A user suspended, removed or demoted mid-run: the pre-change credential must be refused, with nothing committed behind the refusal. | Tests the declared refusal policy only, not in-flight or queued work. |
| Creator versus actor | `capture` on a creating check, `{{name}}` and `precondition` on later checks | One user acting on a record another user created, without hard-coded ids, one check per (creator role, actor role) cell. | The creator is the capturing check's declared actor; two follow-ups are open (KNOWN-LIMITS). |
| Observation settlement and correlation | Applied whenever a check declares effects | A late effect withholds every pass it could change (`effect-outside-window`, `effect-ambiguous-attribution`, `settlement-unobserved`); a fail stays a fail. | Correlation is by selector, not by request. A target may declare a `correlation` header that egress-recorder destinations record (opt-in); the token is the application's own account (any well-formed value it sends is recorded), so it only withholds: no selector or pairing pin reads it, and it never releases a withheld pass or fails one, and per-check settlement (which needs correlation) adds drain barriers that release nothing. Effects after the final mark are outside every claim. |
| Selector pairing | Applied to pinned absence clauses; `assess --check-config` lists `unpairedSelectors` | A pinned actor or resource on an `effect.none` counts only when an allowed-use control shows that selector matching. | Shows the selector selects something, not that the request could cause it. |
| Model identity | `SCOPEHAVEN_MODEL_TAP_UPSTREAM` and `SCOPEHAVEN_MODEL_TAP_PORT`; `gate --require-model-identity` | Each run records which model served it through Scopehaven's own model tap, and a comparison credits each verdict change to the application, the model, both or neither. | The identity is what the model server reported, and only calls routed through the tap are seen. |
| Regression gate | `./scopehaven gate --config PROFILE --target ID --out DIR --authorization RECORD [--baseline RUN_ID]` | A fresh assessment plus a decision (`clean`, `assessment-failed`, `config-or-runtime-error`) and, with a same-directory baseline, a comparison with its repair label. | One-shot; not a scheduler, monitor or enforcement layer. |
| Sequences through the regression gate | `./scopehaven sequence ... --authorization RECORD --save DATA_DIR --build LABEL --regression-gate [--baseline RUN_ID]` | A timed sequence run (for example a request held at the hold gate while access changes) saved as a native run and judged by the same gate, with same-actor pairing for refusal rows. The hold gate is a request-path observer. | A status row shows what the application answered; another sequence evaluator never compares. |
| Owned refund lifecycle contract | `./scopehaven gate --target refund-clean --out DIR --refund-trust-out KEY` and the eight `refund-*` variants | An owned synthetic refund workflow judged on operator-held windows through the gate, with a signed result. Each defective variant must block. | Owned synthetic workflow only; no baseline comparison; acceptance timing is an application-ledger control. |
| Exports and report | `./scopehaven export --data DIR --run RUN_ID [--baseline RUN_ID] --format FORMAT --out NEW_FILE [--standards-file MAP_JSON]` | Single-run `json`, `html` (full report with a print cover and limits section), `sarif` or compact HTML `summary`; comparisons as `json` or `html`. New `0600` files with their SHA-256. Print to PDF from a browser. | Exports and evidence packs are signed by default with the operator's local Ed25519 key, into `NAME.dsse.json` beside each file (`--unsigned` skips it for a single export; a pack is always signed). That signature shows only that whoever holds the key produced these bytes, so a pack signed on the application owner's machine is self-attested. ScopeHaven can add a second signature: a countersignature over hashes only, with a key published at `https://scopehaven.dev/.well-known/scopehaven-keys.json`, and an RFC 3161 timestamp from freetsa.org ([SIGNING-KEYS.md](SIGNING-KEYS.md)). Signing, the countersignature and both verifiers are available but not yet in this release's tested modes. The summary accompanies the full report and run JSON and is not anonymized. SARIF and comparison exports do not mark backend-observed rows. SARIF standards tags (OWASP LLM 2025 and 2026, OWASP Agentic 2026, MITRE ATLAS 2026.09, CWE) are mappings, not compliance claims; configured HTTP suites are tagged only through `--standards-file`. Print layout and page counts are unverified. |
| GitHub Action | `integrations/github-action` (composite action) | An HTTP assessment, the gate and JSON, HTML and SARIF exports in a workflow that starts the application on loopback, with a job summary. | Tested locally only; backend observers are not part of the action. See its README. |

## Not in the tested modes of this release

- **Withheld:** the second-opinion extension, generated coverage, and install-state isolation, which is not in this release. [KNOWN-LIMITS.md](KNOWN-LIMITS.md#withheld-from-this-release) says why.
- **Available, not in the tested release modes:** remote staging over direct HTTPS (`"targetContext": "operator-remote"`), under an authorization record naming its exact origin, with DNS pinned for the run ([KNOWN-LIMITS.md](KNOWN-LIMITS.md#remote-https-targets)); operator-forwarded staging, under an authorization record that names the forwarder's destination and with the same-route control rule ([KNOWN-LIMITS.md](KNOWN-LIMITS.md#operator-forwarded-staging)); the dashboard; policy-import drafting; multi-turn pairs and the conversation connector; the operator-side payments double as a profile observer (it is used only by the owned refund contract); evaluation import, attestation (export signing, the ScopeHaven countersignature and both verifiers, [SIGNING-KEYS.md](SIGNING-KEYS.md)), monitoring and the other modules under `integrations/` not listed above.
- **Never in scope for this release:** hosted vendor targets and anything not covered by an authorization record, production systems, real customer data, hosted vendor services, scheduled monitoring and runtime enforcement.
