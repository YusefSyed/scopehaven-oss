# Observers

Observers record what a target application actually did during a check (effect events), next to what its HTTP responses said. Each one has a declared scope. Authoritative observers (the app's database, its audit log or audit endpoint, the request-path hold gate, an egress or SMTP sink with proven routing) can show that an effect did not happen. Presence-only telemetry (OTel traces, MCP logs) can only show that it did.

| Module | Observer |
|---|---|
| `sqlite.mjs` | `sqlite-snapshot` (diffs selected tables between marks) and `sqlite-audit` (reads an append-only audit table) |
| `file-snapshot.mjs` | Report only, not an observer of the effect rules: lists files under declared directories (by digest, never content, links never followed) at two points and reports the net change. Used by the sequence CLI's `--files`; it makes no window and decides no check |
| `audit-http.mjs` | `http-audit`: the app's own audit endpoint, through the loopback client |
| `otel.mjs` | `otel`: an OTLP/HTTP JSON receiver on loopback (presence-only) |
| `mcp.mjs` | `mcp-log`: the MCP stdio recorder and Streamable HTTP proxy logs (presence-only) |
| `audit-file.mjs` | `audit-file`: the app's own request audit log file (JSON lines), with a witness request per check |
| `pg-snapshot.mjs`, `pg-wire.mjs` | `pg-snapshot`: the app's own Postgres tables, read-only row versions (xmin) through a built-in wire client |
| `egress-recorder.mjs` | `egress-recorder`: a loopback sink for the app's outbound HTTP (never forwards unless a destination opts in to a loopback upstream); authoritative only with declared routing and a witness per check |
| `mysql-snapshot.mjs`, `mysql-wire.mjs` | `mysql-snapshot`: the app's own MySQL (InnoDB) tables, read in one consistent snapshot per mark through a built-in client; exact absence only with a server-maintained change column |
| `smtp-sink.mjs` | `smtp-sink`: a loopback mail server the app's mail host points at (never relays); authoritative only with declared routing and a witness message per check |
| `provider-feed.mjs` | `provider-feed`: an email provider's own signed record of the messages it accepted (a provider stub's loopback feed or an export file), never the app's record |
| `request-feed.mjs` | Not an observer: the reader an egress recorder builds for its declared `requestFeed` (in-doubt resolution), a provider's own signed record of the write requests it received, joined to the recorder's own sends by their exact idempotency key (collector `request-feed/1`) |
| `read-back.mjs` | Not an observer: the reader an egress recorder builds when a destination declares `readBack` (in-doubt resolution), ScopeHaven's own proven reads of the system of record the destination writes to, through its forward upstream on loopback under a read credential the application never holds (in the egress recorder's collector, `egress-recorder/9`) |
| `app-log.mjs` | Not an observer: the reader of a target's declared app action log (`appLogs`), the app's own record of what it did. App-reported, never custody evidence; it decides nothing, or with `"use": "admission"` it can make a clause fail, never pass (see below) |
| `sink-ledger.mjs` | The window, witness and quiet-period rules both sinks and the provider feed share |
| `events.mjs` | Effect events, windows and the effect.none / effect.exists / effect.count evaluator |

## SQLite safety

The observer never opens the application's database file; it reads a private copy.

- Both SQLite observers, in WAL and rollback-journal mode, read the live files as bytes only, and run every query on a copy in a private temporary directory. A copy is accepted only when nothing committed while it was being taken. Otherwise the copy is retried, and then the mark fails (`no-consistent-copy`) instead of using a copy that changed while it was taken.
- WAL: the database file is copied, then its `-wal` log, never the `-shm` index. Opening a live WAL database, even read-only, creates `-wal`/`-shm` files in the app's directory and writes its shared-memory index. Across a container's VM file share, that index and the file locks are not shared with the app, so such a reader can see a stale snapshot and can disturb the app's own view of its database.
- The one exception is opt-in: `lockFallback: true` on a `sqlite-snapshot` observer of a rollback-journal database. When every copy attempt fails, it opens the live file read-only to hold one shared lock while copying. It is refused on WAL databases.
- `sqlite-snapshot` reads a declared table of up to 2,000,000 rows (it was 200,000) in key order and keeps one 32-byte digest per row. Declare `key: "rowid"` for a table whose primary key spans columns. An unlisted table of over 200,000 rows is read into one scan-order digest. See `docs/KNOWN-LIMITS.md`.
- An INTEGER past 2^53 (a nanosecond timestamp, a large id) reads exactly in a declared table, the other-table scan and an audit row's actor, action and resource. A declared row digests integers inside the safe range as numbers, as before, and tags one past it, so it never digests like TEXT holding the same digits. A change-column stamp past 2^53 makes its row ambiguous. An audit id past 2^53 fails that mark (`read-failed`) rather than round its cursor.
- `integrations/observers/observers.test.mjs` records every SQLite open on every path to prove this.

## Audit-log file observer (`audit-file`)

It reads the application's own request audit log (one JSON line per answered request, for example Open WebUI's `audit.log`) and maps each line to one declared rule. It can show that an effect did not happen only when every line in the window is accounted for. See the header of `audit-file.mjs` for the full rules.

Profile entry:

```json
{ "id": "log", "type": "audit-file", "path": "/path/to/audit.log", "origin": "http://127.0.0.1:4420",
  "rules": [{ "name": "knowledge.update", "method": "POST", "path": "/api/v1/knowledge/{id}/update", "refusedStatuses": [400, 401, 403] },
            { "name": "witness.status", "method": "GET", "path": "/api/v1/status", "operation": "read" }],
  "ignore": [{ "method": "POST", "path": "/api/v1/auths/signin" }],
  "logActors": { "support1": "<the log's user id for support1>" },
  "witness": { "rule": "witness.status", "actorId": "support1", "method": "GET", "path": "/api/v1/status" },
  "settleMs": 1000, "quietMs": 300 }
```

**The witness.** For each check that declares effects, after the check's settle and after every other observer has taken its end mark, the connector sends one witness request per audit-file observer: a GET carrying `scopehaven_witness=<nonce>`, tagged for that check's window. Each audit-file window is collected right after its own witness, before the next one is sent. The window is complete only when that exact witness line is logged.

- **The witness must be a GET the app logs, matching exactly one rule: the witness rule.** A POST is refused, because it would change the app's state on every check. Some apps log only state-changing requests: Open WebUI's audit log at `METADATA` level records POSTs only. Those apps cannot give this observer a witness. On Open WebUI it could not prove absence anyway, since its lines carry no status (see below).
- **The witness is never an effect.** It cannot satisfy `effect.exists` or `effect.count`, and cannot fail `effect.none`, on its own rule.
- **Lines that cannot be attributed.** A rule line logged after the witness request was sent, or after the witness line, is never attributed to the check: the window is partial, so absence reads missing, and the line is not an event, so it never satisfies `effect.exists`. This covers lines the witness route itself logs.
- **What is not separated.** A side effect of the witness route that another observer records after the next check starts. Choose a witness route that changes nothing.
- **Relies on complete logging.** The observer relies on the app logging every request on its rule routes.
- **The witness response must carry no secret.** Apps that log response bodies write the witness's response into their log. On Open WebUI, `GET /api/v1/auths/` returns the session token, so choose a route such as a read-only settings or status GET.
- **Body-logging audit levels are for test environments only.** Open WebUI records statuses only at `REQUEST_RESPONSE`, which also logs request and response bodies (session tokens included). Enable it only on a test install, and invalidate any sessions it logged.

**Apps that log no status give partial, never absence.** Only an integer 2xx status is a committed effect, and only a declared `refusedStatuses` code is a refusal. A line with no status, a null status or any other status makes the window partial (`audit-status-missing` or `audit-status-undecided`), so an absence check reads missing, never pass. This is the fail-safe. Open WebUI's audit lines carry `"response_status_code": null`, so on Open WebUI this observer can show that a request was made but cannot prove that an effect did not happen.

**Limits:**
- Once the witness is logged, lines appended after the log has been quiet for `quietMs` are not observed (this is stated in every run's limitations).
- Waiting for the witness (`witnessWaitMs`) and the quiet period is not counted in the run's time budget, unless the target declares `timing` (its plan counts each witness close, and every wait ends by the declared run budget).
- Sequences cannot use this observer: they send no witness, so their windows would always be partial.
- A log rotated before the observer started is not detected: the app must reopen its log before testing starts.

## Postgres snapshot observer (`pg-snapshot`)

To try a disposable Docker server, the live tests and a SELECT-only profile role, follow [Trying the observers against a local Postgres](../../docs/POSTGRES-LOCAL.md).

It reads the application's own Postgres tables at each mark, in one `REPEATABLE READ READ ONLY` transaction: for every row, its key, its `xmin` (the transaction that wrote this row version) and `md5(row::text)`. The hash is computed in the database, so no non-key values leave it (each row's key does). The client (`pg-wire.mjs`) has no npm dependency. By default it speaks SCRAM-SHA-256 only: it verifies the server's signature, requires at least 4096 iterations and a server nonce that extends the client's, and refuses md5 (operator code can opt in with `allowMd5`; a profile cannot), cleartext and unchallenged (trust) logins. It connects only to the literal `127.0.0.1`, and drops the password after the handshake.

```json
{ "id": "db", "type": "pg-snapshot", "host": "127.0.0.1", "port": 5432, "database": "app",
  "credentialEnv": "SCOPEHAVEN_TARGET_APP_DB_READER", "tables": [{ "table": "Chat", "key": "id" }], "settleMs": 1000 }
```

`SCOPEHAVEN_TARGET_APP_DB_READER` holds `user:password` for a role with `SELECT` only on each declared table. Each mark locks the table and, through it, every partition and inheritance child. PostgreSQL 17 checks only the parent's privilege for that. A server that also checks each child's fails the mark as `permission-denied` until the role can `SELECT` the children too. It is never a partial read. The profile can carry no other connection field.

- **Updates of identified rows are exact.** Every committed UPDATE writes a new row version with a new `xmin`: a no-op update, a HOT update, and a write reverted within the window all change it. Row locks (`SELECT … FOR UPDATE`) set `xmax`, not `xmin`. So an existing row whose `xmin` did not change had no committed update. No operator assertion is needed, unlike the SQLite change column.
- **Freezing is not an update.** A row whose `xmin` reads as the frozen id at one mark only is ambiguous, never an event.
- **Inserts and deletes are net-only.** A row added and removed within a window is not seen, and neither is an update to a row inserted or deleted in the window.
- **Absence is claimed only about rows seen at both marks.** A check naming one row (`"resource": "Chat/<key>"`) is exact when that row is present at both marks. A prefix or table-wide selector would also cover rows never seen, so it is exact only on a **quiescent** window: the end snapshot's `xmax` equals the start's and no transaction was in progress at either mark, so nothing anywhere in the cluster committed. The entry records these marks (`startXmax`, `endXmax`, `inProgress`) and the validator rechecks them.
- **In-flight transactions make the window partial.** A write transaction still in progress at the end mark could commit later. The observer looks for it in `pg_current_snapshot()`'s in-progress list and in `pg_locks` (transactionid locks, readable by any role): the snapshot does not list the newest writer, whose id is not below `xmax`. A transaction that commits in the instant between the end mark's snapshot and its lock read is not seen there; its write is after the end snapshot, so it reads as committed after the window.
- **Each mark locks before it reads.** Every declared table, and through it every partition and inheritance child, is locked `IN ACCESS SHARE MODE` before the mark's snapshot is taken. So a DETACH, DROP, TRUNCATE, NO INHERIT or rewriting ALTER cannot commit, on a table this mark has locked, between the snapshot (which the catalog reads use) and the scan (which reads current storage). LOCK lists the tree once and then waits, so a child that joins during that wait is listed by the snapshot but not locked: each mark reads its own granted locks and fails (`descendant-not-locked`) unless every relation it reads is among them. The lock waits at most the statement timeout (`lock-timeout`). It blocks those statements only while the mark reads; it does not block ordinary reads or writes of rows, except that rows can wait while an ACCESS EXCLUSIVE request is queued behind the mark's lock. Output settings that change `row::text` (DateStyle, TimeZone, IntervalStyle, extra_float_digits, bytea_output, lc_monetary) are pinned for the mark.
- **A rewrite is not an update.** Each mark records every relation's file node. When one changed between the marks (TRUNCATE, VACUUM FULL, CLUSTER, ALTER COLUMN TYPE), the window fails as `relation-rewritten` with no events, instead of reading every row as updated. A file node that changed during a mark fails that mark. A server restart between the marks fails the window (`server-restarted`). **Unlogged tables are refused** (`unlogged-table`, for the declared table and every descendant): crash recovery empties them without a new file node, and with `restart_after_crash` (the default) the server recovers without a new `pg_postmaster_start_time()`, so no mark could tell. A declared temporary table fails as `temporary-table`.
- **Rows must be identifiable across the marks, or the window fails with no events.** The table's oid changed, its set of descendants changed, a row came from a relation outside the verified set (`relation-unverified`); a key is NULL or duplicated (`duplicate-key`); a row's `xmin` is 0 or 1 (`invalid-row-version`); the end snapshot's `xmax` is below the start's (`xmax-regressed`); a column was renamed, retyped or dropped (`columns-changed`); or a key whose row version is new to it (a key seen only at the end mark, or one whose `xmin` changed) carries an id already committed at the start mark (`key-without-new-version`), so key texts changed without a write, for example enum labels renamed or swapped between rows. An honest insert or update always carries an id that was not committed at the start mark. **The key itself must read stored bytes** (`key-type-refused` otherwise). For the table and every descendant, each mark reads the key column and its type's output function (a domain has its base type's). It accepts only:
  - exactly one column of that name, not a function of the row (attribute notation can call a pg_catalog function such as `to_jsonb`);
  - that is not a virtual generated column;
  - whose type's output function is immutable, or depends only on a setting each mark pins: `date`, `timestamp`, `timestamptz`, `interval` and `money` output in `pg_catalog`.

  A stable output reads the catalog or another type's output. An enum label, a `reg*` name or an `aclitem` role name can change through a rename with no row written (observed live for `aclitem`: `ALTER ROLE ... RENAME`). So can a virtual column, when its expression is replaced. Arrays, ranges and composites have stable outputs too. An output function declared immutable is trusted to be immutable. The client pins `client_encoding` to UTF8 at startup, so a database or role default cannot change how a key decodes. In each case no change is reported at all, so nothing can satisfy a presence check or make backend evidence observed. A table whose content changed under an unchanged `xmin` is violated: never exact, and none of its changes is reported.
- **Partitions and inheritance children are checked.** Each descendant, at any depth, must be a heap table or a partitioned table (whose access method may read empty or, on PostgreSQL 17, `heap`), and each row's `tableoid` must be the parent (if it stores rows) or a heap descendant. A descendant the parent scan would skip fails the mark (`descendant-not-scanned`): another session's temporary child, and a partition whose `DETACH ... CONCURRENTLY` is pending (PostgreSQL 14+). More than 10000 descendants fail it too (`too-many-descendants`).
- **Wraparound.** An unchanged `xmin` between the start snapshot's `xmin` and the end snapshot's `xmax` could be a new id that wrapped onto the old one, so it is ambiguous.
- **A window must move forward.** A window whose end mark is not after its start mark fails (`window-not-forward`), and a sequence assertion's `to` mark must come after its `from` mark.
- **A role that cannot read a table fails the window.** It never reads as complete and empty.
- **Read-back of declared values (`readBack`; a check names the tables that judge it with `"readBack": [{ "observer", "table" }]`, src/http-readback.mjs: one assertion per table, fail-only in a boundary check).** A table may declare the value columns to read back and what they should hold (`src/pg-readback.mjs`). Each mark then also reads that table's columns and types, and its scan reads exactly the declared columns, as text, beside a sha256 of the row's other columns (an expected row's remainder) and a sha256 of the whole row (any other row's), in the same transaction. Values are typed: text (`text`, `varchar`, `char`), `uuid` (compared in lower case), an exact decimal (`int2` to `int8`, `numeric`, `float4`, `float8`; NaN and infinities refused), boolean, ISO 8601 time (`timestamp`, `timestamptz` in UTC, `date`; infinities and BC refused) and canonical JSON (`json`, `jsonb`; each number compared as the exact decimal of its text, never through a double). A domain reads as its base type. Any other type, a virtual generated column or a missing column leaves the table's read-back unusable, never the window. A column whose name reads as a secret or personal data must be listed under `sensitive`, or the declaration is refused; its values are kept only as digests sealed under a salt the observer holds, unless the operator also lists it under `reveal`. The per-table remainder (each other row whole, and an expected row's undeclared columns) is sealed the same way. Expectations: a value per row key at the end mark, or a change (`from`, `to`) across the window, and exact insert and delete counts within a key range (`{ "prefix" }`, an integer `{ "min", "max" }`, or exact `{ "keys" }`, each compared as the key column reads it: a `uuid` in either case, a `char` without trailing spaces, an integer by its exact digits, a `numeric` as its exact decimal, a time in ISO 8601 UTC, text exactly; a declared key its type cannot read, such as `042` for an integer or `A100` for a uuid, or a key column of any other type, such as `float8` or `citext`, leaves the counts inconclusive). A json column's expectation is JSON text, read as the stored value is read, so a 64-bit id is compared digit for digit; `null` is SQL NULL and `"null"` the JSON null. `judgeReadBack` fails a value or count that does not hold; leaves a pass inconclusive when anything outside the declared values moved (`"remainder": "unchanged"`, the default); and decides nothing on a partial or failed window, a violated table, or a value or expectation it cannot read. Counts are net between the marks, as inserts and deletes are. The scan reads every declared value of every row (each cut at 4097 characters); the read-back budget bounds what a mark keeps, not what it reads, so a large table with wide declared columns can reach the statement timeout or the reader's memory and fail the mark (never a pass). Custody is `subject-writable`: the application can write its own database, so a pass says so and a fail stands.
- **Requirements:** PostgreSQL 13 or later (`pg_current_snapshot`).

## Egress recorder (`egress-recorder`)

A loopback sink for the application's outbound HTTP: did the app call out, post a webhook or hit a payments API during a check? The sink listens on `127.0.0.1` and `[::1]` at its port, each bound exclusively, and does not start unless both bind (collector `egress-recorder/10`: a route written as `localhost` may resolve to `::1` first, so another process holding `[::1]` there would take the app's traffic). It answers every request itself (`reply.status`, default 202, empty body) and **never forwards** unless a destination opts in to a loopback upstream (below), so nothing the app sends during a test leaves the machine through it. Each request is one `send` effect named by its destination host.

```json
{ "id": "sink", "type": "egress-recorder", "port": 4461, "routing": "base-url",
  "destinations": [{ "host": "api.pay.example", "paths": ["/v1/charges"] }, { "host": "hooks.chat.example" }],
  "routes": [{ "prefix": "/pay/", "host": "api.pay.example" }, { "prefix": "/hooks/", "host": "hooks.chat.example" }, { "prefix": "/w/", "host": "witness.scopehaven.invalid" }],
  "witness": { "actorId": "ops", "method": "GET", "path": "/webhook/ping", "host": "witness.scopehaven.invalid" }, "settleMs": 500 }
```

- **Routing.** `proxy`: the app's HTTP client uses the sink as its forward proxy (`HTTP_PROXY`). Plain HTTP arrives in absolute form. HTTPS arrives as `CONNECT host:port`, which is recorded and refused, so its payload is never seen and the window is partial. `base-url`: the app's per-destination base URLs point at the sink, one declared path prefix per destination. A container reaches the sink at `host.docker.internal:<port>`. A base-url request must name the sink in its `Host` header (`127.0.0.1`, `localhost` or `host.docker.internal`, at the sink's port): any other name is a page that rebound its own name to 127.0.0.1 (DNS rebinding), so it is refused (403) and recorded like a browser request, never as a send or a forward. The payments double's routes do the same.
- **Authoritative only with routing and a witness.** Without `routing` (and `witness`) the observer is presence-only: a recorded send fails a check, and silence proves nothing. With them, the connector sends the witness request after each check: an app route that makes the app send one outbound request to the witness host carrying `scopehaven_witness=<nonce>`. The window is complete only when that witness arrives. The witness proves the route was live for that request. It does not prove the app has no other way out; for that, run the app on a network whose only exit is the sink. On macOS, `./scopehaven assess --confine <launch.json>` starts the app under `sandbox-exec` with outbound connections refused except to the declared sinks, checks that it is the only listener on each sink port, and states its passes as `routing confined` with the record's limits ([docs/ONBOARDING.md](../../docs/ONBOARDING.md), "Confining the app to its sinks").
- **What makes a window partial:**
  - the witness is missing, duplicated, or belongs to another window;
  - a send arrives after the witness request was sent (never attributed to the check);
  - a request is malformed, dropped at the connection limit, browser-originated (`Origin`/`Sec-Fetch-Site`), or unrouted;
  - a request has a body over `maxBodyBytes`, is aborted, or is still in flight at collect. In flight includes a request whose headers are still arriving, also when it follows a completed request in the same write: the recorder reads the server's own parser state (Node's connections list, kept for its request timeouts). On a runtime without that state, every window is partial (`egress-parser-state-unavailable`);
  - a CONNECT tunnel is requested;
  - a path's percent-decoding names a different declared path than its raw form;
  - a proxy request's `Host` header names another host than its URL, or its destination is an IP literal that is not itself declared: a send to a declared host could be addressed under another name. An event names the URL host, so declare the names and addresses the app may use (or their other names as aliases, below);
  - a connection has sent part of a request whose headers have not ended when collect runs;
  - a request's host is longer than 128 characters, the longest event name (`egress-host-over-limit`; the payments double's `payments-host-over-limit`): it is no event, never shortened into another (declared) host.

  A listener that went down since the start mark, or evicted records, fail the window. A send made later than `quietMs` after the last arrival is not observed.
- **Destination-scoped partial reasons.** For a check window the connector asks for scoped coverage. Then a send after the witness request, a request still in flight at collect, or a path that decodes ambiguously no longer makes the whole window partial: each becomes an entry `{ name, resource, codes }` (codes `after-witness`, `in-flight`, `path-ambiguous`; resource null when the path is ambiguous) in the window's `scoped` list, at most 32 entries (`egress-scope-limit` past that). Only a clause whose selector an entry could fit reads missing, whatever its verdict would be: once the late entries are followed, a fail or count on another selector is decided there. An entry that is exactly one completed after-witness request, not path-ambiguous, on a host that declares capture also carries that request's ledger `seq` and its `captured` record (`egress-recorder/4`); a second request of any kind in the entry removes both. An `effect.only` clause reads the window complete toward a pass only, when every entry has a resource, fits no expected selector and definitely fits an allowed selector that pins only source, operation, name and resource, or, for an entry with its record, one that also pins `fields` and reads match on that record (see KNOWN-LIMITS). The validator binds the entry's seq after its window's own events, and refuses a run where any sealed event with that seq disagrees with the record. Everything else in the list above stays window-wide. So does an undeclared host, a send naming the witness host or nonce, and any connection the recorder closed that the client had not asked to close (`egress-scope-ineligible`: bytes written after such a close, including Node's keep-alive idle close, never reach the recorder). An after-witness entry counts only when a later check window of the same recorder follows it, or the run-end drain does; an in-flight entry counts only when the drain follows it. Otherwise the connector decides the row again with the window read window-wide. The drain (`drain({ capMs })`) runs only when the target declares attribution or a forwarded destination: before the final mark the recorder waits until no request is arriving, no record is pending and `quietMs` has passed since the latest arrival, forward settle or reply, and each mark notes whether it was clear (`markClear`). It then looks once more a turn later, for bytes already read but not yet parsed, and that look checks quiet again too (collector `egress-recorder/12`; under `/3` to `/11` a request read, recorded and answered in that turn could leave the drain quiescent just after it arrived, so a saved run under those labels may carry such a drain). Every quiet period, wait and lateness test the recorder and its ledger make is on a monotonic clock (`performance.now()`), so a step of the wall clock neither fakes quiet nor stalls a collect; a connection Node has accepted but that has sent nothing yet counts as arriving. The settlement record carries `drains: [{ instanceId, quiescent, waitedMs, markClear, closedAfterCollect }]`; a drain follows only when quiescent with the listener up, with a clear final mark, and with no close the recorder made after the first check collect that left a late entry. Observer records carry `collector: { label: 'egress-recorder/4', digest, node }` (`/2` before the drain, `/3` before late entries carried their record), a digest of the recorder files and the Node version, so runs from a different recorder build compare as a different collector.
- **Other names of a declared provider (`egress-recorder/11`).** An event names its URL host, and many providers serve one API under several hosts (a regional or legacy name, `api` and `api2`). So an undeclared host that shares its registrable domain (public suffix plus one label, `src/public-suffix.mjs`) with a declared destination may be that provider under another name: in a check window each completed send to one adds an entry for the destination (code `egress-undeclared-sibling-host`, its resource read on the destination's declared paths), so a clause that selects the destination reads missing, never pass, including a fail that rests on no send (`effect.exists`, a count); in every other window (a settlement gap, a barrier, the run's tail) the code makes the window partial, so settlement withholds every earlier absence pass on that recorder, whatever its destination. A send to an unrelated host (another registrable domain) changes nothing. The registrable domain reads only the Public Suffix List's ICANN section, 55 multi-label suffixes (`src/public-suffix-list.mjs`), so hosts on a shared platform (private-section rules such as `herokuapp.com`, `vercel.app`, `myshopify.com`, `cloudfront.net`, `azurewebsites.net`, `s3.amazonaws.com`) and hosts under a ccTLD suffix outside those 55 (`com.co`, `com.pl`, `co.at`, `gob.mx`, `edu.au`) are one family: a send to another tenant there (`tenant-b.herokuapp.com` beside a declared `tenant-a.herokuapp.com`) makes the destination's clauses read missing. Declare that host as its own destination to separate them. The ICANN-only choice is deliberate: splitting at a platform suffix would stop catching the same company's other name there (`myapp-eu.herokuapp.com` beside `myapp.herokuapp.com`). Trailing dots are dropped (`api.pay.example..` is `api.pay.example`), and a host left with an empty label (`api-eu..pay.example`) is malformed, so its window is partial. Declare such a host as its own destination, or as an alias: `{ "host": "api.pay.example", "aliases": ["api-eu.pay.example"] }` (up to 8, none a destination, the witness host or another destination's alias) records its sends under the destination's name, Host header and CONNECT included, and the scope and run record publish the aliases. A keyed send's head keeps the name it was sent to, so a retry under another name is never collapsed as an exact replay. Every clause's text also names the undeclared hosts its egress windows saw. A provider name in another registrable domain is caught only when declared (as a destination or an alias), and is otherwise only named in that text.
- **Another recorder's destination (`egress-recorder/13`).** A run may declare several egress recorders, each with its own destinations, and an app may send a provider's charge through a recorder that does not declare the provider. So the factory passes each recorder the destinations the run's other egress recorders declare and it does not (`src/egress-rules.mjs` `crossDestinationsOf`; operator input, a profile cannot set it). A send to one of those hosts, or to its alias, is recorded under that host with its resource read on that host's declared paths (never captured, keyed or forwarded there), and an undeclared host sharing a registrable domain with one is its sibling as above (an entry in a check window, the code window-wide elsewhere). The scope and the run record publish them as `cross: { [host]: [alias, ...] }`. A window that holds a send to such a destination, or to its sibling, is one that can see it, so a clause on the destination fails on the send or reads missing on the sibling whichever recorder held it, and its text names the undeclared host from that window too. The window's silence vouches for nothing: without such a send it does not see the destination, so a run whose recorders hold nothing of each other's reads exactly as before, and a run with one recorder has no `cross`.
- **Nothing secret is stored.** An event names the host and a declared path prefix (`POST /v1/charges`, or `POST *` for any other path). Raw paths and queries are only digested, with a salt chosen per recorder, and so are bodies unless a destination declares capture (next item), because webhook URLs often carry their secret in the path. Request headers are not kept, except one value on a destination that declares `"correlation": { "header": "traceparent" }` (or the target's custom `x-` header): the token one well-formed value of that header carries (a traceparent's trace id, or a lowercase UUID's 32 hex digits) is stored in the event's `correlation.settlementToken`, and a missing, repeated or malformed header (a custom value with any uppercase letter included) stores nothing. The recorder checks the format only: the application writes the value, so it stores any well-formed value the application sends, whether or not it is the token the connector sent. No selector or pairing pin reads `settlementToken`, and http-egress events never carry a `correlation.traceId`. Answered requests keep the connection open, so a reused connection's next request is read too.
- **Declared body fields (opt-in).** A destination may add `"capture": { "pointers": ["/amount", "/currency"], "maxBytes": 16384 }`: the recorder then reads those scalar fields of that destination's JSON bodies on its declared `paths` (UTF-8, uncompressed, within `maxBytes`; a destination that declares capture must declare paths, and a send on any other path of the host records `path-undeclared` with no values) and stores them on each send event as `captured: { status, values }`, and publishes the declaration as `scope.capture`. Pointers naming secret-like keys are refused, secret-shaped or over-long strings and objects or arrays are never stored, and an unreadable body records why (`path-undeclared`, `not-json`, `encoded`, `over-cap`, `json-invalid`, `json-too-deep`, `json-duplicate-key`, `content-type-ambiguous`, `no-body`). Effect selectors match them with `fields` (three-valued: an unreadable field is unknown, never absent; a captured string differs from a pinned string only where no common receiver reading makes the two one value, so `"105.50"` against `"105.5"`, `"Refund"` against `"refund"` or `"yes"` against `"true"` is unknown, and an `in` member of another type reads unknown unless no reading makes it equal). Adding `"encodings": ["json", "form"]` also reads the fields from `application/x-www-form-urlencoded` bodies as `{ type: "text", value }`, only for a POST whose target has no query or fragment, with no Cookie header, and a body that parses unambiguously (a non-ASCII value needs an explicit `charset=utf-8`); the scope then lists the host in `scope.captureForm`. **Keyed retries (opt-in).** A destination may add `"idempotency": { "header": "idempotency-key", "methods": ["POST"], "volatile": ["traceparent"] }`, or `{ "pointer": "/event_id", "maxBytes": 16384 }` for an event id in the JSON body; `volatile` may also list webhook signature and timestamp headers: each send to it then carries `idempotency: { status, key, fold, head, firstSeq }`, salted digests of the key, its case-folded form and the request head, never the key itself, and the scope publishes `scope.idempotency`. An `effect.count` with `"countBy": "idempotency-key"` counts an exact sequential replay under one key once (rules: `src/idempotency.mjs`). Form statuses: `not-json-or-form`, `form-media-type`, `form-method`, `form-query-or-cookie`, `form-invalid`, `form-key-ambiguous`, `form-duplicate-key`, `form-too-deep`, `form-over-cap`, and a field a receiver could bind differently reads `unusable` with reason `ambiguous`. A text value matches a number operand only as a canonical integer of at most 15 digits; a decimal text that no common reading makes the pinned value can only turn a missing clause into a fail (`src/body-fields.mjs` decimalDiffers). Rules: `src/body-fields.mjs`.
- **Correlation (opt-in, run settlement).** With the target's `correlation` header declared, every sent check request carries a per-request token and each destination that declares the same header records the token the app forwarded. Settlement reads the token as the app's own account of which check's request a send came from, and uses it only to withhold a pass, never to release or fail one; a selector or pairing pin never reads it, and a correlated target refuses a `traceId` selector an egress recorder could see (`correlation-token-not-selectable`) (see Settlement across the run in [docs/ONBOARDING.md](../../docs/ONBOARDING.md)). The witness host is never a destination, so a witness send is never tagged.
- **`committed`** means the request reached the sink in full. The real destination never receives it: the effect recorded is the app's attempt to send.
- **Forwarding to a loopback upstream (opt-in).** A destination may add `"forward": { "upstream": "http://127.0.0.1:4010", "applied": [200, 201], "rejected": [402], "proofEnv": "SCOPEHAVEN_TARGET_PAY_UPSTREAM_PROOF" }` (optional `timeoutMs`, 100 to 30000, default 5000, and `maxReplyBytes`, 1024 to 1048576, default 65536). Each send is recorded as above, then forwarded as recorded (`egress-forward.mjs`: the named path and query, the exact body bytes, hop-by-hop headers dropped, `Host` set to the destination) to that upstream (a header the `Connection` header names is still forwarded, so the upstream receives every header the record read), and its reply goes back to the app. The upstream must be the literal `127.0.0.1`, not the recorder's own port, another observer's or the target origin's; a forwarded host takes no `replies`, and sequences cannot forward. The event records `upstream: { outcome, status, proven }`. Only a reply carrying a valid `X-Scopehaven-Forward-Proof` (an HMAC under the `proofEnv` secret over the per-request nonce, the request received and the status; see ONBOARDING) decides: `applied` for a listed 200, 201, 203, 204 or 205 (default 200, 201, 204; never 202) to a method other than GET, HEAD, OPTIONS or TRACE, `rejected` for a listed 4xx, `unknown` otherwise. The secret is at least 32 characters and never a profile credential. A timeout gives the app 504; a refused connection, an invalid status or an oversized or cut reply gives 502. A selector may then require `"upstream": "applied"` (core clauses and claim rules; a pairing pin): unknown holds such a clause at missing, and a recorder that does not forward the host cannot decide it. A forwarded body over 1 MiB gets 413 and is never forwarded, and a send still being forwarded at collect leaves the window partial.
- **Returned ids (opt-in, proof version 2).** A forwarded destination may add `"proofVersion": 2` and `"ids": { "minted": ["/id"], "references": ["/charge"] }`: the /2 proof also covers the reply body, and the declared string ids (8 to 200 characters) of each proven reply are kept as salted digests in `upstream.minted`, `upstream.references` and `upstream.echoed` (a minted-pointer value the request itself carried). Background attribution uses them in one place (`src/id-closure.mjs`), on a target that declares `correlation`: a matched background-possible send that refers to an object one of the check's own selected sends (carrying its own correlation token) had created keeps the check's `effect.exists` pass.
- **Verified signature headers (opt-in, keyed retries).** A destination that declares `idempotency` may add `"signing": { "scheme": "stripe", "signature": "x-hooks-signature", "secretEnv": ["SCOPEHAVEN_TARGET_HOOKS_SIGNING_A"] }` (schemes `stripe`, `standard-webhooks` with `id` and `timestamp` headers, `slack-v0` with a `timestamp` header; optional `dedupeSeconds`, default 300). The recorder reads the secrets once when it is built and verifies each send with HMAC-SHA256 on the raw body bytes it received. The signature and timestamp headers leave the request head only when every signature entry matches exactly one usable declared secret inside the run window with no trailers, and the head then names that secret; anything else keeps the headers bound. Every collapse on such a destination, exact replays included, also needs the later send to arrive within `dedupeSeconds` of the first one (its arrival, or its verified signing timestamp if earlier). Each send's key record carries `signing: { scheme, verified, t, at }`, and the run records `signing: [{ observer, host, scheme, usable }]`. No secret, MAC or value derived from one is ever stored. See docs/ONBOARDING.md and SECURITY.md.
- **Test-mode replies (payments, webhooks).** An app that reads the answer (a payment client that needs a charge object, a webhook sender that checks the receiver's reply) can be given declared JSON per destination, method and path: `"replies": [{ "host": "api.pay.example", "method": "POST", "path": "/v1/charges", "status": 200, "json": { "id": "ch_test_1", "object": "charge", "livemode": false } }]`. Replies are static and bounded (32 entries, 16 KiB each), they never echo anything from the request, and they change only what the app sees, never what is recorded. They are a local stand-in for a provider's test mode: no real provider is contacted, and an HTTPS client that cannot take a base URL still reaches the sink only as CONNECT (host recorded, payload unseen). An app's outgoing webhooks are ordinary egress: point the webhook URL at a `base-url` route.

## SMTP sink (`smtp-sink`)

A loopback mail server: did the app send mail, and to whom? Point the app's mail host at the sink (from a container, `host.docker.internal:<port>`). Like the egress recorder it holds its port on `127.0.0.1` and `[::1]`, each bound exclusively, and does not start unless both bind (collector `smtp-sink/2`). It accepts every message and **never relays one**. Each recipient of a completed message is one `send` effect named by the recipient's domain.

```json
{ "id": "mail", "type": "smtp-sink", "port": 4462, "routing": "smtp-host",
  "domains": [{ "domain": "customers.example", "addresses": ["vip@customers.example"] }, { "domain": "acme.example" }],
  "witness": { "actorId": "ops", "method": "GET", "path": "/webhook/mail-ping", "domain": "witness.scopehaven.invalid" }, "settleMs": 500 }
```

- **Witness.** After each check the connector sends the witness request with `scopehaven_witness=<nonce>`. The app must then mail `<nonce>@<witness domain>`; the nonce is read from the envelope recipient, which is never encoded. The window is complete only when that message arrives. The witness domain is never a destination. A witness message that also goes to another recipient is never treated as a witness.
- **Shared window rules (`sink-ledger.mjs`), the same as the egress recorder.**
  - **Partial when:** the witness is missing, duplicated or foreign; a message is started after the witness request was sent; a message is still in flight at collect; a collect is late; or mail is still arriving after the cap.
  - **Failed when:** the listener went down at any point since the start mark, or the window's records were evicted.
- **SMTP-specific gaps (partial):**
  - a message over `maxMessageBytes` (answered 552);
  - a transaction cut off before its message ended;
  - more than 100 recipients (the rest answered 452);
  - a malformed or unrecognized command, including one that is not UTF-8;
  - a connection dropped at the limit;
  - a recipient at an address literal (`[198.51.100.9]`, `[IPv6:2001:db8::1]`): declared domains are names, and a literal could address a declared domain's server under another name, as an IP literal can for the egress recorder;
  - a recipient domain over 128 characters, the longest event name (`smtp-recipient-unusable`): it is no event, never shortened into another (declared) domain, and a witness message to it is mixed.

  RSET before DATA is not a send.
- **Protocol.** It speaks HELO/EHLO, MAIL, RCPT, DATA (dot-unstuffed), RSET, NOOP, VRFY and QUIT. Commands are read as UTF-8 (SMTPUTF8 is offered), and a recipient domain is compared in its ASCII form, so mail to `bücher.example` is a send to `xn--bcher-kva.example`. A source route (`<@relay:user@domain>`) is dropped, as RFC 5321 directs. AUTH PLAIN/LOGIN is accepted and nothing of it is kept, so an app configured with a mail login still sends. No STARTTLS is offered: a client that requires TLS cannot send to the sink at all, and nothing is recorded.
- **Nothing personal is stored.** An event names the recipient domain and, only for addresses the profile declares, the address. Other recipients read `*`. Senders, recipients, subjects and bodies are digested only.
- **Recipients are named by the shared rules** (`src/mail-address.mjs`, also the provider feed's). Only a canonical mailbox can name a declared address: a plain printable-ASCII dot-atom local part, without the relay characters `%` and `!`, at a host with no second trailing dot and no IDNA deviation character. Anything else (quoted, commented, escaped or non-ASCII forms, `vip%customers.example@relay`, `relay!vip@`, `vip@customers.example..`) is unusable (`smtp-recipient-unusable`). A recipient that could be the same mailbox as another declared address under common alias rules is ambiguous (`smtp-recipient-ambiguous`): a `+` or `-` subaddress or the local part with its dots removed (`vip+x@`, `vip-x@`, `v.ip@` for `vip@`), or a Proton-style form with `.`, `_` and `-` removed (`v_ip@`); two declared addresses that alias each other (`vip@` and `vip+refund@`) are ambiguous too. Either stays a send to its domain and leaves the window partial, so a resource-pinned absence reads missing. A different address (`vipp@`) stays a plain `*`. A declared address must itself be canonical, or the profile is refused.
- **`committed`** means the message reached the sink in full and was accepted. Nothing is delivered: the effect recorded is the app's attempt to send.

## Provider feed (`provider-feed`)

Some apps send mail through a vendor SDK pinned to its provider's endpoint, so neither the egress recorder nor the SMTP sink ever sees the request. This observer reads the provider's own record of what it accepted instead, never the app's record (configuration: `src/provider-feed-rules.mjs`).

**What it needs.** A provider stub, or an operator-run adapter, that implements the signed `scopehaven-provider-feed/1` contract below. Real provider APIs (Postmark, SendGrid, Mailgun, Stripe) are not read directly: reading them needs a provider credential, which is a held decision.

```json
{ "id": "mailfeed", "type": "provider-feed", "feedId": "helplane-mail",
  "feed": { "endpoint": { "port": 4471, "path": "/feed" } },
  "publicKey": "<base64 SPKI DER of the stub's Ed25519 public key>",
  "domains": [{ "domain": "customers.example", "addresses": ["vip@customers.example"] }],
  "routing": "provider",
  "witness": { "actorId": "ops", "method": "GET", "path": "/admin/mail-ping", "domain": "witness.scopehaven.invalid" },
  "witnessWaitMs": 3000, "quietMs": 300, "pollMs": 100, "maxSkewMs": 0, "settleMs": 500,
  "keySource": "stub" }
```

- **Key source (collector `provider-feed/7`).** Custody rests on who holds the key that signs the entries, which nothing in a run shows: an app can serve a feed of its own and sign it with its own key. So the profile says where `publicKey` came from: `"keySource": "provider"` (the provider's own export), `"adapter"` with `"adapterReads": "provider-api"` or `"application-store"` (an operator-run adapter, and what it reads), or `"stub"` (a test stub). The run record's feed and every window carry it, `"undeclared"` when the profile names none. An undeclared source, or an adapter that reads the application's own store, counts as a key the app could hold (custody `subject-writable`): the feed can still fail a check, never pass one. ScopeHaven cannot check the declaration; it is the operator's statement, cited as one.

- **Route (i), the endpoint.** The stub serves `GET <path>?after=<seq>&limit=<n>` on `127.0.0.1:<port>`, answering `{ "schema": "scopehaven-provider-feed/1", "entries": [...], "more": true|false }` in seq order, and the signed head `GET <path>/head?nonce=<nonce>`: `{ "body": "{\"feed\",\"epoch\",\"lastSeq\",\"nonce\"}", "sig" }`, signed over `scopehaven-provider-feed/1 head\n` + body. The host cannot be set, and the port is never the target origin's, another observer's or a forward upstream's. An entry must be in the feed before the stub's send call returns.
- **Route (ii), the export file: presence-only in v1.** `feed.file` names an absolute path to a JSON-lines file of the same signed entries, bound at start (device, inode, the digest of every complete line) and then read as appended lines, each checked against the 4 KiB before the bound position, as for `audit-file`. Each mark reads the file to its end and records its size: an entry whose line began before the start mark's size, or that is stamped at or before the start mark (no skew allowed), stays an event with outcome `unknown`, which holds every clause it could fit at missing, beside any other observer: never a pass, and never the fail a committed send would give. It has no signed head, and an app that can write the file could remove a line not yet read, so it may show that a send happened (`effect.exists`) but never decides absence or a count (they read unobservable). It takes no `routing` or `witness`.
- **Entries.** `{ "body": "<JSON text>", "sig": "<base64 Ed25519 signature of 'scopehaven-provider-feed/1\n' + body>" }`. The body holds `feed` (the declared `feedId`), `epoch`, `seq` (from 1, contiguous in the epoch), `id` (the provider event id), `type`, `at` (ISO 8601, stamped when the stub assigns the seq, never decreasing) and, for `accepted` and `rejected`, `messageId`, every envelope `recipient` and, optionally, `template` (below). Types are an allowlist: `epoch-start` (seq 1 only, the genesis), `accepted` (each recipient is one committed `send` named by its domain, with a declared address as its resource and `*` otherwise), `rejected` (denied sends) and `status` (a delivery update of an earlier accepted message: no effect). Any other type, a status of an unknown message, a repeated event id or message id (never skipped as a redelivery: ids can come from the app's input), or a recipient that is repeated, unparsable, an address literal or carries a source route, leaves the window partial. Recipients are read by the shared mail address rules (`src/mail-address.mjs`: the SMTP sink's envelope rules, one trailing dot dropped, the domain as its A-label, lowercased, a plain dot-atom local part only). App-written values (subject, stream, tags, metadata) belong under one `app` object, where they cannot stand for a contract field; any other top-level field leaves the window partial, and none of them is read: only a digest of the body is kept. A body is at most 64 KiB, so the stub must keep app-written values short (truncate or digest them); a page over 4 MiB is asked again in smaller pages, and a single entry over it is a fault. What the app chooses only makes the window partial, never a fault: no recipients, more than 100 (the first 100 become events), an overlong or unparsable recipient, a local part that is not a plain dot-atom (quoted, commented, escaped or non-ASCII forms can name a declared mailbox another way), or an alias form of a declared address (a `+` or `-` subaddress, the local part with its dots removed, or a Proton-style form: `vip+x@`, `vip-x@`, `v.ip@`, `v_ip@` for `vip@`). A recipient without a canonical mailbox (another written form, a `%` or `!` relay route, an odd host) stays a send to its domain named `*`, as in the SMTP sink.
- **Templates.** `template` is a contract field: the provider's canonical id of the stored template it accepted the message with (a string), omitted for inline content. The stub or adapter copies it from the send it accepted, never from tags, metadata, custom args, headers or anything under `app`, and writes one form per template (for Postmark, the numeric `TemplateId` as text even when the app sent `TemplateAlias`). A feed reads it only when the profile declares a vocabulary, `"templates": { "<label>": "<provider template id>" }` (1 to 64; a label is 1 to 31 characters of `a-z`, `0-9`, `_`, `.` or `-` starting with a letter and not shaped like a secret; ids are distinct also with case and spaces ignored). Each event to a declared domain then carries the captured field `/template`: the label of the declared id the signed entry names exactly, `absent` when it names none, or `unusable` (`undeclared`) for anything else, a case or space variant included. Clauses and `effect.only` selectors pin it with `fields`, for example `"fields": [{ "pointer": "/template", "equals": "order_cancelled" }]` (or `in`), and fieldState reads it three-valued: a declared label equal to the operand matches, another declared label is "no", and absent or undeclared is unknown, so a template-pinned clause never passes on a template the vocabulary does not name exactly (missing instead) and a later such send withholds a settled pass. Only labels reach a run: the run record's `feed` lists them (`templates`) and its observer entry carries `capture: { "<domain>": ["/template"] }`; the profile's provider ids are never stored as such (a label equals an id only when the operator chose it so). When the profile loads, a `/template` pin on a domain a feed declares must use that feed's labels (a typo or a provider id would read "no" on every send), and a feed without `templates` refuses such pins. In `effect.only`, a feed send whose template reads unknown under a template-pinned expected selector is never absorbed by an allowed selector: it holds the clause at missing, as an unknown actor does. Declare every template the app can send to a pinned recipient, each once, in the form the stub records: an undeclared one holds clean checks at missing. Which real providers record it: SendGrid's message details carry `template_id`; Postmark's Messages API returns `MessageStream` but no template id, and SES events carry only tags and the configuration set, so for those only a stub or adapter on the send path can fill it. A ScopeHaven build without template support reads an entry with `template` as an unknown field (the window is partial), so upgrade the stub and ScopeHaven together. The collector label was `provider-feed/2` (now `/3`, below).
- **Custody.** Only the stub holds the signing key, and the app must never be given it; ScopeHaven holds only the public key, so no secret is read. At start the observer reads the signed head and the whole feed from its signed genesis (at most 20000 entries or 64 MiB), verifies every entry and pins the epoch; from then on it reads only seq `lastSeq + 1`. A bad signature, another feed or epoch (a stub reset), a rewritten earlier entry, a time going backward, a head that is unsigned, stale (another nonce) or behind what was read, or a replaced or truncated file is an integrity fault: every later window fails. A missing seq stops reading there, and every window collected while it lasts is partial. Once read, an entry is the observer's own copy: a later delete or edit at the provider changes nothing. Its lineage is `provider-record` and its custody `independent`. The run record carries `witnessed` and `feed: { feedId, keyDigest, route }`, and every sealed window names the same feed.
- **Windows.** The shared sink ledger keeps them: a background poller reads the feed every `pollMs`, and each mark reads the signed head and then the entries up to it (a mark that cannot fetch the head throws, so the window fails; one that cannot read up to it is behind, and every window it starts or ends is partial). An entry at or below the start mark's head belongs before the window. With `routing: "provider"` and a `witness`, the connector's witness request makes the app send one email through the provider to `<nonce>@<witness domain>`; the window is complete only when that witness entry arrives and the feed then stays quiet for `quietMs` (at least twice `pollMs`). Without them the observer is presence-only. The witness-request split uses no clock: the connector awaits the observer before it sends the witness request, the observer reads the signed head there, and only entries up to it are the check's. The provider's time only tightens: an entry stamped before a check window or after its collect (beyond `maxSkewMs`) stays an event with outcome `unknown`, so it never passes `effect.exists` (and an `effect.none` it would fail reads missing), and the window is partial.
- **Late entries and the run-end drain (collector `provider-feed/3`; `/4` adds the template lift below).** On an endpoint feed with a witness the connector collects check windows scoped, as for the egress recorder. An entry after the witness-request split (by the signed head, never a clock) then no longer makes the whole window partial: each of its recipients joins an entry `{ name, resource, codes: ["provider-feed-entry-after-witness-request"] }` for its domain and its declared address or `*` in the window's `scoped` list (at most 32), and only a clause that entry could fit reads missing. Anything that could hide a send keeps the window partial window-wide, as before: any window-wide code, a late recipient that is unusable, an address literal, repeated or ambiguous, a mixed witness, a late entry before the window or stamped outside it, a domain the feed does not declare (`provider-feed-scope-ineligible`), a stall or a gap. An entry that is exactly one recipient of one late entry, on a feed with a template vocabulary, also carries that send's event `seq` and its template record; if that record is a declared label that a clause's `/template` pin does not accept, on a feed window that sees every field the clause pins, the send is outside that clause (`effect.exists`, `effect.none`, `effect.count`, and settlement, custody and attribution through them). Absent, undeclared or variant templates, and merged entries, still fit. In `effect.only` an entry that could fit an expected selector by recipient keeps the window partial, whatever the templates, and a recipient-only allow lifts an entry only when it fits no expected selector. A template-pinned allow lifts only the check's one late feed entry (one across all its feed windows), and only when that entry is one signed send whose template is a declared label that reads match under the allow (collector `provider-feed/4`); absent, undeclared or variant templates, two or more late entries in the check, an allow that also pins a field the feed does not capture, and runs judged by an earlier build (`/3`, which the connector also records for a feed that does not take the lift) never lift this way. An entry counts only when a later check window of the feed follows it, or the feed's run-end drain does; otherwise the row is decided again with the window read window-wide. Every witnessed endpoint feed drains before the final mark, whatever the egress gate: it reads to a fresh signed head until everything the head says the provider accepted is read, there is no gap or fault, and nothing new has been read for `quietMs`; then one more signed head must show nothing new: the same last seq the drain found quiet, with nothing read since (collector `provider-feed/8`; under `/3` to `/7` a background read between the quiet check and that head could leave a drain quiescent just after an entry arrived, so a saved run under those labels may carry such a drain). It is capped at ten quiet periods and two feed requests within the shared cap; each read is bounded by the time left, so it never waits past the cap, and its recorded `waitedMs` never exceeds it. A drainer whose run-end window then fails (its final mark could not be taken) is recorded neither quiescent nor clear. Its record in `settlement.drains` has the egress shape; `markClear` means the final mark read up to its signed head, and `closedAfterCollect` means a fault or a seq gap came after the first late collect. The validator binds a lone entry's seq after its window's own events and to its own event in the following gap, and admits scoped feed windows and feed drains only under `provider-feed/3` on a witnessed endpoint record.
- **Later outcomes (collector `provider-feed/5` records them; `/6` judges them).** A feed may declare `"outcomes": { "waitMs": <0 to 30000> }` (default 0), only on an endpoint with a witness. It then reads one more entry type, signed like every other, with exactly these body fields and no others:

  ```json
  { "feed": "<feedId>", "epoch": "<epoch>", "seq": 57, "id": "<provider event id>", "type": "outcome", "at": "<ISO 8601>",
    "messageId": "<the provider's id of a message it accepted>", "recipients": ["<bare address>"], "outcome": "failed", "app": {} }
  ```

  - `outcome` is one of six words, mapped by the stub or adapter from the provider's own event type (ScopeHaven never maps a provider type): `succeeded` (the provider completed it: delivered to the recipient's server), `deferred` (still trying), `failed` (it did not happen: a permanent bounce, a drop, a reject after accept), `reversed` (done, then undone), `contested` (left open, or a type the adapter cannot map with confidence) and `complained` (the recipient reported spam). Soft bounces and temporary failures that a provider does not document as retried read `contested`.
  - `messageId` must be the provider's own id of an earlier `accepted` entry in the same epoch, never an app header, tag or metadata value; `recipients` is optional (omitted: every recipient of that message), each a bare address of that message. An outcome entry comes after its accept, so an adapter over unordered webhooks holds it until the accept is in the feed.
  - Each outcome binds to the sends it names: the message's events read in the run (an accept read after start), one per recipient by canonical address. The run's settlement record then carries, per such feed, `{ instanceId, clear, waitedMs, records }`, where each record is `{ of: <the send's event seq>, outcome: <word> }`: the observer's own seq, never a provider id or an address, and only for a send a window of the run holds as committed. Records stop at the signed head of a later mark taken when the later wait ends.
  - A message id seen more than once in the epoch (before the run, on a rejected entry, or reused after the send), or a named recipient that maps to no event or to two, makes every send of that message read `ambiguous`.
  - `clear` is false for the rest of the run after any refused outcome entry (a word outside the six, a key outside the list, an orphan outcome before or without its accept, a recipient that cannot be bound, a repeated event id, more than 16 words for one send or 20000 records in a run), any `status` entry, a fault, or a later mark that did not read up to its signed head with no gap. Each refused entry also leaves the window it lands in partial. An outcome for a message accepted before the run, or for the witness message, binds nothing and is not refused.
  - The later wait: once the final mark is taken and every run-end and barrier window is collected, each such feed reads on for up to its `waitMs` (never past the run deadline less the end-of-run probes), then takes a later mark. Nothing a window, a drain record or a verdict reads can depend on it: a send that arrives during it is in no window, so it binds no record. A feed with no in-run send to bind does not wait.
  - A feed that does not declare `outcomes` reads an `outcome` entry as an unknown type (the window is partial), as before. The records are sealed and bound by the run validator to committed sends of their own feed.
  - **The verdict stage (`provider-feed/6`, `src/later-outcome.mjs`).** It reads the clauses after settlement, attribution and pairing, and its findings apply after app-log admissions, only to a clause that still passes there (an admitted clause keeps its fail and its app-log tag). It only ever lowers a positive pass (`effect.exists`, `effect.count` of at least one, a success claim). A send's words fold in feed order: `ambiguous`; `conflicting` (a success after a failure or reversal); `withdrawn` (a failure or reversal after the last success); `contested` (open until a later failure); `succeeded`; or `pending`. On a feed whose `clear` is false every send reads `unobserved`. A pending or succeeded send credits the clause: a pass means accepted and not failed within the horizon, not delivered.
    - When any matched send does not credit, the clause is judged again over its own windows without those sends, through custody, settlement (its own-window rules) and attribution (background, returned-id owners, late fails). The pass stands only when that judgement passes on a send held outside the application, so a record the application wrote never keeps it.
    - Otherwise a boundary check reads the judgement (a fail where the rest decides absence) when only withdrawn sends were removed, and inconclusive when any withheld one was. An allowed-use control always reads inconclusive. Each carries `later: <reason>` (`effect-later-failed`, `-unobserved`, `-ambiguous`, `-conflicting`, `-contested`).
    - A pass whose every matched send reads `succeeded` carries `laterStrength: "succeeded"`. A repair over a later failure is credited (`compareRuns`) only at that strength, and anything weaker reads `unverified` (`baseline-fail-provider-later`).
    - Absence clauses (`effect.none`, a count of 0, refusal claims) and `effect.only` never read outcomes. Every accepted attempt counts there, so a forbidden send that bounced still fails, and two attempts with one bounced still fail `expected: 1`.
    - A lifecycle change check the stage withheld leaves its post-change checks reading change-not-attributed, as an attribution withhold does. A run recorded under `/5` keeps its records inert.
- **Correlation.** Nothing the app writes places an entry in a window. A provider record names no acting principal, so an actor-pinned selector does not see it. Two checks whose sends the records cannot separate are settled by the run's settlement rules (`effect-ambiguous-attribution`, `effect-outside-window`): never released, only withheld.
- **Limits.** A provider feed proves only that provider's pipe was live, not that the app has no other way to send mail. Authoritative absence also rests on the feed's order being the provider's acceptance order with every entry in the feed before the send call returns: an operator adapter over a real provider whose records arrive late (Mailgun documents about 30 minutes) cannot promise that, so such a feed must not declare a witness. Sequences cannot use it. A message the provider accepted after the run's final mark is not observed, nor is an outcome the provider records after the later wait ends.

## App action log (`appLogs`, not an observer)

Many apps keep a log of the actions they take: "email sent to X", "ticket 41 updated", "refund created". A target may declare one under its own key, `appLogs` (never in `observers`), and ScopeHaven reads it with each check. It works on fields the log already has; the application needs no change.

```json
"appLogs": [{ "id": "actions", "use": "record",
  "log": { "file": { "path": "/abs/actions.jsonl" } },
  "fields": { "action": "/event", "outcome": "/result", "actor": "/actor", "target": "/to", "at": "/ts", "id": "/event_id" },
  "outcomes": { "committed": ["ok"], "denied": ["refused"], "error": ["error"] },
  "rules": [
    { "action": "email.sent", "operation": "send", "vocabulary": "mail", "domains": [{ "domain": "customers.example" }], "observedAs": ["provider-feed"] },
    { "action": "refund.created", "operation": "send", "vocabulary": "egress", "name": "pay.example", "resource": "POST /v1/refunds", "observedAs": ["http-egress"] },
    { "action": "order.updated", "operation": "update", "vocabulary": "named", "name": "orders" } ],
  "ignore": [{ "action": "page.viewed" }],
  "logActors": { "agent-a": "u-17" } }]
```

- **App-reported, never custody.** The application writes this log, so what it says is the application's own account, labelled app-reported everywhere. It never decides a custody verdict, and an application that writes a false log defeats anything it would say. Nothing about the tier makes a log-tampering application visible on a path no independent observer also sees.
- **`"use"` is required, with no default.** With `"record"` each check's lines are mapped to effect events (source `app-log`, custody `subject-writable`, presence-only) and sealed beside the check's observer windows as `data.appLogWindows`, and no verdict, custody tag, settlement finding or backend-evidence row changes. With `"admission"` they are also read against the application (`src/app-log-verdicts.mjs`), after every custody rule: a clause that did not fail reads fail when the log records, as committed, an action of the check's own actor in the check's own window that the clause forbids. Its custody is then `subject-writable`, its backend observation not authoritative, and it carries `appLog: { finding: "app-log-unobserved-admission", log, entries, contradicts, custodyVerdict }` (contradicts: an observer held outside the application covered the window and recorded nothing). A test runs the example corpus as shipped, with `"record"` and with `"admission"`: the first two match on every row, and the third differs only by admissions.
- **Whose entries.** Only entries of the check's own app-log window (before its cut, so never a late line), by its own principal, committed, fitting no declared background source (an actor-pinned source never fits the check's actor; a shape-only source fits by operation and name, and by its exact egress resource `"<METHOD> /path"` too where every rule of the entry's name is an egress rule with an exact resource, so a background job on another path of the same host is told apart by the application's own action word) and fitting no selector of an earlier check by the same principal (read as attribution reads a check's selectors: an entry with no resource fits a resource-pinned selector, and a selector with only source or trace pins fits every entry). Every other entry decides nothing. Limit: an earlier check that declares no effect and no claim offers no selector, so a late line of its own that lands in this check's window is not set aside.
- **What an admission can read.** `effect.none` and a refusal claim: any such entry. `effect.count` without countBy: more such entries than expected (never on a window with a repeated entry id). `effect.only` without countBy: an entry outside the declared set or beyond its count, judged over the check's entries alone (never on a window with a repeated entry id); an allow pinned to a background actor never excuses the check's own actor. Never `effect.exists`, a success claim, countBy, or absence in the log. A selector pinned to an observer source is read only where every rule of its exact name lists that source in `observedAs`. When an `effect.only` clause has selectors the log cannot read, an entry is judged against the rest only if every rule of its name lists each unreadable selector's source in `distinctFrom` (`"distinctFrom": ["provider-feed"]`: the operator's statement that this action is never that source's effect); any other entry is set aside, never offending and never counted. Field pins read a rule's declared constants (`"fields": { "/template": { "const": "ticket_update" } }`) or a value read from the line through a closed word map (`"fields": { "/template": { "from": "/params/template", "values": { "ticket_update": ["ticket_update", "TicketUpdate"] } } }`): a listed word (type-strict) captures its selector value, a string; any other word, a missing pointer or a non-scalar captures nothing, so the field reads unknown, and only `equals` and `in` can decide on it. The run validator refuses a captured value the map does not name, and a profile whose clause pins a word-mapped field with a non-string `equals` or `in` operand is refused at load (the log and the recorder would read the same send by different types). An egress rule's exact resource must name a path the recorder declares for its host, `distinctFrom` never names the source that records the rule's own kind of send (`http-egress` for an egress rule; `smtp-capture` and `provider-feed` for a mail rule), and an earlier check's field pins are set aside when its late line is told apart (they say what that check must or must not do, not what it did). Upstream and trace pins never match. A countBy clause (`effect.count` or `effect.only`) is read only on lines whose every rule declares `"lines": "per-application"` (the operator's statement that the application writes one line per application); lines that share the key the log names (`fields.key`: any JSON value of at most 1024 characters, kept only as a digest keyed with a secret the run does not keep; a longer one leaves countBy clauses on that window unread) and their name and resource are one application, and any line of a rule without that declaration leaves the clause unread. A background job may be given its own principal: `logActors` may map the actor pin of a declared background source (`"svc-digest": "system"`). An `effect.only` clause may write `"allowBackground": ["<source id>"]`: at the custody tier it is exactly the shape-only allow it expands to (the source's select without its actor pin), and admissions never let it excuse the check's own actor. Under `"use": "admission"` that needs an actor-pinned source whose principal `logActors` maps and `fields.trace` (the correlation value the application received, which needs the target's `correlation` header). Because a job may log its lines under the requesting user, and may carry the request's trace context, an own entry that fits an actor-pinned background source's shape (actor and resource set aside) counts only when, in the check's own window, custody recorded nothing the job could be or the log names the job's own principal on a committed line of that shape, and only when the line carries the check's own correlation token. With `fields.trace`, a line carrying another check's token is that check's. A token says which request context wrote a line, not which request caused it, so the earlier-check late-line rule applies whatever the token. The clean corpus (`test/app-log-clean-corpus.test.mjs`, `examples/app-log-notify-app.mjs`) runs six honest builds, none admitted, and one leaky build, admitted once; its same-path corpus (the job on the agent's own path and template) runs ten honest builds, none admitted (the job logged as itself, as the agent without a trace, with its own trace, with the request's inherited trace, mixed with its own trace, mixed with the inherited trace, and twice in one window, once as itself and once as the agent with its own trace; an own allowed message; a keyed retry logged twice; an aborted attempt), and one leaky build, admitted on both status clauses, and shows that a profile with `allowBackground` and one with the expanded allow written by hand reach the same custody verdicts.
- **Repairs.** A baseline fail that rests only on admissions is `unverified` in a comparison (`baseline-fail-app-admitted`), never fixed or restored, so the gate reads `comparison-incomplete`. An admitted lifecycle change check keeps the run valid: its post-change checks read `change-not-attributed`.
- **Kept apart by construction.** App logs are not observers: the connector reads them in their own list, every custody entry point refuses an app-log window (`custodyWindows` in `src/effect-events.mjs`), and the run validator binds `appLogWindows` to the run's `appLogs` record apart from the observer windows.
- **When it is read.** Each mark is a local file read (a stat, the last line and the 4 KiB before the mark): the start mark after every observer's start mark, right before the check request; the cut right after the observers' end marks, before any witness request; the window itself after every observer has been collected. It sends no request, holds no port and adds no wait; only those small reads run inside the observers' windows. Lines after the cut (a witness's side effects, a late flush) are not the check's, and neither is a line already being written at the start mark.
- **Mapping.** `fields` are JSON pointers (`action` and `outcome` required, `actor` required, `target` for mail). Each rule maps one action: `egress` (a declared host and a literal resource in the egress recorder's form), `mail` (each recipient named as the SMTP sink and the provider feed name it: the recipient's domain and a declared address or `*`) or `named` (a literal name and a resource, literal or read from the line with `{ "from": "<pointer>" }`; its `observedAs` may name an application-store source or telemetry). `logActors` maps each declared principal to the one log value that names it, one to one. Every line must be a mapped action, an ignored action, or mail to a declared observer's witness domain; an unknown action, an unmapped outcome word, an unusable recipient, an unparsable line, a repeated entry id or a line still being written at the cut leaves the window partial.
- **Consistency at marks.** Each mark fingerprints the 4 KiB before its position. The range is read once, after every observer was collected, and only when both fingerprints and the file's inode still match: a rotated or truncated file, or one rewritten in the 4 KiB before a mark, fails the window. Other rewrites of earlier lines are not detected; the application writes the file. It is opened without following links and without blocking, and anything but a regular file reads failed. Lines written before the run started are never read.
- **Refused at load:** a missing or other `use`, more than one app log, a file that is also an `audit-file` log or a provider feed's file, an actor map that is not one to one or names no checking actor, a background source pinned to a checking actor's principal, and the later version's keys (`cause`, `job`, `witness`, `canaries`, an `endpoint` log).

## MySQL snapshot observer (`mysql-snapshot`)

Each mark reads the declared InnoDB tables in one `REPEATABLE READ`, `READ ONLY` transaction started `WITH CONSISTENT SNAPSHOT`. The session time zone is pinned to UTC and `sql_mode` to MySQL 8.4's default. Statements run one per query; multi-statements are never enabled. For every row the mark reads its key and `MD5(JSON_ARRAY(<every column>))`, computed in the server. No other column value leaves the server, except the change column's stamp for a table that declares one. The client (`mysql-wire.mjs`) has no npm dependency.
- It speaks `caching_sha2_password` (the fast path, and full authentication by encrypting to the server's RSA public key) and `mysql_native_password`.
- Full authentication encrypts the password only to a key the operator pins in `<credentialEnv>_RSA_PUBLIC_KEY` (the PEM of the server's `public_key.pem`, for example `SCOPEHAVEN_TARGET_APP_DB_READER_RSA_PUBLIC_KEY`). A key the server offers is never asked for or used, and without a pinned key full authentication is refused (`authentication-refused`) before any password byte is sent. The fast path and `mysql_native_password` need no key. A `credentialEnv` longer than 95 characters after `SCOPEHAVEN_TARGET_` leaves no room for the suffix, so it cannot carry a pin (full authentication is then refused).
- It refuses `mysql_clear_password`, any other plugin, an empty password, and a server without `CLIENT_DEPRECATE_EOF`.
- It connects only to the literal `127.0.0.1` and drops the password after the handshake.

```json
{ "id": "db", "type": "mysql-snapshot", "host": "127.0.0.1", "port": 3306, "database": "app", "credentialEnv": "SCOPEHAVEN_TARGET_APP_DB_READER",
  "tables": [{ "table": "notes", "key": "id", "changeColumn": { "column": "updated_at", "audit": "SOURCE-CHECK-notes-updated_at.md" } }], "maxCommitLagMs": 1000, "settleMs": 1000, "tableIds": true }
```

- **Net-only by default.** InnoDB exposes no row versions to a reader. Inserts, updates and deletes are the net difference between marks. These are not seen:
  - a write undone within a window;
  - an `UPDATE` that sets the values a row already has, which changes nothing.
- **Exact absence needs a change column the server sets.** Each mark checks the schema. The column must be a `TIMESTAMP` defined `DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP`, which means the server stamps every insert and every update that changes the row.
  - `DATETIME` is refused. Its stamp is written in the writer's session time zone, so a fresh stamp from a session behind UTC looks hours old.
  - A constant default is refused, because a delete and reinsert (or `REPLACE`) would then land an old stamp.

  A source-check file must also record that no writer sets the column. Any of these writers leaves the old stamp on a changed row:
  - the app's code;
  - SQL the agent can run;
  - a session that sets its own clock (`SET timestamp`);
  - a trigger that sets it;
  - a foreign-key cascade, which does not stamp.

  With the column and the source check in place:
  - a named row whose column is unchanged between marks had no committed update;
  - a moved column is an update even when the content was reverted.

  The guard uses the server's own clock (`NOW(6)`, read before the snapshot starts), so there is no host-to-server skew. These rows are ambiguous:
  - rows stamped within `maxCommitLagMs` (plus one tick of the column's precision) of the start mark;
  - a NULL or zero-date stamp;
  - rows present at one mark only.

  A table-wide or prefix selector is never exact. Content that changed under an unchanged column voids the table's exactness and reports none of its changes. A write not yet committed at the end mark is not in it, so declare `settleMs` of at least `maxCommitLagMs`.
- **Rows must be identifiable across the marks.** These fail the window with no events:
  - a recreated or rebuilt table (`CREATE_TIME` changed: `ALTER TABLE` rebuilds, `OPTIMIZE`) or changed column names or types (`relation-rewritten`);
  - a table created or rebuilt in the same second the start mark reads it (`relation-unverified`): `CREATE_TIME` has whole seconds, so a second rebuild in that second would keep it;
  - a NULL or duplicated key (`duplicate-key`).

  `TRUNCATE` is not among them unless `tableIds` is declared. On MySQL 8.4 it keeps `CREATE_TIME` and removes every row, so the window reports each row as deleted. It does give the table new InnoDB ids, so with `tableIds` it fails the window (`relation-rewritten`).

  Partitioned tables, views and other engines fail the mark. So does a server with `read_only` set (a replica, usually); a replica without it is not detected.
- **Swapped tables need `tableIds`.** `CREATE_TIME` is the only table identity a SELECT-only reader can see, and two swaps keep it. On MySQL 8.4, observed live:
  - `ALTER TABLE <other> EXCHANGE PARTITION ... WITH TABLE <declared>` swaps the declared table's rows and keeps its `CREATE_TIME`, even with a twin created seconds later;
  - `RENAME TABLE` of a twin created in the same second as the declared table also keeps it.

  Without `tableIds`, either swap reads as the same table. Both need DDL rights on the declared table.

  With `"tableIds": true`, each mark also compares InnoDB's table and tablespace ids (`information_schema.INNODB_TABLES`). Both swaps change those ids, so the window fails (`relation-rewritten`). The reader then needs the `PROCESS` privilege, which also lets it see other sessions' statements. Ids it cannot read fail the mark (`table-ids-unreadable`, or `permission-denied`). The lookup matches the dictionary name byte for byte (`BINARY`, since the column's collation ignores case) and must find exactly one row. Each exact entry's basis says which identity it rested on, so a saved run shows whether `tableIds` was on.
- **The server is not authenticated.** MySQL's native login plugins prove the client to the server, never the server to the client: a process that took the loopback port first could answer the marks. The Postgres observer's SCRAM check has no MySQL equivalent here. That is why the RSA key for full authentication is pinned rather than taken from the server: such a process could offer its own key and decrypt the password. It still sees the login scramble, which a weak password does not survive offline. With a pinned key it cannot read the password, but if the real server is reachable somewhere else it can relay the encrypted password there and sign in as the reader: only TLS with server verification would rule that out, and this client does not speak TLS.
- **Live tests.** `mysql.live.test.mjs` runs against a disposable server named by `SCOPEHAVEN_MYSQL_LIVE=user:password@127.0.0.1:port` and is skipped without it. It passed 5/5, three times, on MySQL 8.4.11 (2026-10-06):
  - full caching_sha2 authentication;
  - an untouched row exact; an update, a write-and-revert, inserts and deletes;
  - an explicit stamp write voiding the table;
  - rebuild, `OPTIMIZE`, an added column and a same-second rebuild failing the window; `TRUNCATE` reading as deletes;
  - a revoked `SELECT` failing the window;
  - `DATETIME`, constant-default and partitioned tables refused;
  - a writer at -04:00 and `REPLACE` both seen;
  - `EXCHANGE PARTITION` unseen without `tableIds`; with it, `EXCHANGE PARTITION`, a same-second `RENAME` swap and `TRUNCATE` fail the window.

  The scripted fake (`fixtures/fake-mysql.mjs`) covers the rest. Since the key pinning (2026-10-16), the live tests' full authentication also needs `SCOPEHAVEN_MYSQL_LIVE_KEY`, the path of the server's `public_key.pem`; they have not been re-run since that change.
