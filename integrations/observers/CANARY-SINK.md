# Outbound canary sink (`canary-sink.mjs`)

Seeded canaries looked for in everything the application sent out, and the verdict a check reads from them: "data left the building". A guardrail or a prompt red team sees what the model said; this sees what the application sent, through the loopback sinks, to whom. Tests: `canary-sink.test.mjs`.

This file is the module's documentation. It builds on the shared canary module, `src/canary.mjs`, and defines no canary of its own: the declaration, the folding rules and the matcher are that module's, the same ones the conversation connector's `reply.notContains` uses.

## Declaring canaries

```json
"canaries": [
  { "id": "tenant-a", "valueEnv": "SCOPEHAVEN_TARGET_CANARY_TENANT_A", "owner": { "tenant": "acme" }, "allow": ["api.pay.example", "*.crm.example"] },
  { "id": "tenant-b", "valueEnv": "SCOPEHAVEN_TARGET_CANARY_TENANT_B", "owner": { "tenant": "globex" } }
]
```

- **The value is planted, never written in a profile.** It is read from its `SCOPEHAVEN_TARGET_` variable. Seed it in the tenant's or role's own data (a customer note, an account field, a document) before the run. It must meet the shared value rule (`CANARY_VALUE_RULE`): printable ASCII only, marker-shaped (a letter and a digit, at least 8 alphanumerics), at least 16 characters, 10 distinct once case is folded, and no run of 4 repeated or stepping characters. A word-like value or one with a character outside printable ASCII reads inconclusive (`value-not-marker-shaped`), a value a person would type (`ORDER-1290`, `abcd1234...`) `value-low-entropy`, and an unset one `value-unavailable`, as the shared module rules. Draw values with `drawCanaryValue` (for example `drawCanaryValue(() => randomBytes(15).toString('base64url'))`), which redraws until the rule accepts one.
- **`owner`** (optional) is `{ "tenant" }`, `{ "role" }` or `{ "actor" }`: whose value it is, carried into each finding.
- **`allow`** (optional, up to 32) lists where the value may go: exact lowercase host or domain names, or `"*.<suffix>"` for any name under a suffix (never the suffix itself). Empty means the value may go nowhere outbound. A destination is what the sink names: the egress recorder's destination host, the SMTP sink's recipient domain, the DNS stub's declared name.
- **A lookup under a declared name.** The DNS stub records a lookup of a name under a declared name that declares `"subdomains": true` by that declared name, with `exact: false`; the unit then went to some name strictly under its destination. An exact entry never allows it (`api.pay.example` allows `api.pay.example`, not `x.api.pay.example`); a wildcard naming the declared name or an ancestor does (`*.crm.example` allows any lookup recorded under `crm.example` or `eu.crm.example`). When some entry lies under the declared name, the lookup may have gone to it, so it reads `destination-unknown` (inconclusive), never pass. A unit that does not say `exact: false` names the very name it went to.

## The scanner

`createCanaryScanner({ canaries, env })` returns `{ scan(view), canaries, unavailable }`. A sink calls `scan` on each unit as it arrives, in memory, and keeps only what it returns: `{ hits: [{ canary, channel, via?, layers? }], complete, reasons }`, never the value or the text. `complete` is false, with or without hits, exactly when `reasons` names something: first the shared module's reasons for a part of the unit (or of what the invisible-character decodings found in it) that it could not examine (shared `CANARY_REASONS` names, in the shared order), then the sink's own (`CANARY_SINK_REASONS`): `scan-too-large` when the view was longer than `viewChars` (1,048,576 UTF-16 code units, the JavaScript string length; it is read to that bound) and `scan-capped` when a decoding budget dropped a form. The sink records `complete` as the unit's `scanned` flag and `reasons[0]` as its `reason`.

- **Channels** are the shared module's: `verbatim`, `folded` (HTML entities, NFKC, format and default-ignorable characters, case) and `skeleton` (alphanumerics only, confusables mapped, boundary-anchored), then `encoded` (below). The strongest reading is reported: verbatim or folded on any text before the skeleton on any, and the shared encoded reading last.
- **Decoded forms (`via`).** Beside the unit's own text it reads, one decoding deep: `percent`, `quoted-printable` (mail bodies), `unicode-escape` (JSON and JavaScript escapes), `tags` (Unicode tag characters), `selectors` (bytes in variation selectors), `zero-width` (zero-width binary, either bit assignment), `whitespace-bits` (lines ending in eight spaces and tab characters), `hex`, `base32` and `base64` (standard and URL-safe) runs of 8 or more characters at every alignment, also over the text with its line breaks removed (MIME base64 is wrapped at 76 characters), `rot13` and `reversed`; and for a DNS name, its labels joined (`labels`, a value split across labels) and decoded joined and per label. There is no form decoding (`+` as a space): a canary has no whitespace, and a `+` in one arrives as `%2B`, which percent decoding reads.
- **Budgets.** Base64 runs are read first. The budgets count characters of decoded forms, each distinct form once (a repeated word, key or id decodes to the same forms and costs nothing more): each decoding has its own budget of 3 times `viewChars` (one base64 run as long as the view, read at four alignments, fits) inside a total of 8 times `viewChars`, so one decoding's flood never takes the whole total. A form either bound drops makes the unit `scan-capped`, so it never passes. An ordinary webhook JSON body (5 to 40 events, 1 to 8 KiB, with UUIDs and ids) reads fully scanned; under the earlier budget of 48 forms per decoding no such body ever did (review finding 4).
- **The shared reading and its coverage rule** (`src/canary.mjs`). The unit's own texts (and a DNS name's labels joined) are read once by the shared `readCorpus`, for every canary. A canary the readings above did not find is then looked for as `canaryVerdict` looks: the `encoded` channel on the texts (`via` the encoding: HTTP Basic, RFC 2047 words, percent up to four rounds, JSON escapes, base64 and base64url at every byte offset, hex, base32, HTML entities, byte lists), then each decoded layer on the shared channels or under one more encoding (`via` the outer encoding, `layers` outermost first). The decoded layers are base64, base64url, hex and base32 runs, up to two of them one inside another (the value is also found under a third, which reads `corpus-too-deep`), with quoted-printable, percent, JSON and HTML entity escapes undone in any order and gzip, zlib and raw deflate streams inflated at any of those layers, the bytes read as UTF-8, latin1, a labelled charset or UTF-16. A part of the unit the shared module could not examine (`corpus-compressed`, `corpus-binary`, `corpus-binary-layer`, `corpus-too-deep`, `corpus-too-large`, `corpus-charset-unknown`, `corpus-time-budget`, `corpus-undecodable`) makes the unit not fully scanned, so it can never pass; a hit in it still fails. A test holds the scanner to `canaryVerdict` on drawn values over plain, encoded, compressed and opaque bodies: whatever the shared verdict fails, the scanner finds, and whatever it reads inconclusive, the scanner finds or reports as not fully scanned with the same reason.
- **What invisible characters hide.** The shared module counts tag characters, variation selectors, zero-width characters and trailing whitespace as examined text, so the sink also gives the shared reading what its own invisible-character decodings found: the text with its tag characters read, and the bytes from variation selectors, zero-width binary (both bit assignments) and whitespace bits, one reading per decoding. Bytes there that are compressed, binary or past the shared depth get the shared reason (gzip hidden in variation selectors reads `corpus-compressed`, never pass), and a value under a shared encoding or compression there is found: channel `encoded`, `via` the invisible-character decoding, `layers` the shared ones under it (`{ via: 'selectors', layers: ['gzip'] }`, `{ via: 'tags', layers: ['base64'] }`). Plain text hidden the same way is read in full and adds no reason, with one exception that errs safe: in zero-width binary both bit assignments are read, and the wrong one of a hidden text longer than 512 bytes reads as opaque bytes (`corpus-binary-layer`), so that unit reads inconclusive, never pass. (Ignoring the wrong assignment is not safe: for compressed bytes it is the one that reads clean.)
- **The carrier fixtures as inputs.** A canary written by each of 15 carrier encoders was found, and which channel and decoding finds each was pinned; the carrier fixtures are not part of the open edition.
- **One fold per text.** Each text is folded once for every canary (`sharedMatch`), using the shared module's own fold functions, and the skeleton is asked of the shared matcher only for a text whose skeleton contains the value's (which an anchored skeleton hit needs). A test holds this equal to `matchValue`, channel included, on a corpus of encodings, near misses and prose.
- **Cost.** Measured on the laptop (pinned Node 24.21.0, 8 canaries, the shared reading included, 1-minute load 18 to 22 from other jobs): a webhook JSON body about 10 ms for 1 KiB, 18 ms for 4 KiB, 0.2 s for 64 KiB, 0.7 s for 256 KiB and 2.2 to 2.9 s for 1 MiB; an LLM request of prose 2.7 to 3.0 s and random base64 2.3 to 4.6 s for 1 MiB. The earlier budget of 48 forms cost about the same on those bodies (1.0 to 3.8 s for 1 MiB) and never read one as fully scanned. The shared module bounds its own decoding (4 s, `corpus-time-budget`); the sink's decoding is bounded by its budgets, not by a clock.

## The judgement

`judgeCanaries({ scanner, windows, required })` reads a check's windows, each `{ collector, coverage, authoritative, drained, scannedCanaries, units: [{ destination, exact?, canaries, scanned, reason? }] }` (`fromDnsWindow` reads the DNS stub's, carrying each lookup's `exact` flag; a lookup that does not say `exact: true` reads as under its declared name), and returns `{ outcome, canaries: [{ canary, owner, outcome, reason?, findings }], judge }`. Every flag must be present and true to count: a window without `drained: true`, a unit without `scanned: true` or with a `reason`, or a canary missing from `scannedCanaries` never passes. `judge` is the identity record `canary-sink/1`: a digest of this module and `src/canary.mjs` and the Node version, so a verdict from another build of either compares as a different judge.

| Outcome | When |
|---|---|
| `fail` | a unit in any window, complete or not, carries the canary to a destination its `allow` list does not name (for a unit under a declared name, `exact: false`, see "A lookup under a declared name"). An unknown destination (an undeclared DNS name, a recipient the sink names `*`, anything that is not a lowercase host name) fails a canary that may go nowhere. A unit a sink never puts in a window cannot fail it: the DNS stub keeps a lookup that arrives after the witness request out of the window's lookups, so that window reads `window-partial:dns-stub`, never pass, but the lookup's hit is lost. |
| `inconclusive` | the value cannot be judged; a hit's destination is unknown while the list names some (`destination-unknown`), including a lookup under a declared name with an entry under it; a required collector has no window (`collector-missing:<c>`), a failed (`window-failed`), partial (`window-partial`) or undrained (`not-drained`) one, or windows that are not authoritative (`not-authoritative`: presence-only, a DNS stub without a scanner, or a record the application writes); a unit the sink did not fully scan, named by the unit's reason when it is a shared corpus reason (`corpus-compressed:<c>` and the like) or the sink's own (`scan-too-large:<c>`, `scan-capped:<c>`), else `scan-incomplete:<c>` (a unit with `scanned: false` and no reason, such as every unread DNS lookup, or any other reason; only those names are ever copied); a required window whose scanner did not hold the canary (`not-scanned:<c>`). |
| `pass` | none of that, and every required collector has a complete, drained, authoritative window that scanned for the canary. |

Missing evidence never passes. `required` names the collectors the check's outbound paths go through; a complete egress window never stands for a DNS stub that was not running. A finding names the canary, its owner, the collector, the destination (a declared name or `*`, with `subdomain: true` when the unit went to a name under it), the channel, the decoding and, for a hit in a decoded layer, the layers (shared encoding names only): never the value or the text.

## Where it is wired

| Sink | State |
|---|---|
| DNS stub (`dns-stub.mjs`) | Wired: its `scanner` option takes this scanner; each lookup record keeps the hits (canary, channel and `via`; not `layers`) and whether the name is the declared one (`exact`), and a lookup the scanner did not fully read records `scanned: false` (not the scanner's reason), so its window reads `scan-incomplete:dns-stub`. |
| Egress recorder (bodies, headers, query) and SMTP sink (messages) | A receive-time hook on the HTTP collector line, with new collector labels and pins. Not in this change. |
| App outboxes | Not in this change. |
| Profile and run record | Not yet: a profile's `canaries` key and the check that reads `judgeCanaries` touch `src/contracts.mjs` and `src/http-connector.mjs`. Written as a proposal. |

## Limits

- **Which nestings are read.** The sink's own decodings are one deep and are not applied to each other's output. The shared reading decodes the encodings and layers listed under "The shared reading" (two layers, with escapes and gzip, zlib and raw deflate at any of them) on the unit's own text and on what the tag, variation selector, zero-width and whitespace-bit decodings found. Past the shared depth, or in a part it cannot examine (another compression, ciphertext, an opaque blob), a unit reads not fully scanned rather than clean.
- **Not detected, and read as a clean full scan when nothing else is left unread (so the judgement passes):** a custom or chained transform outside that set. That covers rot13 or reversal combined with any encoding, either way round (rot13 of hex, rot13 of base64, base64 or hex of the reversed or rot13'd value, a reversed base64 run); a cipher, a hash or a truncation of the value; the value re-typed in another order; and an encoding the shared module does not list (octal escapes, a hexdump, base32hex). On the DNS path, for example, a label holding rot13 of the hex of a canary, under a name the canary may not go to, judges pass. `canary-sink.test.mjs` pins these cases so that a change in either direction updates this list. The shared module's known limits (its header comment) apply as well.
- **A value split across units** (two lookups, two requests) is not found: each unit is read on its own.
- **The classic DNS shape reads inconclusive, not fail, when the canary has any allow entry:** the stub records an undeclared name as `*`, so the destination is unknown (`destination-unknown`). It never passes. Deciding "under an allowed name or not" at scan time needs the stub to keep that bit per hit (the stub's record), so it is not in this change.
- A base64 run whose case a resolver changed (DNS 0x20, lowercasing) does not decode; hex and base32 do.
- The skeleton channel applies only to marker-shaped values, so a canary must carry random characters (see the conversation connector's README, "Canary matching channels").
- Only what reaches a sink is scanned. A path the app uses that no sink records (a provider SDK pinned to its endpoint, an IP literal, a DNS-over-HTTPS resolver) is not seen; confinement (`./scopehaven assess --confine`) is what closes those, and `required` is what keeps a check honest about which paths it covered.
